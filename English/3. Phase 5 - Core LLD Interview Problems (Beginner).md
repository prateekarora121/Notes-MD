## How to Approach ANY LLD Problem

Interviewers do not just want the "answer". They want to see a **structured thought process**. Use this 6-step method every single time. It turns a scary open-ended prompt into a checklist.

### Step 1 — Clarify Requirements & Scope
Never start coding immediately. Ask clarifying questions. Nail down *functional* requirements (what it does) and *non-functional* ones (thread-safety, scale, latency, extensibility). Explicitly state what's **in scope** and **out of scope** (e.g., "I'll assume single-machine, in-memory, no persistence unless you want it").

### Step 2 — Identify Entities / Classes (the "nouns")
Read the problem and pull out the **nouns** — these usually become your classes/interfaces. Logger → `Logger`, `LogLevel`, `ILogAppender`, `ILogFormatter`. Give each a *single clear responsibility*.

### Step 3 — Define Relationships
How do entities relate? Use the right relationship:
- **Composition ("has-a", strong ownership)** — a `Directory` *owns* its files. Delete the directory → files gone.
- **Aggregation ("has-a", weak)** — a `Logger` *uses* appenders that can live independently.
- **Inheritance / Realization ("is-a")** — `ConsoleAppender` *is-an* `ILogAppender`.

Rule of thumb: **favour composition over inheritance.**

### Step 4 — Apply SOLID + Design Patterns
Now shape the design. Ask: "Which part varies?" — that variation is a *seam* for a pattern. Formatting varies → **Strategy**. Object creation is complex → **Factory**. Behaviour changes with state → **State**. One shared instance → **Singleton**.

### Step 5 — Handle Edge Cases & Concurrency
Talk about `null`/empty inputs, invalid operations, resource cleanup, and — very important for SDE-2 — **thread-safety**. Will multiple threads call this? What's shared mutable state? How do you protect it (`lock`, concurrent collections, immutability)?

### Step 6 — Walk Through the Code
Trace one real scenario end-to-end (e.g., "user inserts money → selects item → machine dispenses"). This proves the design *works* and catches gaps.

> **Golden rule:** Talk out loud, draw boxes and arrows, and *leave seams for extension*. A good LLD answer is easy to change tomorrow.

## Quick Refresher: SOLID + Common Patterns

| SOLID | One-line meaning |
|-------|------------------|
| **S**ingle Responsibility | One class, one reason to change |
| **O**pen/Closed | Open to extend, closed to modify |
| **L**iskov Substitution | Subtype must work wherever base works |
| **I**nterface Segregation | Small focused interfaces > one fat one |
| **D**ependency Inversion | Depend on abstractions, not concretes |

| Pattern | Use when… | Interview keyword |
|---------|-----------|-------------------|
| **Strategy** | An algorithm/behaviour is pluggable | "formatter / pricing / sort varies" |
| **Factory** | Object creation logic is centralised | "create appropriate object" |
| **Singleton** | Exactly one shared instance | "global logger / config" |
| **Observer** | Many listeners react to an event | "notify subscribers" |
| **State** | Behaviour depends on internal state | "machine in different modes" |
| **Composite** | Tree of part-whole objects, treated uniformly | "file & folder same interface" |
| **Chain of Responsibility** | Pass a request through handlers | "filtering pipeline" |

## Problem 1 — Design a Logger

A logging library like log4net / NLog / Serilog. This tests **Strategy**, **Singleton**, **Observer/Appenders**, filtering, and **thread-safety** (loggers are hit by many threads at once).

In real .NET projects you would almost always reach for `Microsoft.Extensions.Logging` (`ILogger`/`ILogger<T>`) or **Serilog** rather than hand-rolling this. But interviewers want to see you *design* one from scratch, so that's what we do below — and the from-scratch design mirrors exactly how those libraries are built (sinks, formatters, level filtering, async).

### Problem Statement & Clarifying Questions

Design a logging framework that can write messages at different severity levels to multiple destinations with configurable formatting.

**Questions to ask the interviewer:**
- Which **log levels**? (Assume Debug < Info < Warn < Error.)
- Which **destinations/sinks**? (Console, file — extensible to network/DB later.)
- Do we need **async** logging (don't block the caller thread)?
- Should the logger be a **singleton** or allow named loggers (like `ILogger<T>`)?
- Any **format** requirements (timestamp, thread name, JSON)?
- Expected **throughput** and **thread-safety** needs?

### Requirements

**Functional**
- Log a message at a level: `Debug/Info/Warn/Error`.
- **Level filtering** — if threshold is Warn, drop Debug/Info.
- Multiple **appenders/sinks** (console, file) — one message can fan out to many.
- Pluggable **formatter** (plain text, JSON, etc.).

**Non-functional**
- **Thread-safe** writing (no interleaved garbage lines).
- Optional **async** mode for high throughput.
- **Extensible** — add a new appender/formatter without touching core (Open/Closed).
- Clean **shutdown** (flush buffers, close files).

### Core Entities / Classes

| Class / Interface | Responsibility | Relationship |
|-------------------|----------------|--------------|
| `LogLevel` (enum) | Ordered severity levels | used everywhere |
| `LogMessage` | Immutable value object (level, text, timestamp, thread) | created per log call |
| `ILogFormatter` (interface) | Turn a `LogMessage` into a `string` | **Strategy** |
| `ILogAppender` (interface) | Write a formatted line to a destination | **Observer**-like sink |
| `ConsoleAppender`, `FileAppender` | Concrete sinks | *is-a* `ILogAppender` |
| `Logger` | Facade: filter by level, fan out to appenders | *has-a* many appenders (composition) |
| `AsyncAppender` | Decorator/wrapper that buffers + writes on a worker task | wraps an `ILogAppender` |

### Design Patterns Used

- **Strategy** → `ILogFormatter`. Formatting *varies*; swap plain-text ↔ JSON without changing appenders.
- **Singleton** → the root `Logger` is often a single shared instance (global access, one config). In C# use `Lazy<T>` — thread-safe by default.
- **Observer / Appender list** → the `Logger` notifies each registered appender (many sinks react to one event).
- **Level filter** → messages below the threshold are dropped before reaching sinks.
- **Decorator** → `AsyncAppender` wraps any appender to add async behaviour transparently.

### Class Design + Key Code

**Text UML-ish view:**

```
LogLevel (enum: Debug, Info, Warn, Error)

LogMessage { Level, Message, Timestamp, ThreadName }   // immutable

interface ILogFormatter { string Format(LogMessage m); }
    └── SimpleTextFormatter
    └── JsonFormatter

interface ILogAppender { void Append(LogMessage m); void Close(); }
    └── ConsoleAppender   (has-a ILogFormatter)
    └── FileAppender      (has-a ILogFormatter, has-a StreamWriter)
    └── AsyncAppender     (wraps an ILogAppender + channel + worker task)

Logger (SINGLETON)
   - LogLevel Threshold
   - appenders
   + Debug/Info/Warn/Error(string)
   + Log(level, msg)  -> filter -> fan out to appenders
```

```csharp
using System;
using System.Collections.Concurrent;
using System.IO;
using System.Threading;
using System.Threading.Channels;
using System.Threading.Tasks;

namespace LoggerDesign;

// 1) Ordered severity levels. C# enums are integer-backed, so `level >= threshold` works directly.
public enum LogLevel { Debug, Info, Warn, Error }

// 2) Immutable value object — safe to share across threads.
public sealed class LogMessage
{
    public LogLevel Level { get; }
    public string Message { get; }
    public long Timestamp { get; }
    public string ThreadName { get; }

    public LogMessage(LogLevel level, string message)
    {
        Level = level;
        Message = message ?? "";                     // never blow up on null text
        Timestamp = DateTimeOffset.UtcNow.ToUnixTimeMilliseconds();
        ThreadName = Thread.CurrentThread.Name
                     ?? $"T{Environment.CurrentManagedThreadId}";
    }
}

// 3) STRATEGY: formatting varies independently of destination.
public interface ILogFormatter
{
    string Format(LogMessage m);
}

public class SimpleTextFormatter : ILogFormatter
{
    public string Format(LogMessage m) =>
        $"{m.Timestamp} [{m.ThreadName}] {m.Level} - {m.Message}";
}

public class JsonFormatter : ILogFormatter
{
    public string Format(LogMessage m) =>
        $"{{\"ts\":{m.Timestamp},\"thread\":\"{m.ThreadName}\"," +
        $"\"level\":\"{m.Level}\",\"msg\":\"{m.Message}\"}}";
}

// 4) APPENDER (sink). Each concrete appender owns a formatter (composition).
public interface ILogAppender
{
    void Append(LogMessage m);
    void Close();
}

public class ConsoleAppender : ILogAppender
{
    private readonly ILogFormatter _formatter;
    // Lock so two threads never interleave a WriteLine.
    private readonly object _lock = new object();

    public ConsoleAppender(ILogFormatter formatter) => _formatter = formatter;

    public void Append(LogMessage m)
    {
        string line = _formatter.Format(m);
        lock (_lock) { Console.WriteLine(line); }
    }

    public void Close() { /* nothing to close for console */ }
}

public class FileAppender : ILogAppender
{
    private readonly ILogFormatter _formatter;
    private readonly StreamWriter _writer;
    private readonly object _lock = new object();

    public FileAppender(ILogFormatter formatter, string path)
    {
        _formatter = formatter;
        _writer = new StreamWriter(path, append: true) { AutoFlush = false };
    }

    public void Append(LogMessage m)
    {
        string line = _formatter.Format(m);
        lock (_lock)                                 // one writer, guard it
        {
            try
            {
                _writer.WriteLine(line);
                _writer.Flush();                     // flush so nothing is lost on crash
            }
            catch (IOException e)
            {
                // Never let logging blow up the app — degrade gracefully.
                Console.Error.WriteLine("FileAppender failed: " + e.Message);
            }
        }
    }

    public void Close()
    {
        lock (_lock)
        {
            try { _writer.Dispose(); } catch (IOException) { /* ignore */ }
        }
    }
}

// 5) DECORATOR: make ANY appender async without changing it.
//    System.Threading.Channels is the idiomatic bounded queue in .NET.
public class AsyncAppender : ILogAppender
{
    private readonly ILogAppender _inner;
    private readonly Channel<LogMessage> _channel =
        Channel.CreateBounded<LogMessage>(new BoundedChannelOptions(10_000)
        {
            FullMode = BoundedChannelFullMode.DropWrite  // drop if full so caller never stalls
        });
    private readonly Task _worker;

    public AsyncAppender(ILogAppender inner)
    {
        _inner = inner;
        _worker = Task.Run(DrainAsync);
    }

    private async Task DrainAsync()
    {
        await foreach (var m in _channel.Reader.ReadAllAsync())
            _inner.Append(m);
    }

    public void Append(LogMessage m)
    {
        // TryWrite = non-blocking; false when buffer full (DropWrite policy).
        if (!_channel.Writer.TryWrite(m))
            Console.Error.WriteLine("Log buffer full, dropping message");
    }

    public void Close()
    {
        _channel.Writer.Complete();                  // no more writes
        _worker.Wait(2000);                          // let the worker drain
        _inner.Close();
    }
}

// 6) LOGGER: SINGLETON (via Lazy<T>) + level filter + fan-out (observer-ish).
public sealed class Logger
{
    // Lazy<T> gives a thread-safe, lazily-created singleton — the cleanest C# idiom.
    private static readonly Lazy<Logger> _instance = new(() => new Logger());
    public static Logger Instance => _instance.Value;

    private volatile LogLevel _threshold = LogLevel.Info;   // change visible to all threads
    private readonly ConcurrentBag<ILogAppender> _appenders = new();

    private Logger() { }

    public void SetThreshold(LogLevel level) => _threshold = level;
    public void AddAppender(ILogAppender a) => _appenders.Add(a);

    public void Log(LogLevel level, string message)
    {
        if (level < _threshold) return;              // LEVEL FILTER
        var m = new LogMessage(level, message);
        foreach (var a in _appenders) a.Append(m);   // FAN OUT
    }

    public void Debug(string msg) => Log(LogLevel.Debug, msg);
    public void Info(string msg)  => Log(LogLevel.Info,  msg);
    public void Warn(string msg)  => Log(LogLevel.Warn,  msg);
    public void Error(string msg) => Log(LogLevel.Error, msg);

    public void Shutdown()
    {
        foreach (var a in _appenders) a.Close();
    }
}
```

**Usage:**
```csharp
Logger log = Logger.Instance;
log.SetThreshold(LogLevel.Debug);
log.AddAppender(new ConsoleAppender(new SimpleTextFormatter()));
log.AddAppender(new AsyncAppender(new FileAppender(new JsonFormatter(), "app.log")));

log.Info("Server started");
log.Debug("Cache warmed");
log.Error("DB connection lost");
log.Shutdown();
```

### Thread-Safety Considerations

- **Shared appender list** → `ConcurrentBag<ILogAppender>` lets many threads log while occasionally adding an appender, with no exception. (If insertion order matters for fan-out, guard a plain `List<T>` with a `lock` instead.)
- **Singleton creation** → `Lazy<T>` is thread-safe by default (`LazyThreadSafetyMode.ExecutionAndPublication`) — no hand-written double-checked locking needed.
- **Each sink guards its write** → a `lock` on the console/file writer so lines don't interleave.
- **`_threshold` is `volatile`** → a config change is visible to all threads immediately.
- **Async mode** → a bounded `Channel<T>` hands work to one worker `Task`; the underlying writer is touched by exactly one thread, so no interleaving and the caller never blocks.

### Edge Cases
- Logging an exception/stack trace (accept an `Exception` overload).
- File appender: disk full, permission denied, file rotation by size/date.
- Async queue full → drop vs block policy (`BoundedChannelFullMode` — state which you chose).
- Very high log volume → level filtering + async prevents slowdown.
- Ensure `Shutdown()` flushes buffered/async messages (no lost logs).
- Formatter must handle `null` message text safely (handled in `LogMessage`).

### How to Extend / Follow-ups
- Add **named/hierarchical loggers** (`App.Service`) with per-namespace levels, like `ILogger<T>`.
- Add appenders: **network/syslog**, **DB**, **rolling file**.
- Add **scopes / correlation context** (request id per logical operation via `AsyncLocal<T>`).
- **Batching** in the async appender for throughput; back-pressure policy.
- Structured logging / correlation ids for distributed tracing.

## Problem 2 — Design a File System (Composite)

A simplified **in-memory** file system. This is the canonical **Composite pattern** problem: files and directories are treated *uniformly* as nodes of a tree.

### Problem Statement & Clarifying Questions

Design an in-memory file system supporting create, delete, `Ls`, `Find`, path resolution, and size calculation.

**Questions to ask:**
- In-memory only, or persistence? (Assume **in-memory**.)
- Do files store **content**, or just metadata + size? (Assume small content in memory.)
- Are **paths absolute** (`/a/b/c`)? Support `.`/`..`? (Keep it absolute, `/`-separated.)
- **Permissions / symlinks**? (Out of scope for beginner tier — mention as extension.)
- **Thread-safe**? (Yes — multiple users may touch the tree.)
- Should `Find` match by name, glob, or predicate? (Start with exact name / substring.)

### Requirements

**Functional**
- Create file/directory at a path (auto-create intermediate dirs optional).
- Delete a node (recursive for directories).
- `Ls(path)` — list immediate children.
- `Find(root, name)` — search subtree for matching names.
- **Path resolution** — navigate `/a/b/c` to a node.
- **Size** — file's own size; directory = sum of all descendants (recursive).

**Non-functional**
- **Extensible** node types (file, dir, later: symlink).
- **Thread-safe** mutations.
- Uniform treatment of files & directories (**Composite**).

### Core Entities / Classes

> **Naming note:** in C#, `File` and `Directory` already exist in `System.IO`. To avoid confusion we name the tree nodes `FileNode` and `DirectoryNode`.

| Class | Responsibility | Relationship |
|-------|----------------|--------------|
| `FileSystemNode` (abstract) | Common node: `Name`, `GetSize()`, `Print()` | base of the tree |
| `FileNode` | Leaf node; holds content; size = content length | *is-a* node (leaf) |
| `DirectoryNode` | Composite node; **owns** children dictionary | *is-a* node; **composition** of children |
| `FileSystem` | Facade: root + operations (create/delete/ls/find/resolve) | *has-a* root `DirectoryNode` |

> **Composite relationship:** `DirectoryNode` *contains* `FileSystemNode`s, and `DirectoryNode` itself *is-a* `FileSystemNode`. That recursion is the whole pattern — a folder can hold files *and* folders, forever.

### Design Patterns Used

- **Composite** → `FileNode` (leaf) and `DirectoryNode` (composite) share the `FileSystemNode` base type, so client code treats them uniformly (`node.GetSize()` works on both).
- **(Optional) Iterator / Visitor** → for traversals like `Find` or computing total size you could formalise a Visitor; for beginner tier a simple recursive method is fine.

### Class Design + Key Code

**Text UML-ish view:**

```
abstract FileSystemNode { Name; GetSize(); Print(indent); }
        ├── FileNode       (content; size = content.Length)   [LEAF]
        └── DirectoryNode  (Dictionary<string, FileSystemNode> children)  [COMPOSITE]
                            + Add(node) / Remove(name) / GetChild(name)
                            + GetSize() = sum of children.GetSize()

FileSystem { DirectoryNode root ("/") ; Mkdir/CreateFile/Delete/Ls/Find/Resolve }
```

```csharp
using System;
using System.Collections.Generic;

namespace FileSystemDesign;

// COMPOSITE base — the common type for files AND directories.
public abstract class FileSystemNode
{
    public string Name { get; }
    protected FileSystemNode(string name) => Name = name;

    public abstract long GetSize();               // leaf & composite both answer
    public abstract void Print(string indent);    // pretty tree print
}

// LEAF
public class FileNode : FileSystemNode
{
    private string _content;

    public FileNode(string name, string content) : base(name)
        => _content = content ?? "";

    public void Write(string content) => _content = content ?? "";
    public string Read() => _content;

    public override long GetSize() => _content.Length;

    public override void Print(string indent)
        => Console.WriteLine($"{indent}- {Name} ({GetSize()}b)");
}

// COMPOSITE
public class DirectoryNode : FileSystemNode
{
    // Dictionary preserves insertion order in modern .NET for a stable Ls.
    private readonly Dictionary<string, FileSystemNode> _children = new();
    private readonly object _lock = new object();

    public DirectoryNode(string name) : base(name) { }

    public void Add(FileSystemNode node)
    {
        lock (_lock)
        {
            if (_children.ContainsKey(node.Name))
                throw new ArgumentException("Already exists: " + node.Name);
            _children[node.Name] = node;
        }
    }

    public void Remove(string childName)
    {
        lock (_lock)
        {
            if (!_children.Remove(childName))
                throw new KeyNotFoundException("Not found: " + childName);
        }
    }

    public FileSystemNode? GetChild(string childName)
    {
        lock (_lock)
        {
            return _children.TryGetValue(childName, out var n) ? n : null;
        }
    }

    public List<FileSystemNode> List()
    {
        lock (_lock)
        {
            return new List<FileSystemNode>(_children.Values);  // copy = safe to iterate
        }
    }

    // Directory size = recursive sum of all descendants. Composite in action.
    public override long GetSize()
    {
        lock (_lock)
        {
            long total = 0;
            foreach (var child in _children.Values) total += child.GetSize();
            return total;
        }
    }

    public override void Print(string indent)
    {
        Console.WriteLine($"{indent}+ {Name}/");
        foreach (var child in List()) child.Print(indent + "  ");
    }
}

// FACADE with path operations.
public class FileSystem
{
    private readonly DirectoryNode _root = new DirectoryNode("");   // "" represents "/"

    // Split "/a/b/c" -> ["a","b","c"]
    private string[] Parts(string path)
    {
        if (path == null || !path.StartsWith("/"))
            throw new ArgumentException("Path must be absolute: " + path);
        string trimmed = path == "/" ? "" : path.Substring(1);
        return trimmed.Length == 0 ? Array.Empty<string>() : trimmed.Split('/');
    }

    // PATH RESOLUTION: walk from root to the node at 'path'.
    public FileSystemNode Resolve(string path)
    {
        FileSystemNode current = _root;
        foreach (var p in Parts(path))
        {
            if (current is not DirectoryNode dir)
                throw new ArgumentException("Not a directory in path: " + path);
            current = dir.GetChild(p)
                      ?? throw new KeyNotFoundException("No such path: " + path);
        }
        return current;
    }

    private DirectoryNode ResolveParentDir(string path)
    {
        var p = Parts(path);
        FileSystemNode current = _root;
        for (int i = 0; i < p.Length - 1; i++)          // stop before last segment
        {
            if (current is not DirectoryNode dir)
                throw new ArgumentException("Bad parent path: " + path);
            current = dir.GetChild(p[i])
                      ?? throw new KeyNotFoundException("Bad parent path: " + path);
        }
        return (DirectoryNode)current;
    }

    public void Mkdir(string path)
    {
        var p = Parts(path);
        ResolveParentDir(path).Add(new DirectoryNode(p[^1]));
    }

    public void CreateFile(string path, string content)
    {
        var p = Parts(path);
        ResolveParentDir(path).Add(new FileNode(p[^1], content));
    }

    public void Delete(string path)
    {
        var p = Parts(path);
        ResolveParentDir(path).Remove(p[^1]);   // removing a dir drops its subtree
    }

    // Ls: immediate children names.
    public List<string> Ls(string path)
    {
        var node = Resolve(path);
        if (node is FileNode) return new List<string> { node.Name };
        var names = new List<string>();
        foreach (var c in ((DirectoryNode)node).List()) names.Add(c.Name);
        return names;
    }

    // Find: recursive search of the subtree for exact name matches; returns node refs.
    public List<FileSystemNode> Find(string startPath, string targetName)
    {
        var results = new List<FileSystemNode>();
        Dfs(Resolve(startPath), targetName, results);
        return results;
    }

    private void Dfs(FileSystemNode node, string target, List<FileSystemNode> outList)
    {
        if (node.Name == target) outList.Add(node);
        if (node is DirectoryNode dir)
            foreach (var c in dir.List()) Dfs(c, target, outList);
    }

    public long Size(string path) => Resolve(path).GetSize();
    public void PrintTree() => _root.Print("");
}
```

**Usage:**
```csharp
var fs = new FileSystem();
fs.Mkdir("/home");
fs.Mkdir("/home/parteek");
fs.CreateFile("/home/parteek/notes.txt", "hello LLD");
fs.CreateFile("/home/parteek/todo.txt", "learn composite");

Console.WriteLine(string.Join(", ", fs.Ls("/home/parteek")));  // notes.txt, todo.txt
Console.WriteLine(fs.Size("/home"));                            // 9 + 15 = 24
fs.Find("/", "notes.txt");                                      // -> the FileNode
fs.Delete("/home/parteek/todo.txt");
fs.PrintTree();
```

### Thread-Safety Considerations
- Each `DirectoryNode` guards its own mutations (`Add/Remove/List/GetSize`) with a `lock` — the children dictionary is the shared mutable state.
- `List()` returns a **copy**, so callers can iterate without holding the lock (avoids "collection modified" exceptions).
- For higher concurrency, swap `Dictionary` + `lock` for a `ConcurrentDictionary`, or use a `ReaderWriterLockSlim` (many readers for `Ls`/`Find`, exclusive writers for `Create`/`Delete`).
- Watch for **deadlocks** if you ever lock multiple directories at once (e.g., `Move`) — lock in a consistent order (e.g., by path).

### Edge Cases
- Creating a node whose parent doesn't exist → error or auto-create intermediate dirs (state your choice).
- Duplicate name in the same directory.
- Deleting root `/` or a non-existent path.
- Path with trailing slash, empty path, or relative path (reject or normalise).
- Treating a `FileNode` as a `DirectoryNode` (`Ls` on a file).
- Large/deep trees → recursion depth (mention iterative traversal for very deep trees).

### How to Extend / Follow-ups
- Support `.` and `..`, relative paths, current-working-directory.
- **Symlinks** (a node pointing to another path — beware cycles in `GetSize`/`Find`).
- Permissions/ownership, timestamps (created/modified).
- `Move`/`Copy`, glob/regex in `Find`, caching directory size.
- Persistence (serialize the tree), quotas.

## Problem 3 — Design a Vending Machine (State)

The textbook **State pattern** problem. The machine behaves differently depending on its current mode: *Idle*, *HasMoney*, *Dispensing*, *OutOfStock*. Same button press → different result depending on state.

### Problem Statement & Clarifying Questions

Design a vending machine that holds items with inventory, accepts coins/notes, lets a user select a product, dispenses it, and returns change.

**Questions to ask:**
- Payment: **coins/notes** only, or card too? (Assume coins/notes for now.)
- Can the user **cancel** and get a refund mid-transaction? (Yes.)
- **Exact change** required, or does the machine make change? (Machine makes change if it can.)
- One item per transaction or multiple? (Assume one.)
- **Thread-safety** — single physical machine, one user at a time, but admin refills concurrently? (Guard inventory.)
- What happens when **out of stock** or **insufficient money**?

### Requirements

**Functional**
- Insert money (accumulate balance).
- Select a product (by code, e.g., `A1`).
- Dispense when balance ≥ price and item in stock.
- Return **change** (balance − price).
- **Cancel** → refund inserted money.
- Admin: refill inventory, restock coins.

**Non-functional**
- Clean **State pattern** — each state decides what each action does.
- **Thread-safe** inventory/coin updates.
- Extensible states & payment methods.

### Core Entities / Classes

| Class / Interface | Responsibility | Relationship |
|-------------------|----------------|--------------|
| `Item` | Product: name, price, code | value object |
| `Inventory` | Stock counts per item; check/deduct/refill | *has-a* items |
| `Coin` (enum) | Denominations (5, 10, 20, 50, 100) | value |
| `IVendingMachineState` (interface) | Defines actions: `InsertMoney`, `SelectItem`, `Dispense`, `Cancel` | **State** |
| `IdleState`, `HasMoneyState`, `DispensingState`, `OutOfStockState` | Concrete behaviours | *is-a* state |
| `VendingMachine` (context) | Holds current state, balance, inventory; delegates actions to state | *has-a* one state |

> **Relationship:** `VendingMachine` (context) *has-a* current `IVendingMachineState`; states call back into the machine to change balance, deduct stock, and **transition** to the next state.

### Design Patterns Used

- **State** → the heart of the design. Each action (`InsertMoney`, `SelectItem`, `Dispense`, `Cancel`) is implemented per state; the machine delegates to the current state and states drive transitions. This replaces a giant `if/else`/`switch` on a status flag.
- **(Optional) Strategy** → pluggable **payment** (coins vs card) or **pricing**.
- **(Optional) Singleton** → one physical machine instance.
- **(Optional) Factory** → create the right state object.

### Class Design + Key Code

**Text UML-ish view:**

```
Item { Code, Name, Price }
enum Coin { Five=5, Ten=10, Twenty=20, Fifty=50, Hundred=100 }
Inventory { Dictionary<code, Item>, Dictionary<code, count>  + HasStock/Deduct/Refill }

interface IVendingMachineState {
    void InsertMoney(int amount);
    void SelectItem(string code);
    void Dispense();
    void Cancel();
}
   ├── IdleState        (waiting; only InsertMoney does something)
   ├── HasMoneyState    (money in; SelectItem checks price/stock)
   ├── DispensingState  (releasing item + change, then -> Idle)
   └── OutOfStockState  (item unavailable; refund, back to Idle)

VendingMachine (CONTEXT)
   - state, balance, selectedCode, Inventory
   + SetState(), AddBalance(), Refund(), transitions
   + public: InsertMoney/SelectItem/Dispense/Cancel  -> delegate to state
```

```csharp
using System;
using System.Collections.Generic;

namespace VendingMachineDesign;

public class Item
{
    public string Code { get; }
    public string Name { get; }
    public int Price { get; }

    public Item(string code, string name, int price)
    {
        Code = code; Name = name; Price = price;
    }
}

// C# enums can't carry a constructor like Java, but we can make the
// underlying integer BE the denomination: (int)Coin.Ten == 10.
public enum Coin { Five = 5, Ten = 10, Twenty = 20, Fifty = 50, Hundred = 100 }

public class Inventory
{
    private readonly Dictionary<string, Item> _items = new();
    private readonly Dictionary<string, int> _counts = new();
    private readonly object _lock = new object();

    public void AddItem(Item item, int count)
    {
        lock (_lock)
        {
            _items[item.Code] = item;
            _counts[item.Code] = _counts.GetValueOrDefault(item.Code) + count;
        }
    }

    public Item? GetItem(string code)
    {
        lock (_lock) { return _items.GetValueOrDefault(code); }
    }

    public bool HasStock(string code)
    {
        lock (_lock) { return _counts.GetValueOrDefault(code) > 0; }
    }

    public void Deduct(string code)
    {
        lock (_lock)
        {
            int c = _counts.GetValueOrDefault(code);
            if (c <= 0) throw new InvalidOperationException("Out of stock: " + code);
            _counts[code] = c - 1;
        }
    }
}

// STATE interface: every action is defined per-state.
public interface IVendingMachineState
{
    void InsertMoney(int amount);
    void SelectItem(string code);
    void Dispense();
    void Cancel();
}

// CONTEXT
public class VendingMachine
{
    private IVendingMachineState _state;
    private readonly Inventory _inventory;
    private readonly object _gate = new object();   // lock is reentrant on the same thread
    private int _balance = 0;
    private string? _selectedCode = null;

    public VendingMachine(Inventory inventory)
    {
        _inventory = inventory;
        _state = new IdleState(this);   // start Idle
    }

    // --- state management + helpers the states use ---
    internal void SetState(IVendingMachineState s) => _state = s;
    internal Inventory Inventory => _inventory;
    internal int Balance => _balance;
    internal void AddBalance(int amt) => _balance += amt;
    internal void ResetBalance() => _balance = 0;
    internal void SetSelectedCode(string? c) => _selectedCode = c;
    internal string? SelectedCode => _selectedCode;

    internal void Refund()
    {
        if (_balance > 0) Console.WriteLine("Refunding " + _balance);
        ResetBalance();
        _selectedCode = null;
    }

    // --- public API delegates to the CURRENT state ---
    public void InsertMoney(int amount) { lock (_gate) { _state.InsertMoney(amount); } }
    public void SelectItem(string code) { lock (_gate) { _state.SelectItem(code); } }
    public void Dispense()              { lock (_gate) { _state.Dispense(); } }
    public void Cancel()                { lock (_gate) { _state.Cancel(); } }
}

// IDLE: waiting for money.
public class IdleState : IVendingMachineState
{
    private readonly VendingMachine _m;
    public IdleState(VendingMachine m) => _m = m;

    public void InsertMoney(int amount)
    {
        _m.AddBalance(amount);
        Console.WriteLine("Balance: " + _m.Balance);
        _m.SetState(new HasMoneyState(_m));           // transition
    }
    public void SelectItem(string code) => Console.WriteLine("Insert money first.");
    public void Dispense() => Console.WriteLine("Insert money & select item.");
    public void Cancel() => Console.WriteLine("Nothing to cancel.");
}

// HAS MONEY: user can add more, select, or cancel.
public class HasMoneyState : IVendingMachineState
{
    private readonly VendingMachine _m;
    public HasMoneyState(VendingMachine m) => _m = m;

    public void InsertMoney(int amount)
    {
        _m.AddBalance(amount);
        Console.WriteLine("Balance: " + _m.Balance);
    }
    public void SelectItem(string code)
    {
        Item? item = _m.Inventory.GetItem(code);
        if (item == null) { Console.WriteLine("Invalid item: " + code); return; }
        if (!_m.Inventory.HasStock(code))
        {
            Console.WriteLine(item.Name + " is out of stock.");
            _m.SetState(new OutOfStockState(_m));
            return;
        }
        if (_m.Balance < item.Price)
        {
            Console.WriteLine($"Insufficient. Need {item.Price - _m.Balance} more.");
            return;                                  // stay in HasMoney
        }
        _m.SetSelectedCode(code);
        _m.SetState(new DispensingState(_m));        // transition
        _m.Dispense();                               // trigger dispensing
    }
    public void Dispense() => Console.WriteLine("Select an item first.");
    public void Cancel() { _m.Refund(); _m.SetState(new IdleState(_m)); }
}

// DISPENSING: release item + change, then back to Idle.
public class DispensingState : IVendingMachineState
{
    private readonly VendingMachine _m;
    public DispensingState(VendingMachine m) => _m = m;

    public void InsertMoney(int amount) => Console.WriteLine("Dispensing, please wait.");
    public void SelectItem(string code) => Console.WriteLine("Dispensing, please wait.");
    public void Cancel() => Console.WriteLine("Cannot cancel during dispensing.");

    public void Dispense()
    {
        string code = _m.SelectedCode!;
        Item item = _m.Inventory.GetItem(code)!;
        _m.Inventory.Deduct(code);                   // reduce stock
        int change = _m.Balance - item.Price;
        Console.WriteLine("Dispensed: " + item.Name);
        if (change > 0) Console.WriteLine("Change: " + change);
        _m.ResetBalance();
        _m.SetSelectedCode(null);
        _m.SetState(new IdleState(_m));              // ready for next customer
    }
}

// OUT OF STOCK: refund and reset.
public class OutOfStockState : IVendingMachineState
{
    private readonly VendingMachine _m;
    public OutOfStockState(VendingMachine m) => _m = m;

    public void InsertMoney(int amount) => Console.WriteLine("Item unavailable.");
    public void SelectItem(string code) => Console.WriteLine("Item unavailable.");
    public void Dispense() => Console.WriteLine("Item unavailable.");
    public void Cancel() { _m.Refund(); _m.SetState(new IdleState(_m)); }
}
```

**Usage (walk-through):**
```csharp
var inv = new Inventory();
inv.AddItem(new Item("A1", "Coke", 25), 2);
inv.AddItem(new Item("A2", "Water", 15), 0);   // out of stock

var vm = new VendingMachine(inv);
vm.InsertMoney(20);      // Idle -> HasMoney, balance 20
vm.InsertMoney(10);      // balance 30
vm.SelectItem("A1");     // price 25, stock ok -> Dispensing -> "Coke", change 5 -> Idle
vm.SelectItem("A2");     // needs money again (Idle): "Insert money first."
vm.InsertMoney(50);
vm.SelectItem("A2");     // out of stock -> OutOfStock
vm.Cancel();             // refund 50 -> Idle
```

**State transition table:**

| Current state | InsertMoney | SelectItem | Dispense | Cancel |
|---------------|-------------|------------|----------|--------|
| **Idle** | +balance → HasMoney | "insert money" | no-op | no-op |
| **HasMoney** | +balance | price/stock ok → Dispensing; else stay/OutOfStock | "select first" | refund → Idle |
| **Dispensing** | wait | wait | release + change → Idle | can't cancel |
| **OutOfStock** | unavailable | unavailable | unavailable | refund → Idle |

### Thread-Safety Considerations
- A physical machine serves **one customer at a time**, but an **admin refill** can run concurrently → guard `Inventory` (all methods under a `lock`, or `ConcurrentDictionary`).
- The context's public actions take a `lock` so a `SelectItem` + `Dispense` sequence is atomic and state transitions aren't seen half-done. (Note `lock`/`Monitor` is **reentrant** on the same thread, so `SelectItem` calling `Dispense` internally is safe.)
- **`Deduct` must be atomic with the stock check** — otherwise two flows could both pass `HasStock` and over-dispense (check-then-act race). Keep check + deduct under one lock.
- `_balance`/`_selectedCode` are per-machine mutable state — protected by the machine's own lock.

### Edge Cases
- Insufficient balance → prompt for more, don't dispense.
- Invalid/unknown item code.
- Item goes out of stock exactly when selected.
- Exact-change-only scenario (machine can't make change) → reject or ask exact amount.
- Cancel during dispensing (disallow) vs during HasMoney (refund).
- Zero/negative money inserted → reject.
- Coin/note the machine doesn't accept.

### How to Extend / Follow-ups
- **Card/UPI payment** via an `IPaymentStrategy` (Strategy pattern).
- Change-making with limited coin inventory (greedy/DP) and coin restocking.
- Multiple items per transaction / shopping-cart mode.
- Maintenance / admin state; display panel via **Observer**.
- Persist sales, telemetry, price changes.
- Concurrency at scale (many networked machines).

> For a tiny machine you could use a `switch` expression on an enum state, but the **State pattern scales better** as behaviours and transitions grow — prefer it in interviews.

## Quick Revision Tips

- Always run the **6-step method**: clarify → entities → relationships → SOLID/patterns → edge cases & concurrency → code walk-through.
- Say the **pattern name out loud** and *why* — "formatting varies, so I'll use Strategy."
- **Favour composition over inheritance.** Program to interfaces.
- Replace big `if/else` on a status with the **State** pattern; replace big `if/else` on a type with **polymorphism/Strategy**.
- For SDE-2, always mention **thread-safety** and one concrete mechanism (`lock`, concurrent collection, immutability, single-writer channel/queue).
- Draw the **class boxes** and a **state/transition table** — visuals win interviews.
- Keep code **compilable-ish and focused**; implement the *important* methods, stub the rest and say so.

> **Final mantra:** *Clarify, structure, name your patterns, protect shared state, and walk the code.* Do this on Logger, File System, and Vending Machine until it's muscle memory — then any LLD problem will feel easy. All the best!

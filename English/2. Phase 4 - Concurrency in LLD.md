# Phase 4 — Concurrency in LLD (C#/.NET) for SDE-2 Interviews

> A beginner-friendly, in-depth study note. All examples are in **C#/.NET** (your primary stack). Every concept is explained in plain English with real-world analogies.

## Intro

**English:** Concurrency is about doing multiple things at the same time *correctly*. In Low-Level Design (LLD) interviews, you are not just asked to draw classes — you are expected to reason about what happens when **many threads** hit your objects at once. Two threads reading and writing shared state without coordination is where bugs like race conditions, lost updates, and deadlocks live. This note recaps the primitives you *must* know, then applies them to three classic designs: a thread-safe cache, a rate limiter, and a parking lot. **SDE-2 interviews often include a thread-safety discussion — be prepared** to say *what* your shared state is, *how* it is protected, and *why* your choice is correct and performant.

# PART A — Must-Know Primitives

> Keep these practical. (Deep theory — memory model, happens-before — may live in a separate fundamentals file.) Here we focus on **when to use each in a design** and the **thread-safety angle**.

<a id="a1-lock--monitor"></a>
## A1. `lock` / Monitor

**English:** The `lock` statement gives you **mutual exclusion** — only one thread can hold a given monitor at a time — plus a **memory visibility** guarantee (changes made inside the block are visible to the next thread that enters). `lock (obj) { ... }` compiles down to `Monitor.Enter(obj)` / `Monitor.Exit(obj)` wrapped in a `try/finally`, so the lock is always released even on exception. Use it when you have a **critical section**: a compound read-modify-write on shared state that must be atomic. It is the simplest correct tool; reach for it first, optimize later.

```csharp
class Counter
{
    private int _count = 0;

    // Private lock object — never expose the object you lock on
    private readonly object _lock = new object();

    public void Increment()
    {
        lock (_lock)
        {
            _count++; // read-modify-write: NOT atomic without the lock
        }
    }

    // Keep the critical section small: do non-critical work outside the lock
    public void IncrementBlock()
    {
        // ... do non-critical work here (no lock held) ...
        lock (_lock)
        {
            _count++;
        }
    }

    public int Get()
    {
        lock (_lock) { return _count; }
    }
}
```

For a simple atomic counter you don't even need a lock — `Interlocked.Increment(ref _count)` is a lock-free, atomic read-modify-write.

**Interview points / pitfalls:**
- Locking on `this`, a `Type`, or any publicly reachable object leaks your lock — outside code could lock on the same monitor and cause surprises. **Prefer a `private readonly object _lock`.**
- Never `lock` on a value type (it gets boxed — each `lock` sees a different box) or a `string` (interned strings are shared process-wide).
- `lock`/Monitor is **reentrant**: the same thread can re-acquire a monitor it already holds.
- Holding a lock during slow I/O kills throughput — keep critical sections **short**. Never `await` inside a `lock` (you cannot, and it would hold the monitor across a thread switch).
- Two locks acquired in different orders by different threads → **deadlock**. Always acquire in a consistent global order.
- Reads also need synchronization for **visibility**, not just writes.

<a id="a2-volatile--volatile"></a>
## A2. `volatile` & `Volatile`

**English:** The `volatile` keyword guarantees **visibility** and prevents certain instruction reordering around the field, but it does **NOT** give atomicity for compound operations. Every read of a volatile field sees the latest write from any thread (no caching in a register/CPU cache). Use it for a **flag** that one thread sets and others read (e.g. a `_stop`/`_running` boolean). Do **NOT** use it for counters — `_count++` on a volatile field is still three operations (read, add, write) and can be interleaved. `Volatile.Read(ref x)` / `Volatile.Write(ref x)` are the method-based equivalents for cases where you want per-access volatile semantics on a normal field.

```csharp
class Worker
{
    private volatile bool _running = true; // visibility across threads

    public void Stop() => _running = false; // one writer

    public void Run()
    {
        while (_running)   // many-reader flag: volatile is ENOUGH here
        {
            DoWork();
        }
    }

    private void DoWork() { /* ... */ }
}

// volatile is NOT enough here:
class BadCounter
{
    private volatile int _count = 0;
    public void Inc() => _count++; // BUG: read-modify-write, not atomic
    // Fix: use Interlocked.Increment(ref _count) or a lock
}
```

For atomic counters use `Interlocked.Increment(ref _count)` (the correct way to do a thread-safe `++`).

**Interview points / pitfalls:**
- **Enough for:** single-writer / multi-reader flags, publishing an immutable object reference.
- **NOT enough for:** counters, check-then-act, any compound action → use `Interlocked` or a lock.
- `volatile` on a reference makes the *reference* visible, not the object's internal fields deeply.
- `volatile` cannot be applied to `long`/`double`/`ulong` fields (they are 64-bit; use `Interlocked` or `Volatile.Read/Write` for those).
- It is cheaper than a lock (no blocking) but only solves visibility/ordering, not mutual exclusion.

<a id="a3-explicit-locks"></a>
## A3. Explicit locks: `Monitor.TryEnter` & `ReaderWriterLockSlim`

**English:** The `lock` statement covers the simple case, but sometimes you need more. `Monitor.TryEnter(obj, timeout)` gives you a **non-blocking or timed** acquire so you don't wait forever (great for avoiding deadlock). `ReaderWriterLockSlim` lets **many readers share** access while **writers are exclusive** — ideal for read-heavy shared state. For coordinated wait/signal, `Monitor.Wait` / `Monitor.Pulse` / `Monitor.PulseAll` are the low-level primitives, and `SemaphoreSlim` (including its `WaitAsync`) is the modern async-friendly choice.

```csharp
using System;
using System.Threading;

class Account
{
    private readonly object _lock = new object();
    private double _balance;

    public void Deposit(double amt)
    {
        lock (_lock)
        {
            _balance += amt;   // critical section
        }
    }

    // Monitor.TryEnter: don't block forever — bail out or retry
    public bool TransferIfFree(Account to, double amt)
    {
        bool taken = false;
        try
        {
            Monitor.TryEnter(_lock, TimeSpan.FromMilliseconds(500), ref taken);
            if (!taken) return false; // couldn't get the lock in time

            if (_balance >= amt)
            {
                _balance -= amt;
                to.Deposit(amt);
                return true;
            }
            return false;
        }
        finally
        {
            if (taken) Monitor.Exit(_lock); // ALWAYS release in finally
        }
    }
}
```

**Reader/writer separation** for read-heavy data:

```csharp
using System.Threading;

class SettingsStore
{
    private readonly ReaderWriterLockSlim _rw =
        new ReaderWriterLockSlim(LockRecursionPolicy.NoRecursion);
    private string _value = "";

    public string Read()
    {
        _rw.EnterReadLock();               // many readers concurrently
        try { return _value; }
        finally { _rw.ExitReadLock(); }
    }

    public void Write(string v)
    {
        _rw.EnterWriteLock();              // writer is exclusive
        try { _value = v; }
        finally { _rw.ExitWriteLock(); }
    }
}
```

**When to reach past a plain `lock`:**
| Need | `lock` (Monitor) | Explicit API |
|------|------------------|--------------|
| Simple mutual exclusion | Best (auto-release) | — |
| Timed / non-blocking acquire | No | `Monitor.TryEnter(obj, timeout, ref taken)` |
| Read/write separation | No | `ReaderWriterLockSlim` |
| Async-friendly gate | No (can't `await` in `lock`) | `SemaphoreSlim.WaitAsync()` |
| Condition wait/signal | — | `Monitor.Wait/Pulse/PulseAll` |

**Interview points / pitfalls:**
- **Forgetting to release** (`Monitor.Exit` / `ExitReadLock` / `ExitWriteLock`) outside a `finally` → permanent lock leak. The `lock` keyword avoids this; the raw APIs don't.
- `ReaderWriterLockSlim` has a real cost — for very short critical sections a plain `lock` is often faster. Use RW locks only when reads genuinely dominate and are non-trivial.
- Watch for **writer starvation** with many readers; consider `LockRecursionPolicy` and upgradeable read locks carefully.
- Prefer the `lock` keyword for simple cases (less error-prone); reach for the explicit APIs only when you need their features.

<a id="a4-threadpool--tpl"></a>
## A4. ThreadPool & the Task Parallel Library (TPL)

**English:** Don't create a raw `Thread` per task — threads are expensive and unbounded creation crashes the process. Instead submit work to the shared **`ThreadPool`** via the **Task Parallel Library**: `Task` / `Task.Run` reuse pooled worker threads, hand you a handle to the result (`Task<T>`), and let you cancel or await. **Size** matters by workload: CPU-bound work should be capped near `Environment.ProcessorCount`; I/O-bound work shouldn't tie up threads at all — you `await` it. When throughput could overwhelm you, you need **back-pressure** (throttle or bound) so overload doesn't turn into an out-of-memory crash.

**`Task` / `Task.Run` / `Task.WhenAll`** — the default way to run work on the pool:
```csharp
using System.Linq;
using System.Threading.Tasks;

// Task.Run schedules the delegate on the shared .NET ThreadPool
Task<int> t = Task.Run(() => ExpensiveComputation()); // Task<T> is the result handle

int result = await t;                                  // non-blocking await (no thread held)

// Fan out and join — run many tasks, await them all
Task<int>[] tasks = keys.Select(k => Task.Run(() => Compute(k))).ToArray();
int[] all = await Task.WhenAll(tasks);
```

**`Parallel.ForEach`** — data parallelism over a collection (partitions items across pool threads):
```csharp
Parallel.ForEach(items,
    new ParallelOptions { MaxDegreeOfParallelism = Environment.ProcessorCount },
    item => Process(item));   // MaxDegreeOfParallelism caps the effective pool width
```

**`async/await` and the thread pool:** `await` on genuinely I/O-bound work (`HttpClient`, DB, file) does **not** hold a thread while waiting — the thread is returned to the pool and the continuation is scheduled when the I/O completes. So for I/O concurrency you don't size a pool at all; you just `await` many tasks. Use `Task.Run` only to push **CPU-bound** work off the current (e.g. UI) thread — don't wrap already-async I/O in `Task.Run`.

**Sizing / back-pressure in .NET:** the `ThreadPool` auto-tunes its worker count, so you rarely set it directly. Cap CPU-bound fan-out with `MaxDegreeOfParallelism`; throttle concurrent async work with a `SemaphoreSlim(n)` gate; for producer/consumer pipelines use `System.Threading.Channels` (bounded) which gives back-pressure automatically.

```csharp
// Throttle I/O fan-out so you don't launch thousands of concurrent calls
var gate = new SemaphoreSlim(initialCount: 10); // at most 10 in flight

async Task<Result> CallThrottled(Key k)
{
    await gate.WaitAsync();
    try { return await CallServiceAsync(k); }
    finally { gate.Release(); }
}

var results = await Task.WhenAll(keys.Select(CallThrottled));
```

**Interview points / pitfalls:**
- Don't block on async: avoid `.Result` / `.Wait()` on a `Task` (deadlock risk + wastes a pool thread) — `await` instead.
- `Task.Run` is for CPU-bound offloading, not for making I/O "async" — I/O is already async via `await`.
- Cap CPU-bound parallelism to `~ Environment.ProcessorCount`; throttle I/O fan-out with `SemaphoreSlim` so you don't launch thousands of concurrent calls.
- Exceptions surface when you `await` the task (or via `task.Exception`); an unobserved faulted task can be swallowed.
- For scheduled/recurring work use `System.Threading.Timer` or `PeriodicTimer`; for long-running dedicated work, `Task.Factory.StartNew(..., TaskCreationOptions.LongRunning)` gives a dedicated thread instead of a pool thread.

<a id="a5-thread-safe-singleton"></a>
## A5. Thread-safe Singleton

**English:** A singleton ensures exactly one instance. The challenge is making it **thread-safe** and **lazy** (created only when first needed) without paying a locking cost on every access. In .NET the runtime does the hard part for you, so you rarely need to hand-write locking. The two recommended approaches are `Lazy<T>` and the static-field / static-constructor pattern.

**1) `Lazy<T>` (idiomatic, thread-safe by default)**
```csharp
public sealed class Config
{
    // ExecutionAndPublication is the DEFAULT: the factory runs once, result published safely
    private static readonly Lazy<Config> _instance =
        new Lazy<Config>(() => new Config());

    private Config() { }

    public static Config Instance => _instance.Value; // lazy: built on first access
}
```
- Lazy + thread-safe with **zero manual locking**. Default mode `LazyThreadSafetyMode.ExecutionAndPublication` guarantees the factory runs exactly once even under a race; other threads block until it completes, then all see the same instance.
- This is the cleanest way to get "lazy + fast + safe" — you write almost no code.

**2) Static field / static constructor (`static readonly`)**
```csharp
public sealed class Config
{
    // CLR guarantees static-field init runs once, thread-safely, before first use
    private static readonly Config _instance = new Config();

    private Config() { }

    public static Config Instance => _instance;
}
```
- Thread-safe by the CLR's type-initialization guarantee. No locks in your code.
- Note on laziness: with `beforefieldinit` (the default when there is no explicit static constructor) the runtime *may* initialize eagerly-ish at any point before first field use. Add an explicit `static Config() { }` constructor to force strict "init only on first touch of the type" laziness.

**Why these are preferred in C#:** The runtime already gives you a one-time, thread-safe initialization primitive — either via `Lazy<T>` or static-field/static-ctor semantics — so hand-rolled double-checked locking is unnecessary and error-prone. Prefer `Lazy<T>` when you want explicit control over the factory or thread-safety mode; prefer `static readonly` when the object is cheap and always needed.

**Trade-off summary:**
| Approach | Lazy? | Locking cost | Notes |
|----------|-------|--------------|-------|
| **`Lazy<T>`** | Yes | None (runtime-managed) | **Recommended**; factory runs once |
| **`static readonly`** | Effectively (see note) | None | Best when object is cheap + always needed |
| Manual `lock` in getter | Yes | Every call (or double-check needed) | Works but error-prone — avoid; use `Lazy<T>` |

**Interview points / pitfalls:**
- Lead with `Lazy<T>` (or `static readonly`) — say the runtime guarantees one-time thread-safe init so you don't hand-write locking.
- If asked about double-checked locking: it's the manual pattern (`if (null) { lock { if (null) ... } }`) other ecosystems need; a subtle reordering bug can publish a reference before the constructor finishes. `Lazy<T>` closes this gap for you, so you never hand-write it in C#.
- `Lazy<T>` gotcha: `LazyThreadSafetyMode.None` and `PublicationOnly` do **not** give the run-once guarantee — the default `ExecutionAndPublication` does.
- Beware singletons in tests (global state) — mention dependency injection (register the type with a **singleton lifetime** in the DI container, e.g. `services.AddSingleton<Config>()`) as the modern alternative.

<a id="a6-producerconsumer-pattern"></a>
## A6. Producer–Consumer pattern

**English:** Producers create work items; consumers process them; a **bounded blocking collection** sits between them to decouple their speeds. `BlockingCollection<T>` handles all the synchronization: `Add()` blocks when the collection is full (**back-pressure** — slows fast producers), `Take()` blocks when empty (consumers idle-wait cheaply). Modern .NET prefers `System.Threading.Channels` (`Channel<T>`) for the same pattern with a clean `async` API. This is the go-to pattern for pipelines, task ingestion, and log processing.

**`BlockingCollection<T>`** (wraps `ConcurrentQueue<T>` by default):
```csharp
using System.Collections.Concurrent;

class PC
{
    // bounded => back-pressure; producers block when full
    private readonly BlockingCollection<int> _queue =
        new BlockingCollection<int>(boundedCapacity: 100);

    public void Producer()
    {
        for (int i = 0; ; i++)
            _queue.Add(i);                 // blocks if full
        // call _queue.CompleteAdding() to signal "no more items"
    }

    public void Consumer()
    {
        foreach (int item in _queue.GetConsumingEnumerable()) // blocks if empty
        {
            Process(item);                 // exits cleanly when CompleteAdding() is called
        }
    }

    private void Process(int x) { /* ... */ }
}
```

**`System.Threading.Channels`** — the modern, async-first choice:
```csharp
using System.Threading.Channels;

var channel = Channel.CreateBounded<int>(new BoundedChannelOptions(100)
{
    FullMode = BoundedChannelFullMode.Wait   // back-pressure: writer awaits when full
});

// Producer
async Task ProduceAsync()
{
    for (int i = 0; i < 1000; i++)
        await channel.Writer.WriteAsync(i); // awaits (no thread held) when full
    channel.Writer.Complete();              // signal completion
}

// Consumer
async Task ConsumeAsync()
{
    await foreach (int item in channel.Reader.ReadAllAsync())
        Process(item);
}
```

**Interview points / pitfalls:**
- **Always bound the collection/channel** in production — an unbounded one turns a slow consumer into an out-of-memory crash.
- Use `CompleteAdding()` / `Writer.Complete()` (a graceful "no more items" signal) instead of a poison-pill sentinel to shut consumers down cleanly.
- Don't hand-roll low-level wait/signal if a collection/channel fits — it already gets the tricky parts right. (The low-level primitive is `Monitor.Wait`/`Monitor.Pulse`, but modern C# prefers `SemaphoreSlim`, `BlockingCollection<T>`, or `Channels`.)
- Multiple producers/consumers scale naturally; the collection/channel is the single synchronization point.
- `BlockingCollection<T>` also supports `TryAdd`/`TryTake` with timeouts and `CancellationToken` — use these for responsive shutdown.

<a id="b1-thread-safe-cache"></a>
## B1. Thread-safe Cache

### Requirements
**English:** In-memory key→value store with `Get(k)` and `Put(k,v)`, a maximum size with **LRU eviction**, optional **TTL** (entries expire), safe under heavy concurrent reads/writes, and protection against **cache stampede** (many threads all missing the same key and all recomputing it at once).

### Class design
| Component | Role |
|-----------|------|
| `ConcurrentDictionary<K, CacheEntry<V>>` | The store — lock-striped, high concurrency |
| `CacheEntry<V>` | Holds value + `ExpiryAt` (for TTL) |
| Eviction policy | LRU ordering (access order) |
| `GetOrAdd` (with `Lazy<T>`) | Atomic "get-or-load", solves stampede per key |

### Thread-safety strategy
**English:** Use `ConcurrentDictionary` because it allows concurrent reads and **fine-grained (bucket-level) locking** for writes — far better throughput than wrapping a `Dictionary` in a single `lock`. For simple get-or-compute, `GetOrAdd(k, factory)` returns an existing value or adds a new one; but note the **.NET gotcha**: the `factory` may run **more than once** under a race (only the result of one winner is stored). To get a true "run the loader exactly once per key" (which prevents cache stampede), store a `Lazy<V>` as the value — then `GetOrAdd` may build several `Lazy` wrappers, but only the winner's `.Value` is ever evaluated, so the expensive loader runs once. You still need **explicit locks** when an operation spans multiple keys/structures atomically (e.g. evict-and-insert to keep size ≤ capacity, or coordinating with an external LRU list), because `ConcurrentDictionary` only makes single-key operations atomic.

### C# skeleton
```csharp
using System;
using System.Collections.Concurrent;
using System.Collections.Generic;

class ThreadSafeCache<K, V> where K : notnull
{
    private sealed class Entry
    {
        public readonly V Value;
        public readonly long ExpiryAt;   // epoch millis; long.MaxValue = never
        public Entry(V value, long expiryAt) { Value = value; ExpiryAt = expiryAt; }
        public bool IsExpired() =>
            DateTimeOffset.UtcNow.ToUnixTimeMilliseconds() > ExpiryAt;
    }

    private readonly ConcurrentDictionary<K, Lazy<Entry>> _map = new();
    private readonly int _capacity;
    private readonly long _ttlMillis;

    // Access-ordered LRU tracking — NOT thread-safe, so guard it with a lock
    private readonly LinkedList<K> _lruOrder = new();      // front = most recent
    private readonly Dictionary<K, LinkedListNode<K>> _lruNodes = new();
    private readonly object _evictionLock = new object();

    public ThreadSafeCache(int capacity, long ttlMillis)
    {
        _capacity = capacity;
        _ttlMillis = ttlMillis;
    }

    public bool TryGet(K key, out V value)
    {
        value = default!;
        if (!_map.TryGetValue(key, out var lazy)) return false; // lock-free read
        var e = lazy.Value;
        if (e.IsExpired())
        {
            _map.TryRemove(key, out _);                         // lazy TTL expiry
            return false;
        }
        Touch(key);                                             // mark recently used
        value = e.Value;
        return true;
    }

    // get-or-load: prevents cache stampede via Lazy<T> (loader runs exactly once per key)
    public V GetOrLoad(K key, Func<K, V> loader)
    {
        var lazy = _map.GetOrAdd(key,
            k => new Lazy<Entry>(() => new Entry(loader(k), Expiry())));
        var e = lazy.Value;                                     // only ONE loader runs
        if (e.IsExpired())
        {
            _map.TryRemove(key, out _);
            return GetOrLoad(key, loader);                      // reload on expiry
        }
        Touch(key);
        return e.Value;
    }

    public void Put(K key, V value)
    {
        _map[key] = new Lazy<Entry>(new Entry(value, Expiry()));
        Touch(key);
        EvictIfNeeded();                                        // multi-key op → needs the lock
    }

    private void Touch(K key)
    {
        lock (_evictionLock)
        {
            if (_lruNodes.TryGetValue(key, out var node))
                _lruOrder.Remove(node);
            _lruNodes[key] = _lruOrder.AddFirst(key);           // most recent at front
        }
    }

    private void EvictIfNeeded()
    {
        lock (_evictionLock)
        {
            while (_map.Count > _capacity && _lruOrder.Last != null)
            {
                K eldest = _lruOrder.Last.Value;                // least recently used
                _lruOrder.RemoveLast();
                _lruNodes.Remove(eldest);
                _map.TryRemove(eldest, out _);
            }
        }
    }

    private long Expiry() =>
        _ttlMillis <= 0
            ? long.MaxValue
            : DateTimeOffset.UtcNow.ToUnixTimeMilliseconds() + _ttlMillis;
}
```
> Note: for real applications prefer the built-in `Microsoft.Extensions.Caching.Memory.MemoryCache` / `IMemoryCache` — it gives TTL (absolute/sliding expiration), size limits, and eviction callbacks out of the box, done far more efficiently than a hand-rolled cache. In an interview, showing you know *where the lock is needed* (multi-key eviction) and *where it isn't* (single-key `GetOrAdd`) is the key insight.

**Interview talking points / pitfalls:**
- **Why `ConcurrentDictionary` over a `lock`ed `Dictionary`?** The latter locks the whole map per operation; `ConcurrentDictionary` uses bucket-level locking → much higher read/write concurrency, and reads are lock-free.
- **`GetOrAdd` for stampede:** the **key .NET gotcha** is that the factory can run multiple times under a race. Wrap the value in `Lazy<V>` so the expensive loader runs exactly once per key; others block on that same `Lazy`.
- **TTL strategies:** lazy (check on read, shown above) vs. active (a background `Timer`/`PeriodicTimer` sweeper). Lazy is simple but leaks memory for never-read keys — mention both. `MemoryCache` handles this for you.
- **LRU + concurrency is genuinely hard** — a plain `LinkedList`/`Dictionary` isn't thread-safe, so it must be lock-guarded; that lock can become a bottleneck. Real libs shard it.
- **Stampede alternatives:** request coalescing (`Lazy<T>` + `GetOrAdd`), stale-while-revalidate, jittered TTLs to avoid synchronized expiry.

<a id="b2-rate-limiter"></a>
## B2. Rate Limiter

### Requirements
**English:** Allow at most **N requests per time window** per client (key). Must be thread-safe (many requests hit it concurrently), low-overhead, and ideally smooth (no huge bursts at window edges). Design two classic algorithms: **Token Bucket** and **Sliding Window**.

### Algorithm 1 — Token Bucket
**English:** A bucket holds up to `capacity` tokens and refills at a fixed rate (e.g. 10 tokens/sec). Each request consumes one token; if none are available, it's rejected (or waits). It allows short **bursts** (up to bucket size) while enforcing a long-run average rate. Thread-safety: refill + consume must be one atomic critical section.

```csharp
using System.Diagnostics;

class TokenBucket
{
    private readonly long _capacity;       // max tokens
    private readonly double _refillPerMs;  // tokens added per millisecond
    private double _tokens;                // current tokens (double for fractional refill)
    private long _lastRefillMs;            // last refill timestamp (monotonic)
    private readonly object _lock = new object();

    public TokenBucket(long capacity, double tokensPerSecond)
    {
        _capacity = capacity;
        _refillPerMs = tokensPerSecond / 1000.0;
        _tokens = capacity;
        _lastRefillMs = Stopwatch.GetTimestamp() * 1000 / Stopwatch.Frequency;
    }

    // One lock guards the refill+consume compound operation
    public bool TryAcquire()
    {
        lock (_lock)
        {
            Refill();
            if (_tokens >= 1) { _tokens -= 1; return true; }
            return false; // rate exceeded
        }
    }

    private void Refill()
    {
        long now = Stopwatch.GetTimestamp() * 1000 / Stopwatch.Frequency; // monotonic ms
        double add = (now - _lastRefillMs) * _refillPerMs;
        if (add > 0)
        {
            _tokens = System.Math.Min(_capacity, _tokens + add); // never exceed capacity
            _lastRefillMs = now;
        }
    }
}

// Per-client: ConcurrentDictionary<string, TokenBucket>, one bucket per key
```

### Algorithm 2 — Sliding Window (log / counter)
**English:** Track request timestamps in the last window (e.g. 1 minute). On each request, drop timestamps older than `now - window`, then allow if the remaining count `< limit`. More accurate than a fixed window (no double-burst at the boundary) but stores per-request timestamps (memory). A **sliding-window-counter** variant approximates this cheaply using two adjacent fixed buckets.

```csharp
using System.Collections.Generic;
using System.Diagnostics;

class SlidingWindowLimiter
{
    private readonly int _limit;
    private readonly long _windowMs;
    private readonly Queue<long> _timestamps = new();
    private readonly object _lock = new object();

    public SlidingWindowLimiter(int limit, long windowMs)
    {
        _limit = limit;
        _windowMs = windowMs;
    }

    public bool Allow()
    {
        long now = Stopwatch.GetTimestamp() * 1000 / Stopwatch.Frequency; // monotonic ms
        lock (_lock)
        {
            // evict timestamps outside the window
            while (_timestamps.Count > 0 && _timestamps.Peek() <= now - _windowMs)
                _timestamps.Dequeue();

            if (_timestamps.Count < _limit)
            {
                _timestamps.Enqueue(now);
                return true;
            }
            return false;
        }
    }
}
```

### Trade-offs
| Algorithm | Accuracy | Memory | Bursts | Notes |
|-----------|----------|--------|--------|-------|
| Fixed window counter | Low (boundary spikes) | Tiny | Allows 2×limit at edges | Simplest |
| **Token bucket** | Good | Tiny (few numbers) | Allows controlled bursts | Great default; smooth avg |
| **Sliding window log** | Highest | High (per-request) | Strict | Accurate but memory-heavy |
| Sliding window counter | Good | Tiny | Smooths edges | Best memory/accuracy balance |

**Built-in option:** .NET 7+ ships `System.Threading.RateLimiting` with `TokenBucketRateLimiter`, `SlidingWindowRateLimiter`, `FixedWindowRateLimiter`, and `ConcurrencyLimiter` — you'd typically use these (they support async `AcquireAsync`, queueing, and permit counts) rather than hand-roll. For distributed limiting, move state to Redis (e.g. `INCR`+`EXPIRE` or a Lua token-bucket script).

**Interview talking points / pitfalls:**
- **Per-client isolation:** keep a `ConcurrentDictionary<string, Limiter>`; watch for unbounded growth (evict idle clients — tie into the cache design above).
- **Single-node vs distributed:** in-memory limiters don't hold across N app servers. Say "for distributed, move state to Redis with an atomic Lua script or use a token bucket in Redis."
- **Token bucket vs leaky bucket:** leaky bucket smooths output to a constant rate (queue), token bucket permits bursts. Know the difference.
- **Clock issues:** use monotonic time (`Stopwatch.GetTimestamp()`) rather than wall-clock (`DateTime.UtcNow`) — wall-clock jumps (NTP, DST) can misbehave.
- Keep the critical section tiny (just refill+consume / evict+check).

## B3. Parking Lot with concurrent access

### Requirements
**English:** A multi-level parking lot. Vehicles (Motorcycle, Car, Truck) enter, get assigned the **nearest available compatible spot**, receive a **ticket**, and later exit (freeing the spot, computing a fee). Multiple entry/exit gates operate **concurrently** — no two vehicles may be assigned the same spot; a full lot must be reported cleanly; free-spot counts must stay accurate under races.

### Entities
| Entity | Responsibility |
|--------|----------------|
| `ParkingLot` (singleton) | Holds levels; routes entry/exit |
| `Level` | Holds spots; allocates/frees within itself (lock scope) |
| `ParkingSpot` | One spot; `SpotType`, occupied flag, `AssignedTo` |
| `Ticket` | SpotId, vehicle, entry time, (exit time, fee) |
| `Vehicle` / subtypes | `Motorcycle`, `Car`, `Truck` (+ size compatibility) |
| `SpotType` enum | `Small`, `Medium`, `Large` |

### Thread-safety strategy
**English:** The contended shared state is "which spots are free." Two safe designs:
1. **Lock per Level (coarse-ish, simple):** each `Level` has its own `lock` object; find-and-occupy runs inside it. Different levels proceed in parallel; only same-level operations serialize. Simple and correct.
2. **Lock-free per spot (`Interlocked.CompareExchange`):** each spot's occupied flag is an `int` (0/1); claiming uses `Interlocked.CompareExchange(ref _occupied, 1, 0) == 0` — the winner of the CAS gets it, losers scan the next spot. Combine with an `Interlocked`-updated free-count for O(1) "is the lot full?".

Prefer **per-level locking** for interview clarity; mention the CAS approach as the higher-concurrency optimization. Keep a per-level counter (updated via `Interlocked`) so "nearest available" scans and "full lot" checks don't need a full lock just to count.

### C# skeleton
```csharp
using System;
using System.Collections.Concurrent;
using System.Collections.Generic;
using System.Threading;

enum VehicleType { Motorcycle, Car, Truck }
enum SpotType { Small, Medium, Large }

class Vehicle
{
    public string Plate { get; }
    public VehicleType Type { get; }
    public Vehicle(string plate, VehicleType type) { Plate = plate; Type = type; }
}

class ParkingSpot
{
    public string Id { get; }
    public SpotType Type { get; }

    // Lock-free claim: CAS from 0 -> 1 wins the spot (C# has no AtomicBoolean; use int)
    private int _occupied = 0;
    private volatile Vehicle? _vehicle;

    public ParkingSpot(string id, SpotType type) { Id = id; Type = type; }

    public bool TryOccupy(Vehicle v)
    {
        if (Interlocked.CompareExchange(ref _occupied, 1, 0) == 0) // atomic winner-takes-spot
        {
            _vehicle = v;
            return true;
        }
        return false; // someone else grabbed it
    }

    public void Free()
    {
        _vehicle = null;
        Interlocked.Exchange(ref _occupied, 0);
    }

    public bool IsFree() => Volatile.Read(ref _occupied) == 0;

    public bool Fits(VehicleType vt) => vt switch
    {
        VehicleType.Motorcycle => true,                 // fits anywhere
        VehicleType.Car        => Type != SpotType.Small,
        VehicleType.Truck      => Type == SpotType.Large,
        _                      => false
    };
}

class Level
{
    public int Floor { get; }
    private readonly List<ParkingSpot> _spots;          // ordered => "nearest" = first free
    private int _available;                              // O(1) full-check, no full lock

    public Level(int floor, List<ParkingSpot> spots)
    {
        Floor = floor;
        _spots = spots;
        _available = spots.Count;
    }

    // Lock-free allocation using each spot's CAS + an Interlocked counter
    public ParkingSpot? Allocate(Vehicle v)
    {
        if (Volatile.Read(ref _available) == 0) return null;   // fast fail if full
        foreach (var s in _spots)                              // scan in order = nearest first
        {
            if (s.Fits(v.Type) && s.IsFree() && s.TryOccupy(v))
            {
                Interlocked.Decrement(ref _available);
                return s;
            }
        }
        return null; // full or no compatible spot
    }

    public void Release(ParkingSpot s)
    {
        s.Free();
        Interlocked.Increment(ref _available);
    }

    public int AvailableCount() => Volatile.Read(ref _available);
}

class Ticket
{
    public string Id { get; }
    public string SpotId { get; }
    public Vehicle Vehicle { get; }
    public long EntryTime { get; }
    public long ExitTime { get; set; }
    public double Fee { get; set; }

    public Ticket(string id, string spotId, Vehicle v, long entryTime)
    {
        Id = id; SpotId = spotId; Vehicle = v; EntryTime = entryTime;
    }
}

// Singleton via Lazy<T> — thread-safe, lazy, no manual locking
sealed class ParkingLot
{
    private static readonly Lazy<ParkingLot> _instance = new(() => new ParkingLot());
    public static ParkingLot Instance => _instance.Value;
    private ParkingLot() { }

    private readonly List<Level> _levels = new();
    private readonly ConcurrentDictionary<string, (ParkingSpot Spot, Level Level)> _ticketToSpot = new();

    public void AddLevel(Level l) => _levels.Add(l);

    // Concurrent-safe: each spot claim is atomic; levels scanned lowest-first (nearest)
    public Ticket Park(Vehicle v)
    {
        foreach (var level in _levels)
        {
            var spot = level.Allocate(v);      // thread-safe inside
            if (spot != null)
            {
                var t = new Ticket(Guid.NewGuid().ToString(),
                                   spot.Id, v, NowMs());
                _ticketToSpot[t.Id] = (spot, level);
                return t;
            }
        }
        throw new InvalidOperationException($"Parking full for {v.Type}"); // clean "full" signal
    }

    public double Unpark(Ticket t)
    {
        // TryRemove makes double-exit safe: the second call gets false
        if (!_ticketToSpot.TryRemove(t.Id, out var entry))
            throw new ArgumentException("Invalid/used ticket");

        entry.Level.Release(entry.Spot);       // frees spot + updates the level counter (O(1))
        t.ExitTime = NowMs();
        t.Fee = ComputeFee(t);
        return t.Fee;
    }

    private double ComputeFee(Ticket t)
    {
        long hours = System.Math.Max(1, (t.ExitTime - t.EntryTime) / 3_600_000);
        return hours * 10.0; // $10/hr, min 1 hr
    }

    private static long NowMs() => DateTimeOffset.UtcNow.ToUnixTimeMilliseconds();
}
```
> **Alternative (lock-based `Level.Allocate`):** wrap the scan+occupy in a `lock`:
> ```csharp
> private readonly object _lock = new object();
>
> public ParkingSpot? Allocate(Vehicle v)
> {
>     lock (_lock)
>     {
>         foreach (var s in _spots)
>             if (s.Fits(v.Type) && s.IsFree()) { s.TryOccupy(v); _available--; return s; }
>         return null;
>     }
> }
> ```
> Simpler to reason about; slightly less concurrent than the CAS version. Either is a valid interview answer — state the trade-off.

**Interview talking points / pitfalls:**
- **Where's the race?** Two gates picking the same free spot. Fix: atomic claim — either `Interlocked.CompareExchange` on the spot, or occupy inside the level lock. *Checking* `IsFree()` then occupying in two steps without atomicity is the classic bug.
- **Nearest spot:** keep spots ordered (or a per-level priority structure of free spots) so the first free compatible one *is* the nearest.
- **Full-lot check must be cheap:** an `Interlocked`-maintained counter per level avoids scanning/locking just to answer "are we full?".
- **Don't lock the whole lot** — lock per level (or go lock-free per spot) so different floors run in parallel.
- **`Unpark` needs a spot→level mapping** for O(1) release + counter update — stored here in the ticket map as a tuple.
- **Idempotency:** removing the ticket from a `ConcurrentDictionary` with `TryRemove` ensures a double-exit is caught (the second call returns `false`).
- Mention **fairness/entry queue** if gates back up, and **overflow handling** (waiting queue vs. reject) as extensions.

# Interview Cheat-Sheet

| Design | Key concurrency tools | Main gotcha |
|--------|-----------------------|-------------|
| Singleton | `Lazy<T>` / `static readonly` (runtime-managed) | Don't hand-write double-checked locking; `Lazy<T>` mode must be `ExecutionAndPublication` |
| Producer–Consumer | **bounded** `BlockingCollection<T>` or `Channel<T>` | Unbounded → OOM; no back-pressure |
| Thread-safe Cache | `ConcurrentDictionary` + `Lazy<T>` in `GetOrAdd`, lock for eviction | `GetOrAdd` factory can run twice → wrap in `Lazy<T>`; multi-key eviction needs a lock |
| Rate Limiter | `Interlocked` / small `lock` critical section, `ConcurrentDictionary` per client, `System.Threading.RateLimiting` | Single-node only; window-edge bursts; unbounded client map |
| Parking Lot | Per-level `lock` **or** `Interlocked.CompareExchange` CAS + `Interlocked` counter | Two gates grabbing one spot; check-then-act race |
| Counters | `Interlocked.Increment` | `volatile` alone is NOT atomic for `++` |
| Read-heavy state | `ReaderWriterLockSlim` | Writer starvation; still lock on writes |
| Timed / non-blocking acquire | `Monitor.TryEnter(obj, timeout, ref taken)` | Forgetting `Monitor.Exit` in `finally` |

**Quick decision rules:**
- Need atomicity on a compound action → **`lock`** (Monitor) — smallest correct tool first.
- Need only visibility of a flag → **`volatile`** (or `Volatile.Read/Write`).
- Need an atomic counter → **`Interlocked.Increment`** (not `volatile`).
- Need a concurrent map → **`ConcurrentDictionary`** (+ `Lazy<T>` in `GetOrAdd` for get-or-load).
- Need to run tasks → **`Task.Run`/`Task.WhenAll`** (I/O: just `await`; cap CPU-bound with `SemaphoreSlim`/`MaxDegreeOfParallelism`).
- Need to hand off work between threads → **`BlockingCollection<T>`** or **`Channel<T>`** (bounded).

# How to talk about thread-safety in an interview

**English:** A crisp structure that impresses interviewers:
1. **Name the shared mutable state** explicitly ("the free-spot map / the token count / the LRU list").
2. **Name the operations** that touch it and whether they are read, write, or **compound** (check-then-act, read-modify-write) — compound is where races hide.
3. **Choose the smallest correct tool:** immutable > `Interlocked` > concurrent collection > fine-grained lock > coarse lock. Justify it.
4. **State the critical section** and keep it small (no I/O inside a lock; never `await` inside a `lock`).
5. **Call out failure modes proactively:** race conditions, deadlock (consistent lock ordering), starvation (fairness), memory blow-up (bounded collections), visibility (`volatile`).
6. **Mention scale:** "this is correct on one node; for multiple nodes I'd move shared state to Redis / a DB with atomic ops."
7. **Trade-offs, always:** simplicity vs. throughput; you rarely need the fanciest option.

**One-liner to remember:**
> "First make it **correct** (protect the shared state), then make it **fast** (shrink the lock, go lock-free only where it pays)."

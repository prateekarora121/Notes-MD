# Concurrency Fundamentals (Beginner to Advanced)

> A C#/.NET-first study note for an SDE-2 interview.
> Every topic goes from beginner to advanced, with analogies, pitfalls, interview Q&A, and a final cheat-sheet — all in terms of the C# concurrency toolkit.

## Intro — Why concurrency matters

Modern CPUs have many cores. A program that does one thing at a time leaves most of that hardware idle. Concurrency lets a program make progress on many tasks (serving 1000 web requests, downloading files, crunching data) without blocking — and parallelism lets it run truly at the same time on multiple cores. Getting this right is the difference between a snappy service and one that deadlocks, corrupts data, or falls over under load. Interviewers probe concurrency because it exposes whether you *really* understand shared state, memory, and coordination.

## 1. Threads & Processes

### What it is
A **process** is an independent program in execution with its own isolated memory (heap, stack, file handles). A **thread** is the smallest unit of execution *inside* a process; threads of the same process **share** the process's heap memory but each has its **own stack** and instruction pointer. In a .NET program, `Main()` runs on the "main" thread, and you create more threads (or, more commonly, schedule `Task`s onto the thread pool) to do work concurrently. A thread moves through a **lifecycle** of states, and the OS/CLR performs **context switching** to give each thread CPU time.

Think of a **process** as a separate restaurant — its own kitchen, its own stock, nothing shared with any other restaurant. A **thread** is a waiter in that restaurant. All the waiters of one restaurant share the same kitchen (heap memory), but each waiter holds their own order-slip (stack). Because the kitchen is shared, two waiters touching the same dish at once can cause a mess — and that is where all concurrency problems begin.

**Concurrency vs Parallelism:** Concurrency = one waiter *managing* several tables by switching between them (one core, fast switching). Parallelism = several waiters literally working different tables at the same instant (many cores). Concurrency is "dealing with many things"; parallelism is "doing many things at once."

### Why it matters / when to use it
- Keep UIs responsive, serve many requests, overlap I/O with computation.
- Interviewers love the process-vs-thread and concurrency-vs-parallelism distinction as a warm-up.

### Thread lifecycle / states (.NET `ThreadState`)
| State | Meaning |
|-------|---------|
| `Unstarted` | Created but `Start()` not called yet |
| `Running` | Started and eligible to run (running or ready, waiting for a CPU slot) |
| `WaitSleepJoin` | Blocked in `Monitor.Wait`, `Thread.Sleep`, or `Join` (indefinite or timed) |
| `Background` | Running as a background thread (won't keep the process alive) |
| `Stopped` | The thread's method has finished |

> For `Task`s you reason about `TaskStatus` instead (`Created`, `WaitingToRun`, `Running`, `RanToCompletion`, `Faulted`, `Canceled`) — the thread pool owns the underlying threads.

### Code example
```csharp
using System;
using System.Threading;
using System.Threading.Tasks;

class Demo
{
    static async Task Main()
    {
        // 1) Raw Thread with a ThreadStart delegate
        var t = new Thread(() =>
            Console.WriteLine($"Raw thread {Environment.CurrentManagedThreadId}"));
        t.Start();   // Unstarted -> Running; Start() spawns a new OS thread
        t.Join();    // main waits until t finishes (WaitSleepJoin)

        // 2) Task — the idiomatic path (schedules work onto the thread pool)
        Task task = Task.Run(() =>
            Console.WriteLine($"Task on thread {Environment.CurrentManagedThreadId}"));
        await task;

        // 3) Task<T> — returns a value / can surface an exception
        Task<int> job = Task.Run(() => 40 + 2);
        int result = await job;                 // await instead of blocking
        Console.WriteLine($"Task<int> result = {result}"); // 42
    }
}
```
> Note: call `Start()`, NOT the delegate directly. Invoking the delegate yourself just runs it on the *current* thread — no new thread is created. Prefer `Task`/`Task<T>` + `async/await` over raw `Thread`s for most work; reach for a raw `Thread` only for long-running or specialized blocking work.

### Common pitfalls / interview gotchas
- Invoking the work delegate directly instead of `Start()` (no new thread).
- Assuming threads share stacks — they don't; only the heap is shared.
- Confusing concurrency (structure) with parallelism (execution). A single core can be concurrent but not parallel.
- Thinking `Running` means "currently executing" — it also covers "ready, waiting for a CPU slot."
- Too many threads → excessive **context switching** overhead (saving/restoring registers, cache thrash).

### Interview Q&A
- **Q: Difference between process and thread?** A: Processes have isolated memory; threads share the process heap but have separate stacks. Threads are cheaper to create and switch.
- **Q: `Task` vs `Task<T>` (or `Action` vs `Func<T>`)?** A: `Task`/`Action` runs work with no return value; `Task<T>`/`Func<T>` returns a value and surfaces exceptions when you `await` the result.
- **Q: Concurrency vs parallelism?** A: Concurrency is dealing with many tasks by interleaving; parallelism is executing multiple tasks literally simultaneously on multiple cores.

## 2. Locks & Mutex

### What it is
When multiple threads touch shared data, you need **mutual exclusion** — only one thread in the "danger zone" at a time. That danger zone is the **critical section**. A **mutex** (MUTual EXclusion lock) is the mechanism that enforces it: a thread must *acquire* the lock before entering, and *release* it after. In C#, any reference object can be used as a **monitor** via the `lock` statement; there is also `System.Threading.Mutex` for a true OS-level (cross-process) mutex.

Picture a washroom that only one person can use. There's a lock on the door (the mutex). Before going in you take the lock (acquire); on the way out you release it. While one person is inside, the rest wait in a queue. That "time inside" is the **critical section** — where you use the shared resource (the washroom) alone. In C# you take that lock with the `lock` statement over a dedicated lock object.

### Why it matters / when to use it
- Any time two or more threads read/write the same mutable state and at least one writes.
- To make a compound operation (read-modify-write) appear **atomic**.

### Code example
```csharp
class Counter
{
    private int _count = 0;
    private readonly object _lock = new(); // a dedicated lock object

    public void Increment()
    {
        lock (_lock)   // acquire the monitor
        {
            _count++;  // critical section (only one thread here at a time)
        }              // monitor released automatically on block exit
    }

    public int Get()
    {
        lock (_lock) { return _count; }
    }
}
```
> `lock (obj) { ... }` compiles to `Monitor.Enter/Monitor.Exit` in a `try/finally`, so the lock is always released even on exception. For in-process mutual exclusion prefer `lock`/`Monitor`; use `System.Threading.Mutex` only when you need a named, cross-process lock (it is much heavier).

### Common pitfalls / interview gotchas
- Locking on a **different object** than the one others lock on → no mutual exclusion.
- Locking on a `string` literal (interned) or a boxed value type (shared/re-boxed unexpectedly). Use a `private readonly object`.
- Forgetting that reads also need the lock for **visibility**, not just writes.
- Holding a lock while doing slow I/O → kills throughput.

### Interview Q&A
- **Q: What is a critical section?** A: The block of code that accesses shared resources and must be executed by only one thread at a time.
- **Q: Mutex vs semaphore (one line)?** A: A mutex allows exactly one holder (ownership); a counting semaphore allows up to N permits.
- **Q: What is a monitor in .NET?** A: Any object can act as a synchronization monitor; the `Monitor` class (`Enter`/`Exit`/`Wait`/`Pulse`) underlies the `lock` statement.

## 3. lock statement & Monitor

### What it is
`lock` is C#'s built-in construct for acquiring an object's **monitor** (it lowers to `Monitor.Enter`/`Monitor.Exit`). C# has no `synchronized` method keyword like some languages — you wrap the body in a `lock` block yourself. Locking on an **instance** field (`private readonly object _lock`) protects per-object state; locking on a **static** object protects type-wide state (conceptually like `typeof(X)`, but you should use a private static object rather than `typeof(X)` directly). The `lock`/`Monitor` is **reentrant** — a thread already holding the lock can re-acquire it without deadlocking itself (the CLR keeps a hold count).

`lock` means "before entering this code, take the object's key." Two useful patterns:
- **Whole method body:** wrap everything in `lock (_lock)` — coarse but simple.
- **Small block:** `lock (_lock) { ... }` around only the lines that touch shared state — better performance (you hold the key for less time).

**Object lock vs type lock:** an instance lock object gives each object its own key; a static lock object gives one key shared across all instances.

**Reentrancy:** if a locked method calls another method that takes the *same* lock, the thread doesn't wait — it already owns the key. The CLR counts it (took it twice = must release it twice).

### Why it matters / when to use it
- Simplest way to protect shared state; no explicit unlock to forget (the block releases automatically).
- Lock the **smallest** region necessary to maximize concurrency.

### Code example
```csharp
class Account
{
    private int _balance;
    private readonly object _lock = new();

    // Instance-level lock: guard state with a private lock object
    public void Deposit(int amt)
    {
        lock (_lock) { _balance += amt; }
    }

    // Keep the locked region small — do cheap work outside the lock
    public void DepositChecked(int amt)
    {
        Validate(amt);                       // NOT locked — cheap, keep outside
        lock (_lock) { _balance += amt; }
    }

    // Type-level lock: shared across ALL instances
    private static int _totalAccounts;
    private static readonly object _typeLock = new();
    public static void Register()
    {
        lock (_typeLock) { _totalAccounts++; }
    }

    // Reentrancy demo: TransferFrom holds _lock and calls Deposit which
    // re-acquires the SAME lock — allowed because lock is reentrant.
    public void TransferFrom(Account other, int amt)
    {
        lock (_lock)
        {
            other.Withdraw(amt);
            Deposit(amt);                    // re-acquires _lock; no self-deadlock
        }
    }

    public void Withdraw(int amt) { lock (_lock) { _balance -= amt; } }
    private void Validate(int amt) { if (amt < 0) throw new ArgumentException(); }
}
```

### Common pitfalls / interview gotchas
- **Instance lock and static lock are different monitors** — guarding an instance method does NOT exclude a static method guarded by a different lock object.
- Locking on `this` or `typeof(T)` exposes your lock to outside code (anyone can `lock` the same object/type), risking deadlock. Prefer a `private readonly object`.
- Locking giant regions hurts concurrency; shrink the `lock` block.
- `lock` gives you the memory-visibility guarantee as a bonus — releasing a monitor *happens-before* another thread acquiring it.

### Interview Q&A
- **Q: Why lock a private object instead of `this` or `typeof(T)`?** A: Locking `this`/`typeof(T)` leaks your lock to callers, who can then cause deadlocks; a private lock object is only visible to your class.
- **Q: Is `lock` reentrant?** A: Yes. A thread can re-acquire a monitor it already holds; the CLR keeps a hold count and requires a matching number of exits.
- **Q: Do two threads calling different methods that lock the same object run in parallel?** A: No — both need the same monitor, so they're mutually exclusive.

## 4. Deadlock, Livelock, Starvation

### What it is
- **Deadlock:** Two or more threads each hold a lock the other needs and wait forever. Nobody progresses.
- **Livelock:** Threads are *active* (not blocked) but keep responding to each other and never make progress — like two people stepping side to side in a hallway.
- **Starvation:** A thread never gets CPU/lock because greedier/higher-priority threads keep winning.

A deadlock requires **all four Coffman conditions** simultaneously:
1. **Mutual exclusion** — resources can't be shared.
2. **Hold and wait** — a thread holds one resource while waiting for another.
3. **No preemption** — a resource can't be forcibly taken away.
4. **Circular wait** — a cycle of threads each waiting on the next.

Break **any one** condition → no deadlock.

- **Deadlock:** two diners, one holding the fork, the other the knife. Each says "you first," neither gives in — both sit hungry forever.
- **Livelock:** two people face to face in a corridor; both step left, then both step right — politely moving but never crossing. Busy, zero progress.
- **Starvation:** at a ticket window a pushy person keeps cutting in; the one at the back never gets a turn.

### Why it matters / when to use it
- Prevention (not just detection) is a top interview theme. The go-to fixes are **global lock ordering** (breaks circular wait) and **`Monitor.TryEnter` with a timeout** (breaks hold-and-wait / no-preemption).

### Code example
```csharp
using System.Runtime.CompilerServices;
using System.Threading;

// DEADLOCK: thread A locks a then b; thread B locks b then a
void DeadlockProne(object a, object b)
{
    lock (a)
    {
        lock (b) { /* ... */ }
    }
}

// FIX 1 — Lock ordering: ALWAYS acquire in a fixed global order (by identity hash)
void SafeTransfer(Account x, Account y, int amt)
{
    Account first  = RuntimeHelpers.GetHashCode(x) < RuntimeHelpers.GetHashCode(y) ? x : y;
    Account second = ReferenceEquals(first, x) ? y : x;
    lock (first)
    {
        lock (second) { x.Withdraw(amt); y.Deposit(amt); }
    }
}

// FIX 2 — Monitor.TryEnter with timeout: back off if you can't get both
bool Transfer(object l1, object l2)
{
    if (Monitor.TryEnter(l1, TimeSpan.FromSeconds(1)))
    {
        try
        {
            if (Monitor.TryEnter(l2, TimeSpan.FromSeconds(1)))
            {
                try { /* do work */ return true; }
                finally { Monitor.Exit(l2); }
            }
        }
        finally { Monitor.Exit(l1); }
    }
    return false; // couldn't get both — retry / abort, no deadlock
}
```
> In `async` code the most common deadlock comes from blocking on `.Result`/`.Wait()` while a captured `SynchronizationContext` (e.g. classic ASP.NET or a UI thread) is waiting for the continuation. Fix: `await` all the way down, or use `ConfigureAwait(false)`.

### Common pitfalls / interview gotchas
- Nested `lock`s taken in inconsistent order is the #1 deadlock cause.
- Livelock: a naive "if I can't get the lock, release everything and retry immediately" can loop forever — add randomized backoff.
- .NET's `lock`/`Monitor` is **not fair** — there's no built-in fairness or priority option, so starvation is possible under heavy contention.
- Detecting deadlock at runtime: capture a dump (`dotnet-dump`, Visual Studio "Parallel Stacks") and inspect which threads own/await which locks.

### Interview Q&A
- **Q: Name the 4 Coffman conditions.** A: Mutual exclusion, hold-and-wait, no-preemption, circular wait — all four needed for deadlock.
- **Q: How do you prevent deadlock?** A: Break a condition — most practically, impose a global lock ordering (kills circular wait) or use `Monitor.TryEnter` with a timeout (kills hold-and-wait).
- **Q: Deadlock vs livelock?** A: In deadlock threads are blocked and idle; in livelock they're running and changing state but still make no progress.

## 5. Race Conditions

### What it is
A **race condition** is when the correctness of the result depends on the *timing/interleaving* of threads. The classic culprits:
- **Read-modify-write:** `count++` is actually *read count → add 1 → write back*. Two threads can both read the same old value and one increment is lost.
- **Check-then-act:** `if (!dict.ContainsKey(k)) dict.Add(k, v);` — another thread can slip in between the check and the act.

Two distinct hazards feed races:
- **Atomicity** — a compound operation must happen all-or-nothing.
- **Visibility** — one thread's write must become visible to another (see topic 9, `volatile`).

A race condition means the result depends on which thread arrives first — like two people racing for the same seat. `count++` looks like one line but is three CPU steps: read, add, write back. Two threads both read 5, both write 6 — one increment vanished, the data is corrupt.

**Check-then-act** example: a bank reads balance "1000" and starts a withdrawal; meanwhile another thread also read 1000 and withdrew too — both drain the account into the negative. Fix: put the check and the act inside the same lock so they are atomic together.

### Why it matters / when to use it
- Races cause *intermittent* bugs that pass in dev and explode in prod under load — the scariest category.
- Fix by making the compound op atomic (`lock`, or `Interlocked`/CAS) and ensuring visibility.

### Code example
```csharp
using System.Collections.Concurrent;
using System.Threading;

class Unsafe
{
    public int Count;
    public void Inc() { Count++; }          // RACE: read-modify-write not atomic
}

class SafeLock
{
    private int _count;
    private readonly object _lock = new();
    public void Inc() { lock (_lock) { _count++; } }   // atomic + visible via monitor
}

class SafeAtomic
{
    private int _count;
    public void Inc() => Interlocked.Increment(ref _count); // lock-free atomic (CAS)
}

// check-then-act fix using an atomic dictionary operation
var m = new ConcurrentDictionary<string, int>();
m.TryAdd("k", 1);            // single atomic step, no gap between check and act
m.GetOrAdd("k", _ => 1);     // atomically get existing or create
```

### Common pitfalls / interview gotchas
- Believing `count++` or `x = x + 1` is atomic — it is not.
- Fixing atomicity but forgetting visibility (or vice versa). `volatile` gives visibility but NOT atomicity for `++`.
- `if (instance == null) instance = new X();` in a property/getter — classic check-then-act race (prefer `Lazy<T>`; see topic 9).
- Using a plain `Dictionary<,>` from multiple threads → can corrupt internal state / throw; use `ConcurrentDictionary<,>`.

### Interview Q&A
- **Q: Why is `count++` not thread-safe?** A: It's a read-modify-write of three steps; interleaving can lose updates (lost-update problem).
- **Q: Atomicity vs visibility?** A: Atomicity = the whole operation is indivisible; visibility = a write by one thread is seen by others. You often need both.
- **Q: Give a check-then-act bug and its fix.** A: `if (!dict.ContainsKey(k)) dict.Add(k, v)` racing; fix with `ConcurrentDictionary.TryAdd`/`GetOrAdd` or a lock around both steps.

## 6. Semaphores

### What it is
A **semaphore** maintains a set of **permits**. `Wait()`/`WaitAsync()` takes a permit (blocking if none left); `Release()` returns one. A **counting semaphore** allows up to *N* concurrent holders — perfect for limiting access to a pool of N resources or **rate limiting**. A **binary semaphore** (N=1) behaves like a lock, but unlike a mutex it has **no ownership** — any thread can release it. In C# use `SemaphoreSlim` for fast in-process gating (with async support) and `System.Threading.Semaphore` for a named, system-wide semaphore.

A semaphore is like a parking-lot gate with 3 tokens (3 spots). To enter you take a token (`Wait`) — if tokens are gone you wait at the gate. On leaving you put the token back (`Release`) so the next car can enter. **Counting semaphore** = N tokens (several cars at once). **Binary semaphore** = just 1 token (lock-like), but the difference from a mutex is that a mutex says "only the one who locked it can unlock it," while a semaphore lets any thread return a token — there's no ownership.

### Why it matters / when to use it
- **Resource pools** (DB connections, licenses) — cap concurrent users at N.
- **Rate limiting / throttling** — allow only N calls in flight.
- Signaling between threads (permits as signals).

### Code example
```csharp
using System;
using System.Threading;
using System.Threading.Tasks;

// Allow at most 3 threads to use the "service" concurrently
var sem = new SemaphoreSlim(3);              // 3 permits

async Task UseServiceAsync()
{
    await sem.WaitAsync();                    // take a permit (async; blocks if 0 left)
    try
    {
        await CallExternalApiAsync();         // at most 3 callers here at once
    }
    finally
    {
        sem.Release();                        // ALWAYS release in finally
    }
}

// WaitAsync with a timeout for throttling without waiting forever
if (await sem.WaitAsync(TimeSpan.FromMilliseconds(500)))
{
    try { await DoWorkAsync(); } finally { sem.Release(); }
}
else
{
    // rejected / back-pressure
}
```
> `SemaphoreSlim` is in-process and async-friendly (`WaitAsync`). Use `new Semaphore(3, 3)` (or a named `Semaphore`) only when you need a system-wide, cross-process limit. Neither offers a fairness/FIFO guarantee.

### Common pitfalls / interview gotchas
- Forgetting `Release()` in a `finally` → permits leak, the pool eventually starves.
- Calling `Release()` more times than you acquired → `SemaphoreSlim.Release` throws `SemaphoreFullException` once you exceed the max count (unlike some implementations that silently grow).
- Using a binary semaphore where you need reentrancy — semaphores are NOT reentrant; re-acquiring from the same thread can self-deadlock.
- Assuming FIFO order — `SemaphoreSlim` does not guarantee it.

### Interview Q&A
- **Q: Counting vs binary semaphore?** A: Counting allows up to N permits; binary has 1 (lock-like).
- **Q: Semaphore vs mutex?** A: A mutex has ownership (only the locker unlocks) and `lock` is reentrant; a semaphore is a permit counter with no ownership and any thread may release.
- **Q: A real use case?** A: Limiting concurrent connections to a resource pool, or throttling calls to a downstream API.

## 7. Condition signaling: Monitor.Wait / Pulse

### What it is
`Monitor.Wait`, `Monitor.Pulse`, and `Monitor.PulseAll` provide **condition-based coordination** between threads using an object's monitor. A thread calls `Monitor.Wait(gate)` to **release the lock** and sleep in the object's **wait queue** until another thread calls `Monitor.Pulse(gate)` (wakes one) or `Monitor.PulseAll(gate)` (wakes all) on the *same* object. All three **must be called while holding that object's monitor** (inside `lock`), otherwise you get `SynchronizationLockException`. Always wait **in a loop checking a condition** because of **spurious wakeups** and because the condition may have changed by the time you re-acquire the lock.

Think of a waiter–kitchen signaling system. The waiter (`consumer`) comes to the counter; if no dish is ready, they call `Monitor.Wait` — *releasing the key* and sleeping so the cook can work. The cook (`producer`) makes a dish and calls `Monitor.Pulse` to wake one waiter, or `Monitor.PulseAll` to wake them all.

Three golden rules:
1. Call these **only inside `lock`**, or you get `SynchronizationLockException`.
2. Always check the condition in a **`while` loop**, not an `if` — a thread can wake without being signaled (**spurious wakeup**), and by the time it wakes another thread may have taken the item.
3. `Monitor.Pulse` = wake one (which one is unspecified); `Monitor.PulseAll` = wake all (the safe default).

### Why it matters / when to use it
- Building blocking queues, producer-consumer, and bounded buffers by hand.
- Classic interview topic and the foundation for understanding higher-level signaling primitives.

### Code example
```csharp
using System.Collections.Generic;
using System.Threading;

// Wait/Pulse: all three MUST be called inside lock(_gate) — you must own the monitor.
class BoundedBuffer<T>
{
    private readonly Queue<T> _q = new();
    private readonly object _gate = new();
    private readonly int _cap;
    public BoundedBuffer(int cap) => _cap = cap;

    public void Put(T item)
    {
        lock (_gate)
        {
            while (_q.Count == _cap) Monitor.Wait(_gate); // WHILE, not if (spurious wakeups)
            _q.Enqueue(item);
            Monitor.PulseAll(_gate);                       // wake waiting consumers
        }
    }

    public T Take()
    {
        lock (_gate)
        {
            while (_q.Count == 0) Monitor.Wait(_gate);     // release lock & sleep until pulsed
            var item = _q.Dequeue();
            Monitor.PulseAll(_gate);                        // wake waiting producers
            return item;
        }
    }
}
```
`Monitor.Pulse` wakes one waiter; `Monitor.PulseAll` wakes all.

**Prefer higher-level constructs in modern C#:** you rarely hand-roll `Monitor.Wait/Pulse`. Reach for `SemaphoreSlim` (async-friendly gating/counting), `ManualResetEventSlim` / `AutoResetEvent` (one-shot or gated signals), `TaskCompletionSource<T>` (complete a `Task` when a result is ready), `System.Threading.Channels` (bounded/unbounded producer-consumer with back-pressure), and plain `async/await`. These handle the waiting/signaling correctly and compose with async code.

### Common pitfalls / interview gotchas
- Calling `Wait`/`Pulse` **outside** `lock` → `SynchronizationLockException`.
- Using `if` instead of `while` for the condition → breaks on spurious wakeups and multi-consumer races.
- Using `Pulse` when multiple different conditions share one monitor → may wake the "wrong" thread and stall; prefer `PulseAll` (or use separate signaling primitives per condition).
- `Monitor.Wait` releases only *this* object's monitor, not other locks you hold.
- Confusing `Monitor.Wait` (releases the lock) with `Thread.Sleep` (does NOT release the lock).

### Interview Q&A
- **Q: Why must `Wait`/`Pulse` be inside `lock`?** A: They operate on the object's monitor; you must own it, and it enforces the atomic check-then-wait needed to avoid lost wakeups.
- **Q: `Pulse` vs `PulseAll`?** A: `Pulse` wakes one arbitrary waiter; `PulseAll` wakes all. Use `PulseAll` when different threads wait on different conditions to avoid stuck threads.
- **Q: Why loop on the condition?** A: Spurious wakeups, and the fact that another thread may invalidate the condition before you re-acquire the lock.

## 8. Thread Pools & Task Parallel Library (TPL)

### What it is
Creating a new thread per task is expensive (memory, OS scheduling) and unbounded (can exhaust resources). A **thread pool** reuses a fixed set of worker threads to run many tasks from a queue. .NET ships a managed `ThreadPool`, and the **Task Parallel Library (TPL)** — `Task`, `Task.Run`, `Task.WhenAll`, `Parallel.ForEach` — sits on top of it, so you submit *work*, not threads.

Key knobs of a thread pool (conceptual — same everywhere):
- **minimum threads** — worker threads kept ready even when idle (`ThreadPool.SetMinThreads`).
- **maximum threads** — the ceiling on worker threads (`ThreadPool.SetMaxThreads`).
- **work queue** — where queued work waits before a worker picks it up.
- **idle management** — the pool trims extra idle threads over time.
- **injection heuristic** — .NET auto-tunes the live thread count with a hill-climbing algorithm; it injects new threads slowly (roughly one or two per second) once the minimum is exceeded.

Creating a new thread per task is like hiring a new waiter for every customer — expensive and absurd. A thread pool means a fixed set of workers pulling tasks off a queue: finish one, grab the next, reuse.

### Why it matters / when to use it
- Almost every real server uses a pool. Sizing and back-pressure behavior are prime SDE-2 questions.
- For bounded producer-consumer pipelines prefer `System.Threading.Channels` or TPL Dataflow over hand-sizing a raw pool; they give you back-pressure and clean async composition.

### Code example
```csharp
using System.Linq;
using System.Threading;
using System.Threading.Tasks;

// 1) Managed thread pool directly (fire-and-forget)
ThreadPool.QueueUserWorkItem(_ => DoWork());

// 2) TPL — the idiomatic path: Task.Run schedules the work onto the thread pool
Task<int> t = Task.Run(() => 40 + 2);
int result = await t;                        // 42 (no thread is blocked while awaiting)

// 3) Fan-out, then join
var tasks = urls.Select(u => Task.Run(() => Fetch(u)));
string[] pages = await Task.WhenAll(tasks);  // run in parallel, await all

// 4) Data parallelism over a collection (partitions across pool threads)
Parallel.ForEach(items, item => Process(item));

// 5) Tune the pool floor to cut ramp-up latency for bursty load
ThreadPool.SetMinThreads(workerThreads: 50, completionPortThreads: 50);
```
`async/await` also runs its continuations on the thread pool by default, so you rarely touch threads directly. For work that must block for a long time, create a dedicated thread (or `Task.Factory.StartNew(..., TaskCreationOptions.LongRunning)`) instead of tying up a pool worker.

### Common pitfalls / interview gotchas
- **Thread-pool starvation:** blocking a pool thread (`.Result`, `.Wait()`, `Thread.Sleep`, sync-over-async) ties up a worker; because the pool injects new threads slowly, throughput collapses under load. Stay async end-to-end.
- Exceptions in a `Task` are **captured** and rethrown when you `await` it or read `.Result`; an un-awaited task's exception can go unobserved. Always await (or otherwise observe) your tasks.
- Wrapping naturally-async I/O in `Task.Run` wastes a pool thread — just `await` the async API directly.
- Unbounded fan-out (queueing millions of tasks) causes memory/scheduler pressure — throttle with `SemaphoreSlim`, `Parallel.ForEachAsync`'s `MaxDegreeOfParallelism`, or `Channels`.

### Interview Q&A
- **Q: `Task.Run` vs `new Thread`?** A: `Task.Run` schedules onto the shared pool (reused workers, cheap, good for short CPU-bound work); `new Thread` creates a dedicated OS thread (expensive — reserve it for long-running or blocking work).
- **Q: `Task.WhenAll` vs `Task.WaitAll`?** A: `WhenAll` returns a `Task` you `await` (non-blocking, composes with async); `WaitAll` blocks the calling thread until all complete.
- **Q: How does the .NET thread pool manage its size?** A: It keeps a configurable minimum (`SetMinThreads`), serves work from a queue, and adds/removes workers up to the max via a hill-climbing heuristic; blocking pool threads causes starvation and slow injection.

## 9. volatile keyword

### What it is
Under the .NET memory model, a thread may cache a field in a register/CPU cache, and the compiler/JIT/CPU may reorder instructions. So one thread's write may **never become visible** to another. Marking a field `volatile` (or using the `Volatile.Read`/`Volatile.Write` methods) provides:
- **Visibility** — a volatile read always sees the latest write; reads/writes are not cached away.
- **Ordering (acquire/release)** — a volatile write has release semantics and a volatile read has acquire semantics, preventing certain reorderings across it.

What `volatile` does **NOT** give: **atomicity** of compound operations. `volatile int x; x++;` is still a race (read-modify-write).

Each thread has its own little notebook (CPU cache) where it copies values for speed. Problem: Thread A writes `flag = true` to main memory, but Thread B keeps reading its stale notebook copy (`flag == false`) — infinite loop. `volatile` says "don't cache this variable in a notebook; always read/write the shared blackboard (main memory)." That guarantees **visibility** and some **ordering**.

But careful: `volatile` gives visibility only, **not atomicity**. `count++` still races because it's three steps. It's perfect for flags, but for counters you need `Interlocked`.

### Why it matters / when to use it
- **Stop/ready flags** shared across threads: `private volatile bool _running`.
- One writer, many readers of a single value (publishing a reference safely).
- Historically, the field in a hand-rolled double-checked-locking singleton had to be `volatile` — but in C# prefer `Lazy<T>` instead of hand-rolling it.

### Code example
```csharp
using System;
using System.Threading;

class Worker
{
    private volatile bool _running = true;   // visibility across threads
    public void Run()
    {
        while (_running) { DoWork(); }        // sees Stop() promptly
    }
    public void Stop() { _running = false; }  // visible to the running thread
}

// volatile does NOT make ++ atomic:
//   volatile int count;  ->  count++ is STILL a race; use Interlocked.

// Volatile.Read/Write give explicit acquire/release without the field modifier
int flag = 0;
Volatile.Write(ref flag, 1);
int seen = Volatile.Read(ref flag);

// Thread-safe lazy singleton — prefer Lazy<T> over hand-rolled double-checked locking
class Singleton
{
    private static readonly Lazy<Singleton> _instance =
        new(() => new Singleton(), LazyThreadSafetyMode.ExecutionAndPublication);
    public static Singleton Instance => _instance.Value;
    private Singleton() { }
}
```
> The .NET and Java memory models differ in detail, but the practical rule is the same: `volatile`/`Volatile` give visibility and ordering for a single field; compound operations still need `Interlocked` or `lock`. `Lazy<T>` replaces hand-rolled double-checked locking.

### Common pitfalls / interview gotchas
- Thinking `volatile` makes `++`/compound ops atomic — it does not.
- Using `volatile` on a reference makes the *reference* visible, not the object's mutable internals.
- Reaching for hand-rolled double-checked locking instead of `Lazy<T>` — easy to get the ordering wrong.
- `volatile` is cheaper than a lock but is NOT a mutual-exclusion tool.

### Interview Q&A
- **Q: What does `volatile` guarantee?** A: Visibility (always read/write the latest value) and acquire/release ordering; not atomicity.
- **Q: How do you build a thread-safe lazy singleton in C#?** A: Use `Lazy<T>` with `LazyThreadSafetyMode.ExecutionAndPublication`; it handles the ordering/visibility correctly so you don't hand-roll double-checked locking.
- **Q: `volatile` vs `lock`?** A: `volatile` gives visibility/ordering for a single field with no mutual exclusion; `lock` gives mutual exclusion + visibility for a whole critical section.

## 10. Atomic operations with Interlocked

### What it is
The `System.Threading.Interlocked` class provides **lock-free**, thread-safe operations on a single variable using the CPU's **CAS (Compare-And-Swap)** instruction. `Interlocked.CompareExchange(ref x, newValue, expected)` says: "set `x` to *newValue* only if it currently equals *expected*; return the original value." Lock-free algorithms loop on `CompareExchange` until it succeeds, giving atomic increments/updates without blocking — usually faster than locks under moderate contention.

**ABA problem:** CAS only checks the value, not whether it changed A→B→A in between. If A→B→A matters (e.g. lock-free stacks/pointers), pair the value with a version counter so the CAS also sees the version change. .NET has no built-in "stamped reference"; you roll your own (e.g. a value+version struct swapped via `CompareExchange`).

`Interlocked.Increment` is a counter that grows safely without a lock. Under the hood CAS runs a loop: "I thought the value was 5; if it's still 5, make it 6, else tell me and I'll retry." That retry loop runs until it succeeds. Because there's no lock, it's fast and can't deadlock (**lock-free**).

**ABA problem:** say the value was 5, and someone did 5→10→5. CAS thinks "it's still 5, nothing changed" — even though it did change in between. If that matters, attach a version number (5 with stamp 1 vs 5 with stamp 3).

### Why it matters / when to use it
- High-throughput counters, sequence generators, statistics, flags, and lock-free data structures.
- When a single variable needs atomic updates and you want to avoid lock overhead/contention.

### Code example
```csharp
using System.Threading;

int counter = 0;

Interlocked.Increment(ref counter);          // atomic ++ (returns new value)
Interlocked.Decrement(ref counter);          // atomic --
Interlocked.Add(ref counter, 5);             // atomic += 5
int old = Interlocked.Exchange(ref counter, 100); // atomic set, returns previous value

// CompareExchange == CAS: set to 100 only if it currently equals 6
Interlocked.CompareExchange(ref counter, value: 100, comparand: 6);

// Atomic update of a reference
string? reference = "A";
Interlocked.CompareExchange(ref reference, "B", "A"); // CAS on a reference

// Manual CAS loop (how a lock-free update is built; the lambda-free equivalent
// of "read current, compute next, publish if unchanged, else retry")
int prev, next;
do
{
    prev = counter;
    next = prev * 2;
} while (Interlocked.CompareExchange(ref counter, next, prev) != prev);
```

### Common pitfalls / interview gotchas
- Under **very high contention**, CAS retry loops can waste CPU (livelock-ish); a `lock` may win. Benchmark.
- In a manual CAS loop, the "compute next" step must be **side-effect free** — it may run several times on retry.
- `Interlocked` covers a *single* variable. Two variables updated together are NOT jointly atomic — you still need a `lock` or a single `CompareExchange` on a reference to an immutable composite object.
- Ignoring the ABA problem in lock-free stacks/pointers.

### Interview Q&A
- **Q: What is CAS?** A: Compare-And-Swap — an atomic CPU op that updates a value only if it still equals an expected value, returning the original; the basis of lock-free algorithms. `Interlocked.CompareExchange` exposes it.
- **Q: `Interlocked` vs a `lock`ed counter?** A: `Interlocked` is lock-free (CAS retry), typically faster under moderate contention, and can't deadlock; a `lock` blocks threads and has more overhead but is simpler for compound state.
- **Q: What's the ABA problem?** A: A value changes A→B→A, so CAS wrongly thinks nothing changed. Fix by attaching a version counter to the value.

## 11. lock reentrancy & ReaderWriterLockSlim

### What it is
In C# the `lock`/`Monitor` is **reentrant** — a thread already holding the lock re-enters without deadlocking, and the CLR keeps a per-thread hold count (took it twice = must exit twice). For a non-blocking or timed attempt, use `Monitor.TryEnter` (with an optional timeout). Note that C# does **not** ship a built-in fair or interruptible lock like some languages' explicit lock types; for those semantics you build on `SemaphoreSlim`/events. For condition variables, use `Monitor.Wait/Pulse` (a single wait-set per monitor) or a dedicated `SemaphoreSlim`/`ManualResetEventSlim` per condition.

`ReaderWriterLockSlim` has two modes: many threads can hold the **read lock** simultaneously, but the **write lock** is exclusive (no readers, no other writer). It also offers an **upgradeable read lock** — you decide under a shared lock and upgrade to a write lock only if needed. Great for read-heavy data.

`Monitor.TryEnter` is "is the key free? no? fine, I won't wait" — the best way to avoid deadlocks. Reentrancy means a locked method can call another method that takes the same lock without blocking itself. And `ReaderWriterLockSlim` is like a library: unlimited readers can be in at once, but a writer clears the room — exclusive access. For read-heavy data that's excellent performance.

Trade-off: `lock` releases automatically at the end of its block, but with `Monitor.TryEnter` / `ReaderWriterLockSlim` you must **release yourself in a `finally`**, or the lock stays held forever.

### Why it matters / when to use it
- Need a timeout or try-lock → `Monitor.TryEnter`.
- Read-mostly shared structure (caches, config) → `ReaderWriterLockSlim` for concurrent reads.

### Code example
```csharp
using System;
using System.Collections.Generic;
using System.Threading;

// lock is reentrant — the CLR keeps a per-thread hold count
class ReentrantDemo
{
    private readonly object _lock = new();
    public void Outer()
    {
        lock (_lock)
        {
            Inner();            // re-acquires the SAME lock — allowed
        }
    }
    private void Inner()
    {
        lock (_lock) { /* critical section */ }
    }
}

// Monitor.TryEnter for try-lock with timeout
void TryLockDemo(object gate)
{
    bool taken = false;
    try
    {
        Monitor.TryEnter(gate, TimeSpan.FromSeconds(1), ref taken);
        if (taken) { /* critical section */ }
        // else: couldn't get it in time — back off / retry
    }
    finally
    {
        if (taken) Monitor.Exit(gate); // MUST release what you took
    }
}

// ReaderWriterLockSlim: many readers, one writer, plus upgradeable read
class Cache
{
    private readonly ReaderWriterLockSlim _rw = new();
    private readonly Dictionary<string, string> _map = new();

    public string? Read(string k)
    {
        _rw.EnterReadLock();
        try { return _map.TryGetValue(k, out var v) ? v : null; }
        finally { _rw.ExitReadLock(); }
    }

    public void Write(string k, string v)
    {
        _rw.EnterWriteLock();
        try { _map[k] = v; }
        finally { _rw.ExitWriteLock(); }
    }

    // Upgradeable read: check under a shared lock, upgrade to write only if needed
    public string GetOrAdd(string k, Func<string> factory)
    {
        _rw.EnterUpgradeableReadLock();
        try
        {
            if (_map.TryGetValue(k, out var v)) return v;
            _rw.EnterWriteLock();
            try { var nv = factory(); _map[k] = nv; return nv; }
            finally { _rw.ExitWriteLock(); }
        }
        finally { _rw.ExitUpgradeableReadLock(); }
    }
}
```
> Conditions map to `Monitor.Wait/Pulse` (one wait-set per monitor). If you need multiple independent wait-sets on one lock, use a separate `SemaphoreSlim`/`ManualResetEventSlim` per condition rather than one monitor.

### Common pitfalls / interview gotchas
- Forgetting to `Exit`/`ExitReadLock`/`ExitWriteLock` in a `finally` → permanent lock / deadlock.
- Not balancing enters and exits (both `Monitor` and `ReaderWriterLockSlim` track a hold count).
- `ReaderWriterLockSlim` is **not reentrant by default** (`LockRecursionPolicy.NoRecursion`) — re-entering the same lock throws `LockRecursionException`. This surprises people migrating from a reentrant `lock`.
- Write-starvation: a steady stream of readers can starve writers.
- You cannot hold a plain read lock and then directly take the write lock (deadlock); use `EnterUpgradeableReadLock` for that pattern.

### Interview Q&A
- **Q: `lock`/`Monitor` vs an explicit lock type?** A: `lock` is reentrant and auto-releases; for a timed/try acquire use `Monitor.TryEnter`. .NET has no built-in fair or interruptible lock — you build those on `SemaphoreSlim`/events.
- **Q: When `ReaderWriterLockSlim`?** A: Read-heavy, write-rare shared data — many readers proceed concurrently while writes stay exclusive.
- **Q: Why release in `finally`?** A: To guarantee release even if the critical section throws, avoiding a stuck lock.
- **Q: Is `ReaderWriterLockSlim` reentrant?** A: No, by default; re-entering throws `LockRecursionException` unless you opt into `LockRecursionPolicy.SupportsRecursion`.

## 12. Producer-Consumer Pattern

### What it is
A coordination pattern where **producer** threads generate items and **consumer** threads process them, decoupled by a shared **bounded buffer/queue**. It smooths out speed mismatches. When the buffer is **full**, producers wait (**back-pressure**); when it's **empty**, consumers wait. You can implement it by hand with `Monitor.Wait/Pulse`, but the idiomatic C# solutions are `BlockingCollection<T>` (classic, blocking) and `System.Threading.Channels` (modern, async) — both handle all the waiting internally.

**Back-pressure:** a full bounded buffer forcing producers to slow down — critical for preventing unbounded memory growth when producers outrun consumers.

Picture a kitchen: **cooks (producers)** make dishes and place them on a counter (buffer); **waiters (consumers)** pick them up and serve. The counter has limited space (bounded):
- Counter **full** → cooks stop making dishes → that's **back-pressure** (otherwise dishes hit the floor = memory blowup).
- Counter **empty** → waiters wait for a new dish.

That way each side works at its own pace without depending directly on the other.

### Why it matters / when to use it
- Task pipelines, message processing, work queues, batching, log processing.
- Interviewers ask you to implement it both ways (hand-rolled AND with a built-in queue) and to explain back-pressure.

### Code example

**Classic hand-rolled with Monitor.Wait/Pulse:**
```csharp
using System.Collections.Generic;
using System.Threading;

class WaitPulsePC<T>
{
    private readonly Queue<T> _buf = new();
    private readonly object _gate = new();
    private readonly int _cap;
    public WaitPulsePC(int cap) => _cap = cap;

    public void Produce(T item)
    {
        lock (_gate)
        {
            while (_buf.Count == _cap) Monitor.Wait(_gate); // full -> back-pressure
            _buf.Enqueue(item);
            Monitor.PulseAll(_gate);                         // wake consumers
        }
    }

    public T Consume()
    {
        lock (_gate)
        {
            while (_buf.Count == 0) Monitor.Wait(_gate);     // empty -> wait
            var item = _buf.Dequeue();
            Monitor.PulseAll(_gate);                          // wake producers
            return item;
        }
    }
}
```

**Idiomatic BlockingCollection (blocking):**
```csharp
using System.Collections.Concurrent;
using System.Threading.Tasks;

var queue = new BlockingCollection<int>(boundedCapacity: 10); // bounded => back-pressure

// Producer
var producer = Task.Run(() =>
{
    for (int i = 0; i < 100; i++) queue.Add(i);   // blocks if full
    queue.CompleteAdding();                        // signal: no more items
});

// Consumer
var consumer = Task.Run(() =>
{
    foreach (var item in queue.GetConsumingEnumerable()) // blocks if empty; ends on CompleteAdding
        Process(item);
});

await Task.WhenAll(producer, consumer);
```

**Modern Channels (async, preferred):**
```csharp
using System.Threading.Channels;
using System.Threading.Tasks;

var channel = Channel.CreateBounded<int>(10); // bounded => back-pressure

// Producer
var producer = Task.Run(async () =>
{
    for (int i = 0; i < 100; i++)
        await channel.Writer.WriteAsync(i);      // awaits (back-pressure) if full
    channel.Writer.Complete();                    // signal: no more items
});

// Consumer
var consumer = Task.Run(async () =>
{
    await foreach (var item in channel.Reader.ReadAllAsync()) // awaits if empty; ends on Complete
        Process(item);
});

await Task.WhenAll(producer, consumer);
```
> `BlockingCollection<T>` wraps a concurrent collection (defaults to a FIFO `ConcurrentQueue<T>`; can wrap `ConcurrentStack`/`ConcurrentBag`). `Channel.CreateBounded`/`CreateUnbounded` is the async-first option with built-in back-pressure. Always use a **bounded** capacity to get back-pressure.

### Common pitfalls / interview gotchas
- Using an **unbounded** queue → no back-pressure → memory blows up when producers outpace consumers.
- Hand-rolled version: using `if` instead of `while`, or `Pulse` instead of `PulseAll` with mixed producers/consumers → stuck threads.
- Forgetting to signal completion (`CompleteAdding` / `Writer.Complete`) or to honor a `CancellationToken` → consumers hang forever.
- Busy-waiting/polling instead of blocking → wastes CPU; let the queue block/await for you.

### Interview Q&A
- **Q: What problem does producer-consumer solve?** A: Decoupling producers and consumers of different speeds via a shared buffer, with back-pressure when the buffer fills.
- **Q: Why prefer `BlockingCollection`/`Channels` over hand-rolled `Monitor.Wait/Pulse`?** A: They encapsulate all synchronization, blocking/awaiting, and signaling correctly, so you avoid spurious-wakeup and lost-signal bugs.
- **Q: What is back-pressure?** A: A full bounded buffer forcing producers to slow/pause so consumers can catch up, preventing unbounded memory growth.

## Mental Model / Analogy Recap

- **Process vs Thread** — Separate restaurants vs waiters sharing one kitchen (shared heap, private stacks).
- **Mutex / lock** — A washroom with a single key: acquire before entering, release on exit.
- **Deadlock** — Two diners each clutching one utensil, each waiting for the other's; break the circular wait with a fixed ordering.
- **Livelock** — Two people politely dodging in a hallway forever. **Starvation** — the pushy guy always cuts the queue.
- **Race condition** — Both threads read "5", both write "6"; one increment vanishes.
- **Semaphore** — A parking lot with N tokens; no token, no entry.
- **Monitor.Wait/Pulse** — A waiter sleeps at the counter (releasing the key) until the cook rings the bell; always re-check the counter in a `while` (spurious wakeups).
- **Thread pool / TPL** — A fixed crew of waiters pulling orders off one queue instead of hiring a new waiter per customer.
- **volatile** — Don't trust your private notebook; read/write the shared blackboard so everyone sees the latest.
- **Interlocked / CAS** — "I thought it was 5; if it's still 5, make it 6, else tell me and I'll retry." No lock needed.
- **ReaderWriterLockSlim** — A library: unlimited readers together, but a writer clears the room.
- **Producer-Consumer** — Cooks put dishes on a limited counter, waiters take them; a full counter makes cooks pause (back-pressure).

> **Golden interview reminders:** `count++` is not atomic • `volatile` ≠ atomicity • always `Monitor.Wait` in a `while` • always release (`Monitor.Exit`/`ExitWriteLock`) in `finally` • bounded queues give back-pressure • break any one Coffman condition to prevent deadlock.

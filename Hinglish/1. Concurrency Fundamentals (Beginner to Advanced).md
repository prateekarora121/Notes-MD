# Concurrency Fundamentals (Beginner to Advanced)

> Ek C#/.NET-first study note, SDE-2 interview ke liye.
> Har topic beginner se advanced tak jaata hai — analogies, pitfalls, interview Q&A, aur end mein ek cheat-sheet ke saath — sab kuch C# ke concurrency toolkit ki bhaasha mein.

## Intro — Concurrency kyun matter karti hai

Aaj kal har CPU ke paas multiple cores hote hain. Agar program ek time pe ek hi kaam karega to zyada hardware khaali baitha rahega — paisa waste. Concurrency ka matlab hai program bahut saare kaam pe progress kare (1000 web requests serve karna, files download karna, data crunch karna) bina block hue — aur parallelism ka matlab hai sach mein ek saath multiple cores pe chalana. Isko sahi karna hi farak hai ek snappy service aur ek aisi service mein jo deadlock ho jaaye, data corrupt kar de, ya load pe gir jaaye. Interviewers concurrency isliye poochte hain kyunki yahi batata hai ki aapko shared state, memory aur coordination sach mein samajh aati hai ya nahi.

## 1. Threads & Processes

### Kya hai?
Ek **process** ek independent program hai jo execute ho raha hai, apni isolated memory ke saath (heap, stack, file handles). Ek **thread** process ke *andar* execution ki sabse chhoti unit hai; same process ke threads process ki heap memory **share** karte hain, lekin har thread ke paas apna **stack** aur instruction pointer alag hota hai. Ek .NET program mein `Main()` "main" thread pe chalta hai, aur aap aur threads banate ho (ya zyada common — thread pool pe `Task`s schedule karte ho) taaki kaam concurrently ho sake. Ek thread states ke **lifecycle** se guzarta hai, aur OS/CLR **context switching** karke har thread ko CPU time deta hai.

Socho ek **process** ek alag restaurant hai — apni kitchen, apna stock, kisi aur restaurant se koi lena-dena nahi. Ek **thread** us restaurant ka ek waiter hai. Ek hi restaurant ke saare waiter same kitchen (heap memory) share karte hain, lekin har waiter ke haath mein apni order-slip (stack) alag hoti hai. Kyunki kitchen shared hai, do waiters ek saath same dish ko haath lagayein to gadbad ho sakti hai — yahi se saari concurrency problems shuru hoti hain.

**Concurrency vs Parallelism:** Concurrency = ek waiter kai tables ko *manage* kar raha hai, beech-beech mein switch karke (ek core, tez switching). Parallelism = kai waiters sach mein ek saath alag tables pe kaam kar rahe hain (kai cores). Concurrency "dealing with many things", parallelism "doing many things at once".

### Kab use karein / kyun matter karta hai
- UIs ko responsive rakhna, bahut saari requests serve karna, I/O ko computation ke saath overlap karna.
- Interviewers ko process-vs-thread aur concurrency-vs-parallelism ka farak warm-up question ke roop mein bahut pasand hai.

### Thread lifecycle / states (.NET `ThreadState`)
| State | Matlab |
|-------|--------|
| `Unstarted` | Ban gaya par `Start()` abhi call nahi hua |
| `Running` | Start ho gaya, chalne ke liye eligible (chal raha ya ready, CPU slot ka wait) |
| `WaitSleepJoin` | `Monitor.Wait`, `Thread.Sleep`, ya `Join` mein block (indefinite ya timed) |
| `Background` | Background thread ke roop mein chal raha (process ko zinda nahi rakhta) |
| `Stopped` | Thread ka method khatam ho gaya |

> `Task`s ke liye aap `TaskStatus` se sochte ho (`Created`, `WaitingToRun`, `Running`, `RanToCompletion`, `Faulted`, `Canceled`) — underlying threads thread pool ke paas hote hain.

### Code example
```csharp
using System;
using System.Threading;
using System.Threading.Tasks;

class Demo
{
    static async Task Main()
    {
        // 1) Raw Thread with a ThreadStart delegate
        var t = new Thread(() =>
            Console.WriteLine($"Raw thread {Environment.CurrentManagedThreadId}"));
        t.Start();   // Unstarted -> Running; Start() spawns a new OS thread
        t.Join();    // main waits until t finishes (WaitSleepJoin)

        // 2) Task — the idiomatic path (schedules work onto the thread pool)
        Task task = Task.Run(() =>
            Console.WriteLine($"Task on thread {Environment.CurrentManagedThreadId}"));
        await task;

        // 3) Task<T> — returns a value / can surface an exception
        Task<int> job = Task.Run(() => 40 + 2);
        int result = await job;                 // await instead of blocking
        Console.WriteLine($"Task<int> result = {result}"); // 42
    }
}
```
> Note: `Start()` call karo, seedha delegate NAHI. Delegate ko khud call karoge to wo *current* thread pe hi chalega — koi naya thread nahi banega. Zyaadatar kaam ke liye raw `Thread` ki jagah `Task`/`Task<T>` + `async/await` use karo; raw `Thread` sirf long-running ya specialized blocking kaam ke liye rakho.

### Common pitfalls / interview gotchas
- Work delegate ko seedha call karna, `Start()` ki jagah (naya thread hi nahi banta).
- Ye maan lena ki threads stack share karte hain — nahi karte; sirf heap shared hoti hai.
- Concurrency (structure) ko parallelism (execution) se confuse karna. Single core concurrent ho sakta hai par parallel nahi.
- Ye samajhna ki `Running` matlab "abhi execute ho raha hai" — isme "ready, CPU slot ka wait" bhi aata hai.
- Bahut zyada threads → excessive **context switching** overhead (registers save/restore, cache thrash).

### Interview Q&A
- **Q: Process aur thread mein farak?** A: Processes ki memory isolated hoti hai; threads process heap share karte hain par stack alag. Threads banana aur switch karna sasta hai.
- **Q: `Task` vs `Task<T>` (ya `Action` vs `Func<T>`)?** A: `Task`/`Action` bina return value ke kaam chalata hai; `Task<T>`/`Func<T>` value return karta hai aur `await` karne pe exceptions surface karta hai.
- **Q: Concurrency vs parallelism?** A: Concurrency matlab kai tasks ko interleave karke handle karna; parallelism matlab kai tasks ko literally ek saath multiple cores pe chalana.

## 2. Locks & Mutex

### Kya hai?
Jab multiple threads shared data ko chhoote hain, to aapko **mutual exclusion** chahiye — ek time pe sirf ek thread "danger zone" mein. Wo danger zone hi **critical section** hai. Ek **mutex** (MUTual EXclusion lock) wahi mechanism hai jo isko enforce karta hai: thread ko andar jaane se pehle lock *acquire* karna padta hai, aur baad mein *release*. C# mein koi bhi reference object `lock` statement ke through **monitor** ke roop mein use ho sakta hai; aur ek sach ka OS-level (cross-process) mutex ke liye `System.Threading.Mutex` hai.

Socho ek washroom hai jismein sirf ek banda ja sakta hai. Darwaze pe ek taala (mutex) hai. Andar jaane se pehle taala lena padega (acquire), aur nikalne pe taala chhodna padega (release). Jab tak ek banda andar hai, baaki queue mein wait karte hain. Wo "andar ka time" hi **critical section** hai — jahan shared resource (washroom) ko sirf akela use karte ho. C# mein wo taala ek dedicated lock object pe `lock` statement se lete ho.

### Kab use karein / kyun matter karta hai
- Jab bhi do+ threads same mutable state read/write karein aur kam se kam ek write kare.
- Ek compound operation (read-modify-write) ko **atomic** dikhane ke liye.

### Code example
```csharp
class Counter
{
    private int _count = 0;
    private readonly object _lock = new(); // a dedicated lock object

    public void Increment()
    {
        lock (_lock)   // acquire the monitor
        {
            _count++;  // critical section (only one thread here at a time)
        }              // monitor released automatically on block exit
    }

    public int Get()
    {
        lock (_lock) { return _count; }
    }
}
```
> `lock (obj) { ... }` andar se `Monitor.Enter/Monitor.Exit` mein `try/finally` ke saath compile hota hai, isliye exception aane pe bhi lock hamesha release ho jaata hai. In-process mutual exclusion ke liye `lock`/`Monitor` prefer karo; `System.Threading.Mutex` sirf tab jab named, cross-process lock chahiye (wo kaafi heavy hai).

### Common pitfalls / interview gotchas
- Doosre object pe lock lena bजाय usi object ke jispe baaki lock lete hain → koi mutual exclusion nahi.
- `string` literal (interned) ya boxed value type pe lock lena (unexpectedly shared/re-boxed). `private readonly object` use karo.
- Ye bhool jaana ki reads ko bhi lock chahiye **visibility** ke liye, sirf writes ko nahi.
- Slow I/O karte waqt lock hold karna → throughput maar deta hai.

### Interview Q&A
- **Q: Critical section kya hai?** A: Wo code block jo shared resources ko access karta hai aur ek time pe sirf ek thread se execute hona chahiye.
- **Q: Mutex vs semaphore (ek line)?** A: Mutex sirf ek holder allow karta hai (ownership); counting semaphore N permits tak allow karta hai.
- **Q: .NET mein monitor kya hai?** A: Koi bhi object synchronization monitor ban sakta hai; `Monitor` class (`Enter`/`Exit`/`Wait`/`Pulse`) `lock` statement ke andar chalti hai.

## 3. lock statement & Monitor

### Kya hai?
`lock` C# ka built-in construct hai object ka **monitor** acquire karne ke liye (ye `Monitor.Enter`/`Monitor.Exit` mein lower hota hai). C# mein kuch languages jaisa `synchronized` method keyword nahi hai — body ko khud `lock` block mein wrap karna padta hai. Ek **instance** field (`private readonly object _lock`) pe lock lena per-object state protect karta hai; ek **static** object pe lock lena type-wide state protect karta hai (concept mein `typeof(X)` jaisa, par `typeof(X)` seedha use karne ki jagah private static object use karna chahiye). `lock`/`Monitor` **reentrant** hai — jo thread already lock hold kar raha hai wo dobara acquire kar sakta hai bina khud ko deadlock kiye (CLR ek hold count rakhta hai).

`lock` matlab "is code ke andar aane se pehle object ki chaabi lo". Do useful patterns:
- **Poori method body:** sab kuch `lock (_lock)` mein wrap — coarse par simple.
- **Chhota block:** sirf shared state chhoone waali lines ke around `lock (_lock) { ... }` — better performance (chaabi kam der ke liye pakadte ho).

**Object lock vs type lock:** ek instance lock object har object ko apni chaabi deta hai; ek static lock object saare instances ke liye ek common chaabi deta hai.

**Reentrancy:** agar ek locked method usi lock waale doosre method ko call kare, to thread wait nahi karta — chaabi already uske paas hai. CLR ise count karta hai (2 baar liya = 2 baar release karna padega).

### Kab use karein / kyun matter karta hai
- Shared state protect karne ka sabse simple tareeka; koi explicit unlock bhoolne ka darr nahi (block apne aap release karta hai).
- Concurrency maximize karne ke liye **sabse chhota** zaroori region hi lock karo.

### Code example
```csharp
class Account
{
    private int _balance;
    private readonly object _lock = new();

    // Instance-level lock: guard state with a private lock object
    public void Deposit(int amt)
    {
        lock (_lock) { _balance += amt; }
    }

    // Keep the locked region small — do cheap work outside the lock
    public void DepositChecked(int amt)
    {
        Validate(amt);                       // NOT locked — cheap, keep outside
        lock (_lock) { _balance += amt; }
    }

    // Type-level lock: shared across ALL instances
    private static int _totalAccounts;
    private static readonly object _typeLock = new();
    public static void Register()
    {
        lock (_typeLock) { _totalAccounts++; }
    }

    // Reentrancy demo: TransferFrom holds _lock and calls Deposit which
    // re-acquires the SAME lock — allowed because lock is reentrant.
    public void TransferFrom(Account other, int amt)
    {
        lock (_lock)
        {
            other.Withdraw(amt);
            Deposit(amt);                    // re-acquires _lock; no self-deadlock
        }
    }

    public void Withdraw(int amt) { lock (_lock) { _balance -= amt; } }
    private void Validate(int amt) { if (amt < 0) throw new ArgumentException(); }
}
```

### Common pitfalls / interview gotchas
- **Instance lock aur static lock alag monitors hain** — ek instance method ko guard karna doosre lock object se guarded static method ko exclude NAHI karta.
- `this` ya `typeof(T)` pe lock lena aapka lock baahar wale code ko expose kar deta hai (koi bhi usi object/type pe `lock` le sakta hai), deadlock ka risk. `private readonly object` prefer karo.
- Bade regions lock karna concurrency maar deta hai; `lock` block chhota karo.
- `lock` bonus mein memory-visibility guarantee bhi deta hai — ek monitor release karna doosre thread ke acquire karne se *happens-before* hota hai.

### Interview Q&A
- **Q: `this` ya `typeof(T)` ki jagah private object kyun lock karein?** A: `this`/`typeof(T)` lock karna aapka lock callers ko leak kar deta hai, jo phir deadlock create kar sakte hain; private lock object sirf aapki class ko dikhta hai.
- **Q: Kya `lock` reentrant hai?** A: Haan. Thread apne already-held monitor ko dobara acquire kar sakta hai; CLR hold count rakhta hai aur utne hi exits maangta hai.
- **Q: Same object pe alag-alag methods lock karte do threads parallel chalenge?** A: Nahi — dono ko same monitor chahiye, isliye mutually exclusive hain.

## 4. Deadlock, Livelock, Starvation

### Kya hai?
- **Deadlock:** Do ya zyada threads mein se har ek wo lock hold kar raha hai jo doosre ko chahiye, aur hamesha wait karte hain. Koi progress nahi.
- **Livelock:** Threads *active* hain (blocked nahi) par ek doosre ko respond karte rehte hain aur kabhi progress nahi karte — jaise corridor mein do log side to side hilte rehte hain.
- **Starvation:** Ek thread ko kabhi CPU/lock nahi milta kyunki greedier/higher-priority threads baar-baar jeet jaate hain.

Deadlock ke liye **chaaron Coffman conditions** ek saath chahiye:
1. **Mutual exclusion** — resource share nahi ho sakta.
2. **Hold and wait** — ek thread ek resource pakad ke doosre ka wait karta hai.
3. **No preemption** — resource zabardasti chheena nahi ja sakta.
4. **Circular wait** — threads ki ek cycle jahan har ek agle ka wait kar raha hai.

Kisi bhi **ek** condition ko tod do → koi deadlock nahi.

- **Deadlock:** do dost, ek ke paas fork hai doosre ke paas knife. Dono kehte hain "pehle tu de", koi nahi deta — dono bhookhe baithe rahenge, hamesha.
- **Livelock:** corridor mein do log aamne-saamne, dono ek saath left jaate, phir dono right — politely hilte reh jaate hain par kabhi cross nahi karte. Busy dikh rahe hain par kaam zero.
- **Starvation:** ticket window pe ek aggressive banda baar-baar aage ghus jaata hai; peeche wala garib kabhi turn nahi paata.

### Kab use karein / kyun matter karta hai
- Prevention (sirf detection nahi) top interview theme hai. Go-to fixes hain **global lock ordering** (circular wait todta hai) aur **`Monitor.TryEnter` with timeout** (hold-and-wait / no-preemption todta hai).

### Code example
```csharp
using System.Runtime.CompilerServices;
using System.Threading;

// DEADLOCK: thread A locks a then b; thread B locks b then a
void DeadlockProne(object a, object b)
{
    lock (a)
    {
        lock (b) { /* ... */ }
    }
}

// FIX 1 — Lock ordering: ALWAYS acquire in a fixed global order (by identity hash)
void SafeTransfer(Account x, Account y, int amt)
{
    Account first  = RuntimeHelpers.GetHashCode(x) < RuntimeHelpers.GetHashCode(y) ? x : y;
    Account second = ReferenceEquals(first, x) ? y : x;
    lock (first)
    {
        lock (second) { x.Withdraw(amt); y.Deposit(amt); }
    }
}

// FIX 2 — Monitor.TryEnter with timeout: back off if you can't get both
bool Transfer(object l1, object l2)
{
    if (Monitor.TryEnter(l1, TimeSpan.FromSeconds(1)))
    {
        try
        {
            if (Monitor.TryEnter(l2, TimeSpan.FromSeconds(1)))
            {
                try { /* do work */ return true; }
                finally { Monitor.Exit(l2); }
            }
        }
        finally { Monitor.Exit(l1); }
    }
    return false; // couldn't get both — retry / abort, no deadlock
}
```
> `async` code mein sabse common deadlock tab aata hai jab aap `.Result`/`.Wait()` pe block karte ho jabki ek captured `SynchronizationContext` (jaise classic ASP.NET ya UI thread) continuation ka wait kar raha hota hai. Fix: neeche tak `await` karo, ya `ConfigureAwait(false)` use karo.

### Common pitfalls / interview gotchas
- Nested `lock`s inconsistent order mein lena #1 deadlock cause hai.
- Livelock: naive "agar lock nahi mila to sab release karke turant retry" hamesha ke liye loop kar sakta hai — randomized backoff daalo.
- .NET ka `lock`/`Monitor` **fair nahi** hai — koi built-in fairness ya priority option nahi, isliye heavy contention pe starvation possible hai.
- Runtime pe deadlock detect karna: ek dump lo (`dotnet-dump`, Visual Studio "Parallel Stacks") aur dekho kaunse threads kaunse locks own/await kar rahe hain.

### Interview Q&A
- **Q: 4 Coffman conditions batao.** A: Mutual exclusion, hold-and-wait, no-preemption, circular wait — deadlock ke liye chaaron chahiye.
- **Q: Deadlock kaise prevent karte ho?** A: Ek condition todo — practically, global lock ordering impose karo (circular wait khatam) ya `Monitor.TryEnter` with timeout use karo (hold-and-wait khatam).
- **Q: Deadlock vs livelock?** A: Deadlock mein threads blocked aur idle hote hain; livelock mein wo chal rahe hain aur state badal rahe hain par phir bhi koi progress nahi.

## 5. Race Conditions

### Kya hai?
Ek **race condition** tab hoti hai jab result ki correctness threads ke *timing/interleaving* pe depend karti hai. Classic culprits:
- **Read-modify-write:** `count++` asal mein *read count → add 1 → write back* hai. Do threads dono same purani value read kar sakte hain aur ek increment gayab.
- **Check-then-act:** `if (!dict.ContainsKey(k)) dict.Add(k, v);` — doosra thread check aur act ke beech mein ghus sakta hai.

Do alag hazards races ko feed karte hain:
- **Atomicity** — compound operation all-or-nothing hona chahiye.
- **Visibility** — ek thread ki write doosre ko dikhni chahiye (dekho topic 9, `volatile`).

Race condition matlab result is baat pe depend karta hai ki kaunsa thread pehle pahuncha — jaise do log same seat pe race laga rahe hain. `count++` dekhne mein ek line hai par CPU ke liye teen steps hain: padho, badhao, wapas likho. Do threads dono ne 5 padha, dono ne 6 likha — ek increment gayab! Data ki value corrupt.

**Check-then-act** example: bank mein balance check kiya "1000 hai", withdraw karne laga; usi beech doosre thread ne bhi 1000 dekh ke withdraw kar diya — dono nikal le gaye, account negative. Fix: check aur act ko ek hi lock ke andar atomic bana do.

### Kab use karein / kyun matter karta hai
- Races *intermittent* bugs deti hain jo dev mein pass hote hain aur prod mein load pe phatt jaate hain — sabse darawni category.
- Fix: compound op ko atomic banao (`lock`, ya `Interlocked`/CAS) aur visibility ensure karo.

### Code example
```csharp
using System.Collections.Concurrent;
using System.Threading;

class Unsafe
{
    public int Count;
    public void Inc() { Count++; }          // RACE: read-modify-write not atomic
}

class SafeLock
{
    private int _count;
    private readonly object _lock = new();
    public void Inc() { lock (_lock) { _count++; } }   // atomic + visible via monitor
}

class SafeAtomic
{
    private int _count;
    public void Inc() => Interlocked.Increment(ref _count); // lock-free atomic (CAS)
}

// check-then-act fix using an atomic dictionary operation
var m = new ConcurrentDictionary<string, int>();
m.TryAdd("k", 1);            // single atomic step, no gap between check and act
m.GetOrAdd("k", _ => 1);     // atomically get existing or create
```

### Common pitfalls / interview gotchas
- Ye maan lena ki `count++` ya `x = x + 1` atomic hai — nahi hai.
- Atomicity fix kar dena par visibility bhool jaana (ya ulta). `volatile` visibility deta hai par `++` ke liye atomicity NAHI.
- Ek property/getter mein `if (instance == null) instance = new X();` — classic check-then-act race (`Lazy<T>` prefer karo; dekho topic 9).
- Multiple threads se plain `Dictionary<,>` use karna → internal state corrupt / throw kar sakta hai; `ConcurrentDictionary<,>` use karo.

### Interview Q&A
- **Q: `count++` thread-safe kyun nahi?** A: Ye teen steps ka read-modify-write hai; interleaving updates lose kar sakti hai (lost-update problem).
- **Q: Atomicity vs visibility?** A: Atomicity = poora operation indivisible; visibility = ek thread ki write doosre ko dikhe. Aksar dono chahiye.
- **Q: Ek check-then-act bug aur uska fix do.** A: `if (!dict.ContainsKey(k)) dict.Add(k, v)` race karta hai; fix `ConcurrentDictionary.TryAdd`/`GetOrAdd` ya dono steps ke around ek lock.

## 6. Semaphores

### Kya hai?
Ek **semaphore** **permits** ka set maintain karta hai. `Wait()`/`WaitAsync()` ek permit leta hai (agar koi na bache to block); `Release()` ek wapas karta hai. Ek **counting semaphore** *N* tak concurrent holders allow karta hai — N resources ke pool ka access limit karne ya **rate limiting** ke liye perfect. Ek **binary semaphore** (N=1) lock jaisa behave karta hai, par mutex ke ulat isme **koi ownership nahi** — koi bhi thread ise release kar sakta hai. C# mein fast in-process gating (async support ke saath) ke liye `SemaphoreSlim` use karo aur named, system-wide semaphore ke liye `System.Threading.Semaphore`.

Semaphore ek parking lot ke gate jaisa hai jismein 3 tokens hain (3 parking spots). Andar jaane ke liye ek token lo (`Wait`) — token khatam to gate pe wait karo. Nikalte waqt token wapas daal do (`Release`) taaki agla aa sake. **Counting semaphore** = N tokens (kai gaadi ek saath). **Binary semaphore** = sirf 1 token (lock jaisa), lekin fark ye hai ki mutex mein "jisne lock liya wahi khol sakta hai", semaphore mein koi bhi token wapas daal sakta hai — ownership nahi hoti.

### Kab use karein / kyun matter karta hai
- **Resource pools** (DB connections, licenses) — concurrent users ko N pe cap karo.
- **Rate limiting / throttling** — ek time pe sirf N calls in flight.
- Threads ke beech signaling (permits ko signal ki tarah).

### Code example
```csharp
using System;
using System.Threading;
using System.Threading.Tasks;

// Allow at most 3 threads to use the "service" concurrently
var sem = new SemaphoreSlim(3);              // 3 permits

async Task UseServiceAsync()
{
    await sem.WaitAsync();                    // take a permit (async; blocks if 0 left)
    try
    {
        await CallExternalApiAsync();         // at most 3 callers here at once
    }
    finally
    {
        sem.Release();                        // ALWAYS release in finally
    }
}

// WaitAsync with a timeout for throttling without waiting forever
if (await sem.WaitAsync(TimeSpan.FromMilliseconds(500)))
{
    try { await DoWorkAsync(); } finally { sem.Release(); }
}
else
{
    // rejected / back-pressure
}
```
> `SemaphoreSlim` in-process aur async-friendly hai (`WaitAsync`). `new Semaphore(3, 3)` (ya named `Semaphore`) sirf tab jab system-wide, cross-process limit chahiye. Dono mein fairness/FIFO ki guarantee nahi hai.

### Common pitfalls / interview gotchas
- `finally` mein `Release()` bhool jaana → permits leak, pool aakhir mein starve ho jaata hai.
- Acquire se zyada baar `Release()` call karna → max count cross karte hi `SemaphoreSlim.Release` `SemaphoreFullException` throw karta hai (kuch implementations chupchaap badh jaate hain, ye nahi).
- Binary semaphore wahan use karna jahan reentrancy chahiye — semaphores reentrant NAHI hain; same thread se dobara acquire self-deadlock kar sakta hai.
- FIFO order maan lena — `SemaphoreSlim` iski guarantee nahi deta.

### Interview Q&A
- **Q: Counting vs binary semaphore?** A: Counting N permits tak allow karta hai; binary ke paas 1 hota hai (lock jaisa).
- **Q: Semaphore vs mutex?** A: Mutex mein ownership hoti hai (jisne lock liya wahi khole) aur `lock` reentrant hai; semaphore ek permit counter hai bina ownership ke aur koi bhi thread release kar sakta hai.
- **Q: Ek real use case?** A: Resource pool ke concurrent connections limit karna, ya downstream API pe calls throttle karna.

## 7. Condition signaling: Monitor.Wait / Pulse

### Kya hai?
`Monitor.Wait`, `Monitor.Pulse`, aur `Monitor.PulseAll` object ke monitor ka use karke threads ke beech **condition-based coordination** dete hain. Ek thread `Monitor.Wait(gate)` call karke **lock release karta hai** aur object ki **wait queue** mein so jaata hai, jab tak doosra thread usi object pe `Monitor.Pulse(gate)` (ek jagata hai) ya `Monitor.PulseAll(gate)` (sab jagata hai) na kare. Teeno ko **us object ka monitor hold karte hue hi** call karna hai (`lock` ke andar), warna `SynchronizationLockException` milta hai. Hamesha ek condition check karte hue **loop mein wait karo** kyunki **spurious wakeups** hoti hain aur lock dobara milte-milte condition badal sakti hai.

Socho ek waiter–kitchen signaling system. Waiter (`consumer`) counter pe aata hai; dish ready nahi hai to `Monitor.Wait` call karta hai — *chaabi chhod ke* so jaata hai taaki cook kaam kar sake. Cook (`producer`) dish bana ke `Monitor.Pulse` maar ke ek waiter jagata hai, ya `Monitor.PulseAll` se sab ko.

Teen golden rules:
1. Inhe **sirf `lock` ke andar** call karo, warna `SynchronizationLockException`.
2. Condition hamesha **`while` loop** mein check karo, `if` nahi — thread bina signal ke bhi jag sakta hai (**spurious wakeup**), aur jag ke dekha to shayad kisi aur ne item le liya.
3. `Monitor.Pulse` = ek jagao (kaunsa, pata nahi); `Monitor.PulseAll` = sab jagao (safe default).

### Kab use karein / kyun matter karta hai
- Blocking queues, producer-consumer, aur bounded buffers khud haath se banane ke liye.
- Classic interview topic aur higher-level signaling primitives samajhne ki foundation.

### Code example
```csharp
using System.Collections.Generic;
using System.Threading;

// Wait/Pulse: all three MUST be called inside lock(_gate) — you must own the monitor.
class BoundedBuffer<T>
{
    private readonly Queue<T> _q = new();
    private readonly object _gate = new();
    private readonly int _cap;
    public BoundedBuffer(int cap) => _cap = cap;

    public void Put(T item)
    {
        lock (_gate)
        {
            while (_q.Count == _cap) Monitor.Wait(_gate); // WHILE, not if (spurious wakeups)
            _q.Enqueue(item);
            Monitor.PulseAll(_gate);                       // wake waiting consumers
        }
    }

    public T Take()
    {
        lock (_gate)
        {
            while (_q.Count == 0) Monitor.Wait(_gate);     // release lock & sleep until pulsed
            var item = _q.Dequeue();
            Monitor.PulseAll(_gate);                        // wake waiting producers
            return item;
        }
    }
}
```
`Monitor.Pulse` ek waiter ko jagata hai; `Monitor.PulseAll` sab ko.

**Modern C# mein higher-level constructs prefer karo:** `Monitor.Wait/Pulse` aap shaayad hi khud likhoge. `SemaphoreSlim` (async-friendly gating/counting), `ManualResetEventSlim` / `AutoResetEvent` (one-shot ya gated signals), `TaskCompletionSource<T>` (result ready hone pe ek `Task` complete karo), `System.Threading.Channels` (bounded/unbounded producer-consumer with back-pressure), aur plain `async/await` use karo. Ye waiting/signaling andar se sahi handle karte hain aur async code ke saath compose hote hain.

### Common pitfalls / interview gotchas
- `Wait`/`Pulse` ko `lock` ke **bahar** call karna → `SynchronizationLockException`.
- Condition ke liye `if` istemaal karna `while` ki jagah → spurious wakeups aur multi-consumer races pe toot jaata hai.
- Jab ek hi monitor pe multiple alag conditions ho to `Pulse` use karna → "galat" thread jag sakta hai aur atak sakta hai; `PulseAll` prefer karo (ya har condition ke liye alag signaling primitive).
- `Monitor.Wait` sirf *is* object ka monitor release karta hai, aapke doosre held locks nahi.
- `Monitor.Wait` (lock release karta hai) ko `Thread.Sleep` (lock release NAHI karta) se confuse karna.

### Interview Q&A
- **Q: `Wait`/`Pulse` `lock` ke andar kyun hone chahiye?** A: Ye object ke monitor pe kaam karte hain; aapko usko own karna padta hai, aur wo lost wakeups avoid karne wala atomic check-then-wait enforce karta hai.
- **Q: `Pulse` vs `PulseAll`?** A: `Pulse` ek arbitrary waiter jagata hai; `PulseAll` sab ko. Jab alag threads alag conditions pe wait karte hon to `PulseAll` use karo taaki koi atka na rahe.
- **Q: Condition pe loop kyun?** A: Spurious wakeups, aur ye ki lock dobara milne se pehle koi doosra thread condition invalidate kar sakta hai.

## 8. Thread Pools & Task Parallel Library (TPL)

### Kya hai?
Har task ke liye naya thread banana mehenga hai (memory, OS scheduling) aur unbounded (resources khatam kar sakta hai). Ek **thread pool** ek fixed set of worker threads reuse karta hai jo queue se bahut saare tasks chalate hain. .NET ek managed `ThreadPool` ship karta hai, aur **Task Parallel Library (TPL)** — `Task`, `Task.Run`, `Task.WhenAll`, `Parallel.ForEach` — uske upar baithti hai, isliye aap *kaam* submit karte ho, threads nahi.

Ek thread pool ke key knobs (concept — har jagah same):
- **minimum threads** — worker threads jo idle hone pe bhi ready rehte hain (`ThreadPool.SetMinThreads`).
- **maximum threads** — worker threads ki ceiling (`ThreadPool.SetMaxThreads`).
- **work queue** — jahan queued kaam wait karta hai jab tak worker na uthaye.
- **idle management** — pool time ke saath extra idle threads trim karta hai.
- **injection heuristic** — .NET live thread count ko ek hill-climbing algorithm se auto-tune karta hai; minimum cross hone ke baad naye threads dheere daalta hai (roughly ek-do per second).

Har task ke liye naya thread banana aise hai jaise har customer ke liye naya waiter hire karna — mehenga aur pagalpan. Thread pool matlab fixed number of workers jo ek queue se tasks uthate rehte hain — ek khatam, agla uthao, reuse.

### Kab use karein / kyun matter karta hai
- Lagbhag har real server pool use karta hai. Sizing aur back-pressure behavior prime SDE-2 questions hain.
- Bounded producer-consumer pipelines ke liye raw pool khud size karne ki jagah `System.Threading.Channels` ya TPL Dataflow prefer karo; wo back-pressure aur saaf async composition dete hain.

### Code example
```csharp
using System.Linq;
using System.Threading;
using System.Threading.Tasks;

// 1) Managed thread pool directly (fire-and-forget)
ThreadPool.QueueUserWorkItem(_ => DoWork());

// 2) TPL — the idiomatic path: Task.Run schedules the work onto the thread pool
Task<int> t = Task.Run(() => 40 + 2);
int result = await t;                        // 42 (no thread is blocked while awaiting)

// 3) Fan-out, then join
var tasks = urls.Select(u => Task.Run(() => Fetch(u)));
string[] pages = await Task.WhenAll(tasks);  // run in parallel, await all

// 4) Data parallelism over a collection (partitions across pool threads)
Parallel.ForEach(items, item => Process(item));

// 5) Tune the pool floor to cut ramp-up latency for bursty load
ThreadPool.SetMinThreads(workerThreads: 50, completionPortThreads: 50);
```
`async/await` bhi apni continuations by default thread pool pe hi chalata hai, isliye aap shaayad hi seedha threads ko chhoote ho. Jo kaam lambe time ke liye block karega, uske liye pool worker ko rokne ki jagah ek dedicated thread banao (ya `Task.Factory.StartNew(..., TaskCreationOptions.LongRunning)`).

### Common pitfalls / interview gotchas
- **Thread-pool starvation:** ek pool thread ko block karna (`.Result`, `.Wait()`, `Thread.Sleep`, sync-over-async) ek worker ko baandh deta hai; kyunki pool naye threads dheere daalta hai, load pe throughput gir jaata hai. End-to-end async raho.
- Ek `Task` ki exceptions **capture** hoti hain aur jab aap `await` karo ya `.Result` padho tab rethrow hoti hain; ek un-awaited task ki exception unobserved reh sakti hai. Hamesha apne tasks await (ya observe) karo.
- Naturally-async I/O ko `Task.Run` mein wrap karna ek pool thread waste karta hai — bas async API ko seedha `await` karo.
- Unbounded fan-out (millions tasks queue karna) memory/scheduler pressure deta hai — `SemaphoreSlim`, `Parallel.ForEachAsync` ka `MaxDegreeOfParallelism`, ya `Channels` se throttle karo.

### Interview Q&A
- **Q: `Task.Run` vs `new Thread`?** A: `Task.Run` shared pool pe schedule karta hai (reused workers, sasta, short CPU-bound kaam ke liye achha); `new Thread` ek dedicated OS thread banata hai (mehenga — ise long-running ya blocking kaam ke liye rakho).
- **Q: `Task.WhenAll` vs `Task.WaitAll`?** A: `WhenAll` ek `Task` return karta hai jise aap `await` karo (non-blocking, async ke saath compose); `WaitAll` calling thread ko block karta hai jab tak sab complete na ho.
- **Q: .NET thread pool apni size kaise manage karta hai?** A: Wo ek configurable minimum rakhta hai (`SetMinThreads`), queue se kaam serve karta hai, aur hill-climbing heuristic se max tak workers add/remove karta hai; pool threads block karne se starvation aur slow injection hoti hai.

## 9. volatile keyword

### Kya hai?
.NET memory model ke andar ek thread ek field ko register/CPU cache mein cache kar sakta hai, aur compiler/JIT/CPU instructions reorder kar sakte hain. To ek thread ki write doosre ko **kabhi visible hi nahi** ho sakti. Ek field ko `volatile` mark karna (ya `Volatile.Read`/`Volatile.Write` methods use karna) deta hai:
- **Visibility** — ek volatile read hamesha latest write dekhta hai; reads/writes cache mein nahi rakhe jaate.
- **Ordering (acquire/release)** — ek volatile write ke paas release semantics aur ek volatile read ke paas acquire semantics hote hain, jo iske aar-paar kuch reorderings rokte hain.

`volatile` jo **NAHI** deta: compound operations ki **atomicity**. `volatile int x; x++;` phir bhi ek race hai (read-modify-write).

Har thread ke paas apni chhoti notebook (CPU cache) hoti hai jisme wo values copy kar leta hai speed ke liye. Problem: Thread A ne main memory mein `flag = true` kiya, par Thread B apni purani notebook (`flag == false`) dekhta reh gaya — infinite loop. `volatile` bolta hai "is variable ko notebook mein cache mat karo, hamesha main blackboard (main memory) se padho/likho". Isse **visibility** guaranteed, aur kuch **ordering** bhi.

Par dhyaan: `volatile` sirf visibility deta hai, **atomicity nahi**. `count++` phir bhi race karega kyunki wo teen steps hai. Flags ke liye perfect, counters ke liye `Interlocked` chahiye.

### Kab use karein / kyun matter karta hai
- **Stop/ready flags** jo threads ke beech shared ho: `private volatile bool _running`.
- Ek writer, kai readers ek single value ke (ek reference safely publish karna).
- Historically, hand-rolled double-checked-locking singleton ka field `volatile` hona chahiye tha — par C# mein ise khud likhne ki jagah `Lazy<T>` prefer karo.

### Code example
```csharp
using System;
using System.Threading;

class Worker
{
    private volatile bool _running = true;   // visibility across threads
    public void Run()
    {
        while (_running) { DoWork(); }        // sees Stop() promptly
    }
    public void Stop() { _running = false; }  // visible to the running thread
}

// volatile does NOT make ++ atomic:
//   volatile int count;  ->  count++ is STILL a race; use Interlocked.

// Volatile.Read/Write give explicit acquire/release without the field modifier
int flag = 0;
Volatile.Write(ref flag, 1);
int seen = Volatile.Read(ref flag);

// Thread-safe lazy singleton — prefer Lazy<T> over hand-rolled double-checked locking
class Singleton
{
    private static readonly Lazy<Singleton> _instance =
        new(() => new Singleton(), LazyThreadSafetyMode.ExecutionAndPublication);
    public static Singleton Instance => _instance.Value;
    private Singleton() { }
}
```
> .NET aur Java ke memory models detail mein alag hain, par practical rule same hai: `volatile`/`Volatile` ek single field ke liye visibility aur ordering dete hain; compound operations ko phir bhi `Interlocked` ya `lock` chahiye. `Lazy<T>` hand-rolled double-checked locking ko replace karta hai.

### Common pitfalls / interview gotchas
- Ye samajhna ki `volatile` `++`/compound ops ko atomic banata hai — nahi banata.
- Ek reference pe `volatile` lagana *reference* ko visible banata hai, object ke mutable internals ko nahi.
- `Lazy<T>` ki jagah hand-rolled double-checked locking use karna — ordering galat karna aasaan hai.
- `volatile` lock se sasta hai par mutual-exclusion tool NAHI hai.

### Interview Q&A
- **Q: `volatile` kya guarantee karta hai?** A: Visibility (hamesha latest value read/write) aur acquire/release ordering; atomicity nahi.
- **Q: C# mein thread-safe lazy singleton kaise banate ho?** A: `LazyThreadSafetyMode.ExecutionAndPublication` ke saath `Lazy<T>` use karo; wo ordering/visibility sahi handle karta hai to aapko double-checked locking khud nahi likhni padti.
- **Q: `volatile` vs `lock`?** A: `volatile` ek single field ke liye visibility/ordering deta hai bina mutual exclusion ke; `lock` poore critical section ke liye mutual exclusion + visibility deta hai.

## 10. Atomic operations with Interlocked

### Kya hai?
`System.Threading.Interlocked` class ek single variable pe **lock-free**, thread-safe operations deti hai CPU ke **CAS (Compare-And-Swap)** instruction ka use karke. `Interlocked.CompareExchange(ref x, newValue, expected)` kehta hai: "`x` ko *newValue* set karo sirf tab jab wo abhi *expected* ke barabar ho; original value return karo." Lock-free algorithms `CompareExchange` pe loop karte hain jab tak succeed na ho, jo bina blocking ke atomic increments/updates deta hai — moderate contention pe aksar locks se tez.

**ABA problem:** CAS sirf value check karta hai, ye nahi ki beech mein A→B→A change hua ki nahi. Agar A→B→A matter kare (jaise lock-free stacks/pointers), to value ke saath ek version counter pair karo taaki CAS version change bhi dekhe. .NET mein built-in "stamped reference" nahi hai; aap khud banate ho (jaise ek value+version struct jo `CompareExchange` se swap ho).

`Interlocked.Increment` ek aisa counter hai jo bina taala lagaye safely badhta hai. Andar CAS ek loop chalata hai: "main samajh raha tha value 5 hai; agar ab bhi 5 hai to 6 kar do, warna batao aur main dobara try karta hoon." Ye retry-loop chalta rehta hai jab tak set na ho jaye. Kyunki koi lock nahi, ye tez hai aur deadlock ka risk nahi (**lock-free**).

**ABA problem:** maano value 5 thi, kisi ne 5→10→5 kiya. CAS ko lagega "arre 5 hi to hai, kuch badla nahi" — halaanki beech mein change hua tha. Agar ye matter kare to ek version number attach karo (5 with stamp 1 vs 5 with stamp 3).

### Kab use karein / kyun matter karta hai
- High-throughput counters, sequence generators, statistics, flags, aur lock-free data structures.
- Jab ek single variable ko atomic updates chahiye aur aap lock overhead/contention avoid karna chahte ho.

### Code example
```csharp
using System.Threading;

int counter = 0;

Interlocked.Increment(ref counter);          // atomic ++ (returns new value)
Interlocked.Decrement(ref counter);          // atomic --
Interlocked.Add(ref counter, 5);             // atomic += 5
int old = Interlocked.Exchange(ref counter, 100); // atomic set, returns previous value

// CompareExchange == CAS: set to 100 only if it currently equals 6
Interlocked.CompareExchange(ref counter, value: 100, comparand: 6);

// Atomic update of a reference
string? reference = "A";
Interlocked.CompareExchange(ref reference, "B", "A"); // CAS on a reference

// Manual CAS loop (how a lock-free update is built; the lambda-free equivalent
// of "read current, compute next, publish if unchanged, else retry")
int prev, next;
do
{
    prev = counter;
    next = prev * 2;
} while (Interlocked.CompareExchange(ref counter, next, prev) != prev);
```

### Common pitfalls / interview gotchas
- **Bahut high contention** pe CAS retry loops CPU waste kar sakte hain (livelock-ish); ek `lock` jeet sakta hai. Benchmark karo.
- Manual CAS loop mein "compute next" step **side-effect free** hona chahiye — retry pe wo kai baar chal sakta hai.
- `Interlocked` ek *single* variable cover karta hai. Do variables jointly update NAHI hote — aapko phir bhi ek `lock` chahiye ya ek immutable composite object ke reference pe ek single `CompareExchange`.
- Lock-free stacks/pointers mein ABA problem ignore karna.

### Interview Q&A
- **Q: CAS kya hai?** A: Compare-And-Swap — ek atomic CPU op jo value ko tabhi update karta hai jab wo abhi bhi expected ke barabar ho, original return karta hai; lock-free algorithms ki basis. `Interlocked.CompareExchange` ise expose karta hai.
- **Q: `Interlocked` vs `lock`ed counter?** A: `Interlocked` lock-free hai (CAS retry), moderate contention pe aksar tez, aur deadlock nahi kar sakta; ek `lock` threads block karta hai aur zyada overhead hai par compound state ke liye simpler.
- **Q: ABA problem kya hai?** A: Ek value A→B→A badalti hai, to CAS galti se sochta hai kuch nahi badla. Fix: value ke saath ek version counter attach karo.

## 11. lock reentrancy & ReaderWriterLockSlim

### Kya hai?
C# mein `lock`/`Monitor` **reentrant** hai — jo thread already lock hold kar raha hai wo bina deadlock ke dobara enter kar sakta hai, aur CLR ek per-thread hold count rakhta hai (2 baar liya = 2 baar exit karna). Ek non-blocking ya timed attempt ke liye `Monitor.TryEnter` (optional timeout ke saath) use karo. Note: C# kuch languages ke explicit lock types jaisa built-in fair ya interruptible lock ship NAHI karta; un semantics ke liye aap `SemaphoreSlim`/events pe build karte ho. Condition variables ke liye `Monitor.Wait/Pulse` (per monitor ek single wait-set) ya har condition ke liye ek dedicated `SemaphoreSlim`/`ManualResetEventSlim` use karo.

`ReaderWriterLockSlim` ke do modes hain: kai threads ek saath **read lock** hold kar sakte hain, par **write lock** exclusive hai (na readers, na doosra writer). Isme ek **upgradeable read lock** bhi hai — aap shared lock ke andar decide karte ho aur zaroorat ho tabhi write lock pe upgrade karte ho. Read-heavy data ke liye zabardast.

`Monitor.TryEnter` matlab "taala mil raha hai? nahi? theek hai main wait nahi karta" — deadlock se bachne ka best tareeka. Reentrancy matlab ek locked method usi lock waale doosre method ko call kar sakta hai bina khud ko block kiye. Aur `ReaderWriterLockSlim` ek library jaisa hai: padhne wale jitne chaaho ek saath aa sakte hain, par likhne wala aaye to sab ko bahar — exclusive access. Read-heavy data ke liye zabardast performance.

Trade-off: `lock` apne block ke end pe apne aap release ho jaata hai, par `Monitor.TryEnter` / `ReaderWriterLockSlim` ke saath aapko `finally` mein **khud release karna** padta hai, warna lock hamesha ke liye held reh jaata hai.

### Kab use karein / kyun matter karta hai
- Timeout ya try-lock chahiye → `Monitor.TryEnter`.
- Read-mostly shared structure (caches, config) → concurrent reads ke liye `ReaderWriterLockSlim`.

### Code example
```csharp
using System;
using System.Collections.Generic;
using System.Threading;

// lock is reentrant — the CLR keeps a per-thread hold count
class ReentrantDemo
{
    private readonly object _lock = new();
    public void Outer()
    {
        lock (_lock)
        {
            Inner();            // re-acquires the SAME lock — allowed
        }
    }
    private void Inner()
    {
        lock (_lock) { /* critical section */ }
    }
}

// Monitor.TryEnter for try-lock with timeout
void TryLockDemo(object gate)
{
    bool taken = false;
    try
    {
        Monitor.TryEnter(gate, TimeSpan.FromSeconds(1), ref taken);
        if (taken) { /* critical section */ }
        // else: couldn't get it in time — back off / retry
    }
    finally
    {
        if (taken) Monitor.Exit(gate); // MUST release what you took
    }
}

// ReaderWriterLockSlim: many readers, one writer, plus upgradeable read
class Cache
{
    private readonly ReaderWriterLockSlim _rw = new();
    private readonly Dictionary<string, string> _map = new();

    public string? Read(string k)
    {
        _rw.EnterReadLock();
        try { return _map.TryGetValue(k, out var v) ? v : null; }
        finally { _rw.ExitReadLock(); }
    }

    public void Write(string k, string v)
    {
        _rw.EnterWriteLock();
        try { _map[k] = v; }
        finally { _rw.ExitWriteLock(); }
    }

    // Upgradeable read: check under a shared lock, upgrade to write only if needed
    public string GetOrAdd(string k, Func<string> factory)
    {
        _rw.EnterUpgradeableReadLock();
        try
        {
            if (_map.TryGetValue(k, out var v)) return v;
            _rw.EnterWriteLock();
            try { var nv = factory(); _map[k] = nv; return nv; }
            finally { _rw.ExitWriteLock(); }
        }
        finally { _rw.ExitUpgradeableReadLock(); }
    }
}
```
> Conditions `Monitor.Wait/Pulse` pe map hoti hain (per monitor ek wait-set). Agar ek lock pe multiple independent wait-sets chahiye, to ek monitor ki jagah har condition ke liye alag `SemaphoreSlim`/`ManualResetEventSlim` use karo.

### Common pitfalls / interview gotchas
- `finally` mein `Exit`/`ExitReadLock`/`ExitWriteLock` bhool jaana → permanent lock / deadlock.
- Enters aur exits balance na karna (dono `Monitor` aur `ReaderWriterLockSlim` hold count track karte hain).
- `ReaderWriterLockSlim` **by default reentrant nahi** (`LockRecursionPolicy.NoRecursion`) — same lock dobara enter karne pe `LockRecursionException` throw hota hai. Reentrant `lock` se migrate karne walon ko ye surprise karta hai.
- Write-starvation: readers ki continuous stream writers ko starve kar sakti hai.
- Aap plain read lock hold karke seedha write lock nahi le sakte (deadlock); us pattern ke liye `EnterUpgradeableReadLock` use karo.

### Interview Q&A
- **Q: `lock`/`Monitor` vs ek explicit lock type?** A: `lock` reentrant hai aur auto-release hota hai; timed/try acquire ke liye `Monitor.TryEnter`. .NET ke paas built-in fair ya interruptible lock nahi — unhe `SemaphoreSlim`/events pe banate ho.
- **Q: `ReaderWriterLockSlim` kab?** A: Read-heavy, write-rare shared data — kai readers concurrently chalte hain jabki writes exclusive rehte hain.
- **Q: `finally` mein release kyun?** A: Taaki critical section throw kare tab bhi release guarantee ho, ek stuck lock se bachne ke liye.
- **Q: Kya `ReaderWriterLockSlim` reentrant hai?** A: Default mein nahi; dobara enter karne pe `LockRecursionException` throw hota hai jab tak aap `LockRecursionPolicy.SupportsRecursion` opt-in na karo.

## 12. Producer-Consumer Pattern

### Kya hai?
Ek coordination pattern jahan **producer** threads items banate hain aur **consumer** threads unhe process karte hain, ek shared **bounded buffer/queue** se decoupled. Ye speed mismatches smooth karta hai. Jab buffer **full** ho, producers wait karte hain (**back-pressure**); jab **empty** ho, consumers wait karte hain. Aap ise `Monitor.Wait/Pulse` se haath se bana sakte ho, par idiomatic C# solutions hain `BlockingCollection<T>` (classic, blocking) aur `System.Threading.Channels` (modern, async) — dono saara waiting andar handle karte hain.

**Back-pressure:** ek full bounded buffer producers ko slow hone pe majboor karta hai — producers consumers se aage nikal jaayein tab unbounded memory growth rokne ke liye critical.

Ek kitchen socho: **cooks (producers)** dishes bana ke ek counter (buffer) pe rakhte hain; **waiters (consumers)** counter se utha ke serve karte hain. Counter ki jagah limited (bounded) hai:
- Counter **full** ho gaya → cooks ruk jaate hain → yahi **back-pressure** hai (warna dishes zameen pe gir jaayengi = memory blowup).
- Counter **khaali** → waiters wait karte hain naye dish ka.

Isse dono apni speed pe kaam karte hain, ek doosre pe seedha depend nahi.

### Kab use karein / kyun matter karta hai
- Task pipelines, message processing, work queues, batching, log processing.
- Interviewers aapse ise dono tareeke se implement karwate hain (haath se AND built-in queue se) aur back-pressure explain karwate hain.

### Code example

**Classic hand-rolled with Monitor.Wait/Pulse:**
```csharp
using System.Collections.Generic;
using System.Threading;

class WaitPulsePC<T>
{
    private readonly Queue<T> _buf = new();
    private readonly object _gate = new();
    private readonly int _cap;
    public WaitPulsePC(int cap) => _cap = cap;

    public void Produce(T item)
    {
        lock (_gate)
        {
            while (_buf.Count == _cap) Monitor.Wait(_gate); // full -> back-pressure
            _buf.Enqueue(item);
            Monitor.PulseAll(_gate);                         // wake consumers
        }
    }

    public T Consume()
    {
        lock (_gate)
        {
            while (_buf.Count == 0) Monitor.Wait(_gate);     // empty -> wait
            var item = _buf.Dequeue();
            Monitor.PulseAll(_gate);                          // wake producers
            return item;
        }
    }
}
```

**Idiomatic BlockingCollection (blocking):**
```csharp
using System.Collections.Concurrent;
using System.Threading.Tasks;

var queue = new BlockingCollection<int>(boundedCapacity: 10); // bounded => back-pressure

// Producer
var producer = Task.Run(() =>
{
    for (int i = 0; i < 100; i++) queue.Add(i);   // blocks if full
    queue.CompleteAdding();                        // signal: no more items
});

// Consumer
var consumer = Task.Run(() =>
{
    foreach (var item in queue.GetConsumingEnumerable()) // blocks if empty; ends on CompleteAdding
        Process(item);
});

await Task.WhenAll(producer, consumer);
```

**Modern Channels (async, preferred):**
```csharp
using System.Threading.Channels;
using System.Threading.Tasks;

var channel = Channel.CreateBounded<int>(10); // bounded => back-pressure

// Producer
var producer = Task.Run(async () =>
{
    for (int i = 0; i < 100; i++)
        await channel.Writer.WriteAsync(i);      // awaits (back-pressure) if full
    channel.Writer.Complete();                    // signal: no more items
});

// Consumer
var consumer = Task.Run(async () =>
{
    await foreach (var item in channel.Reader.ReadAllAsync()) // awaits if empty; ends on Complete
        Process(item);
});

await Task.WhenAll(producer, consumer);
```
> `BlockingCollection<T>` ek concurrent collection wrap karta hai (default FIFO `ConcurrentQueue<T>`; `ConcurrentStack`/`ConcurrentBag` bhi wrap kar sakta hai). `Channel.CreateBounded`/`CreateUnbounded` async-first option hai built-in back-pressure ke saath. Back-pressure paane ke liye hamesha **bounded** capacity use karo.

### Common pitfalls / interview gotchas
- Ek **unbounded** queue use karna → koi back-pressure nahi → producers consumers se aage nikle to memory phatt jaati hai.
- Hand-rolled version: `while` ki jagah `if`, ya mixed producers/consumers ke saath `PulseAll` ki jagah `Pulse` → atke hue threads.
- Completion signal (`CompleteAdding` / `Writer.Complete`) dena ya `CancellationToken` honor karna bhool jaana → consumers hamesha ke liye hang.
- Blocking ki jagah busy-waiting/polling → CPU waste; queue ko block/await karne do.

### Interview Q&A
- **Q: Producer-consumer kaunsi problem solve karta hai?** A: Alag speeds ke producers aur consumers ko ek shared buffer se decouple karna, buffer full hone pe back-pressure ke saath.
- **Q: Hand-rolled `Monitor.Wait/Pulse` se `BlockingCollection`/`Channels` kyun prefer?** A: Wo saara synchronization, blocking/awaiting, aur signaling sahi encapsulate karte hain, to aap spurious-wakeup aur lost-signal bugs se bachte ho.
- **Q: Back-pressure kya hai?** A: Ek full bounded buffer producers ko slow/pause karne pe majboor karta hai taaki consumers catch up kar sakein, unbounded memory growth rok kar.

## Mental Model / Analogy Recap

- **Process vs Thread** — Alag restaurants vs ek kitchen share karte waiters (shared heap, private stacks).
- **Mutex / lock** — Ek chaabi waala washroom: andar jaane se pehle acquire, nikalte waqt release.
- **Deadlock** — Do diners har ek ek utensil pakde, doosre ka wait karte; circular wait ko fixed ordering se todo.
- **Livelock** — Do log corridor mein politely hamesha dodge karte reh jaate hain. **Starvation** — pushy banda hamesha queue cut karta hai.
- **Race condition** — Dono threads "5" padhte, dono "6" likhte; ek increment gayab.
- **Semaphore** — N tokens waala parking lot; token nahi to entry nahi.
- **Monitor.Wait/Pulse** — Waiter counter pe so jaata hai (chaabi chhod ke) jab tak cook ghanti na bajaaye; counter hamesha `while` mein re-check karo (spurious wakeups).
- **Thread pool / TPL** — Har customer ke liye naya waiter hire karne ki jagah ek fixed crew ek queue se orders uthati hai.
- **volatile** — Apni private notebook pe bharosa mat karo; shared blackboard se padho/likho taaki sab latest dekhein.
- **Interlocked / CAS** — "Mujhe laga 5 tha; agar ab bhi 5 hai to 6 kar do, warna batao aur main retry karunga." Koi lock nahi.
- **ReaderWriterLockSlim** — Ek library: unlimited readers saath, par ek writer poora room khaali karwa deta hai.
- **Producer-Consumer** — Cooks limited counter pe dishes rakhte, waiters uthate; full counter cooks ko rok deta hai (back-pressure).

> **Golden interview reminders:** `count++` atomic nahi hai • `volatile` ≠ atomicity • `Monitor.Wait` hamesha `while` mein • release (`Monitor.Exit`/`ExitWriteLock`) hamesha `finally` mein • bounded queues back-pressure dete hain • deadlock rokne ke liye kisi bhi ek Coffman condition ko todo.

### 1.2 Components — Detailed Explanation (Hinglish)

**Angular Frontend (Excel Add-in)**
Ye woh UI hai jo Excel ke andar plugin/add-in ki tarah chalta hai. User yahan se data filter karta hai, template select karta hai, aur "generate" trigger karta hai. Ye seedha backend services se baat nahi karta — hamesha BFF se hi baat karta hai.

**Azure AD (Azure Active Directory) — Authentication**
Azure AD basically Microsoft ka identity provider hai — jaise Google login hota hai waise hi ye Microsoft ka wala hai. Jab user login karta hai, Azure AD verify karta hai ki user kaun hai (company ke andar) aur ek **JWT token** deta hai. Ye JWT token ek signed piece of data hota hai jisme user ki identity aur permissions (claims) hoti hain. Har request ke saath ye token bhejte hain, aur backend usko verify karta hai bina baar-baar Azure AD se poochhe (kyunki signature se hi pata chal jata hai token valid hai ya nahi). Iska fayda: password kahin store nahi karna padta, aur enterprise SSO (Single Sign-On) mil jata hai — company ka employee ek hi login se Excel plugin bhi use kar sakta hai.

**BFF (Backend-for-Frontend)**
Ye ek pattern hai jaha frontend (Angular) ke liye specifically ek layer banate hain jo downstream services ko orchestrate karti hai. Iska kaam hai: Angular se request lena, JWT validate karna, phir decide karna ki ye command hai (kuch likhna/change karna hai) ya query hai (sirf padhna hai), aur uske hisab se right service(s) ko call karna. BFF isliye banate hain taaki Angular ko multiple services ke saath directly deal na karna pade — ek hi jagah se baat karo.

**Azure App Service**
Ye Azure ka **PaaS (Platform as a Service)** hai apne application ko host karne ke liye. Matlab tumhe server manage nahi karna padta — bas apna code deploy karo (Angular build, ya .NET/Node API), Azure khud VM, OS patching, networking sab handle karta hai. Har service (BFF, Data Ingestion, Template Engine) ka apna-apna App Service instance ho sakta hai. Ismein **App Service Plan** hota hai jo decide karta hai kitna CPU/RAM milega aur kitna scale ho sakta hai (Free, Basic, Standard, Premium tiers) — jitna upar tier utna zyada scaling aur availability features milte hain (jaise auto-scale, deployment slots, availability zones).

**Data Ingestion/Filtering Service (MS SQL Server backed)**
Ye service bade centralized tax/audit datasets ko fetch aur filter karta hai. Iske paas **MS SQL Server** hai jisme structured relational data hai (tax records, audit trails) — aur complex tax calculations ke liye **stored procedures** use hoti hain (kyunki stored procedures SQL Server ke andar hi run hoti hain, so heavy calculation logic database ke close reh kar fast execute hoti hai, network round-trips kam hote hain).

**Template Engine Service (Cosmos DB backed)**
Ye service Excel templates (formulas, validations, layout config) manage karta hai. Iske liye **Cosmos DB** use hota hai — jo ek **NoSQL, schema-flexible database** hai. Templates ka structure user-to-user / tax-form-to-tax-form alag ho sakta hai (kisi mein extra formula field, kisi mein extra validation rule) — isliye flexible JSON-based document store (Cosmos) zyada sense banata hai relational table ke comparison mein. Cosmos DB globally distributed bhi ho sakta hai aur low-latency reads deta hai — jo template-heavy read operations ke liye accha hai.

**Saga Orchestration (at BFF)**
Chunki data 2 alag services/databases mein split hai (MSSQL + Cosmos), ek single ACID transaction possible nahi hai cross-service. Isliye **Saga pattern** use karte hain — BFF orchestrator ban kar step-by-step dono services ko call karta hai, aur agar koi step fail ho to pehle wale successful steps ko **compensate** (undo/rollback) karta hai.

**CQRS at BFF**
CQRS matlab **Command Query Responsibility Segregation** — likhne (write) aur padhne (read) ke liye alag-alag path/logic banate hain. Command path Saga trigger karta hai (writes go to respective service — ingestion config MSSQL service ko, template config Cosmos service ko). Query path dono databases (MSSQL + Cosmos) se data combine/aggregate karke ek unified response Angular ko deta hai — jaise ek dashboard view jisme filtered data bhi dikhna hai aur template info bhi.

### 1.3 Key Design Decisions — Why?

| Decision | Reasoning |
|---|---|
| Monolith → Microservices | Ingestion logic aur Template generation logic alag scaling needs rakhte hain — ingestion zyada CPU/DB-heavy, template generation zyada read/compute-on-formula-heavy. Independent scaling aur deployment ke liye split kiya. |
| Saga (Orchestration, not Choreography) | Sirf 2 services hain — orchestration simpler hai manage karna jab services kam hon. BFF already orchestration layer hai (existing responsibility), toh Saga coordination bhi wahin daal diya — extra message broker/event bus ki complexity nahi badhai. |
| Separate DBs (MSSQL + Cosmos) | Alag data shapes — relational tax records vs flexible template schema. Database-per-service bhi microservices best practice hai (loose coupling). |
| CQRS at BFF | Query side ko dono DBs se combine karna padta hai — agar ye har downstream service khud karta to tight coupling ban jata. BFF ek neutral aggregation point hai. |
| JWT + Azure AD | Enterprise SSO chahiye tha (company employees), stateless auth chahiye tha (scaling ke liye session store ki zaroorat nahi). |
| Azure App Service (not AKS/VMs) | PaaS — operational overhead kam, managed scaling/patching, fits well jab team large Kubernetes ops overhead nahi lena chahti. |

## 2. Low-Level Design (LLD)

### 2.1 API Contracts (BFF ↔ Downstream Services)

**BFF → Data Ingestion Service**
```
POST /api/ingestion/filter
Headers: Authorization: Bearer <JWT>
Body: {
  "filterCriteria": { "taxYear": 2025, "entityId": "...", "auditFlag": true },
  "requestId": "saga-txn-123"   // used for Saga correlation
}
Response: {
  "status": "SUCCESS",
  "datasetId": "abc123",
  "recordCount": 45000
}
```

**BFF → Template Engine Service**
```
POST /api/templates/generate
Headers: Authorization: Bearer <JWT>
Body: {
  "datasetId": "abc123",       // reference to ingestion output
  "templateId": "tax-audit-v2",
  "requestId": "saga-txn-123"
}
Response: {
  "status": "SUCCESS",
  "excelFileUrl": "https://.../generated/xyz.xlsx"
}
```

**Compensating call (if Template Engine fails)**
```
POST /api/ingestion/release
Body: { "datasetId": "abc123", "requestId": "saga-txn-123" }
// Releases locked/reserved dataset, marks it as not-in-use
```

### 2.2 Database Schema Considerations

**MS SQL Server (Data Ingestion Service)**
- `TaxRecords` (RecordId, EntityId, TaxYear, Amount, Status, ...)
- `AuditTrail` (AuditId, RecordId, Action, Timestamp, UserId)
- Stored Procedures: `sp_CalculateTaxLiability`, `sp_ApplyDeductions`, `sp_ValidateAuditCompliance`
  — ye complex, multi-step calculations ko DB ke andar hi run karte hain taaki large dataset ko network se bahar na lana pade.

**Cosmos DB (Template Engine Service)**
- Container: `Templates` — partition key: `templateCategory` (e.g., "tax-form", "audit-report")
  ```json
  {
    "id": "tax-audit-v2",
    "templateCategory": "tax-form",
    "layout": { "sheets": [...] },
    "formulas": [ { "cell": "D5", "expression": "SUM(D1:D4)" } ],
    "validations": [ { "cell": "D5", "rule": "range", "min": 0, "max": 999999 } ]
  }
  ```
  — flexible schema kyunki har template ka formula/validation set alag hoga.

### 2.3 Saga Orchestration Flow (Step-by-Step)

```
1. BFF receives "Generate Excel" command from Angular
2. BFF starts Saga (requestId = saga-txn-123)
3. Step A: BFF → Data Ingestion Service: filter & lock dataset
      ✅ Success → datasetId returned
      ❌ Failure → Saga ends, return error to user (nothing to compensate yet)
4. Step B: BFF → Template Engine Service: generate Excel using datasetId
      ✅ Success → excelFileUrl returned → Saga COMPLETE
      ❌ Failure → COMPENSATE Step A:
           BFF → Data Ingestion Service: release dataset (undo lock/reservation)
           Log Saga failure with requestId for traceability
5. BFF returns final status (success/failure) to Angular
```

*(Compensation logic exact implementation tumne confirm nahi kiya tha — upar wala ek standard/reasonable pattern hai jo "reserve → generate → release-on-failure" approach follow karta hai. Interview mein agar drill ho to isi logic ko apne words mein explain karna, aur agar exact implementation yaad aaye to wo bolna.)*

### 2.4 CQRS at BFF — Command vs Query Path

**Command Path** (writes → triggers Saga)
- `POST /api/excel/generate` → triggers full Saga flow above (writes to both services)

**Query Path** (reads → combines Cosmos + MSSQL)
- `GET /api/dashboard/summary?entityId=...`
  → BFF internally calls:
    - Data Ingestion Service (read-only) → tax record counts/status from MSSQL
    - Template Engine Service (read-only) → available templates from Cosmos
  → BFF **aggregates** both responses into one combined JSON for Angular.

Isse Angular ko sirf ek call karni padti hai, aur BFF dono alag data-sources ko internally merge karta hai. Trade-off ye hai ki query response thoda slow ho sakta hai (2 calls internally + merge), aur agar ek downstream service slow/down ho to poora aggregated response affect hota hai (isko timeout/fallback se handle karna padta hai).

### 2.5 Excel Generation Flow (Formulas/Validations)

```
1. Template Engine fetches template JSON from Cosmos DB (formulas + validations + layout)
2. Filtered dataset (from Ingestion service) is mapped into the template's data cells
3. Formulas applied on top (e.g., SUM, tax-liability calculations already computed via
   SQL stored procedures upstream, OR recalculated at Excel-formula-level for live editing)
4. Validation rules applied (e.g., range checks, dropdown lists) so user can't enter
   invalid data when they open/edit the Excel file
5. Final .xlsx generated and stored (e.g., Azure Blob Storage — confirm if this was used)
   → URL returned to BFF → Angular
```

## 3. Azure Services — Detailed Explanation (Hinglish)

**Azure App Service**
PaaS hosting service — apna code deploy karo, Azure infrastructure (VM, OS, patching, networking) manage karta hai. Har microservice (BFF, Ingestion, Template Engine) alag App Service instance pe chal sakta hai, isse independent scaling aur deployment milta hai.

**App Service Plan & Tiers**
App Service Plan decide karta hai kitna compute resource (CPU/RAM) milega aur kaunse features available hain:
- **Free/Shared** — dev/testing ke liye, no SLA
- **Basic** — manual scaling, no auto-scale
- **Standard** — auto-scale support, deployment slots (5), daily backups
- **Premium** — zyada auto-scale instances, availability zones support, better networking (VNet integration)

Production enterprise app (tax/audit data) ke liye typically **Standard ya Premium** tier use hota hai kyunki auto-scale aur availability zones chahiye hote hain.

**Auto-scale Rules**
Ye ek configuration hai jisme tum define karte ho: "agar CPU 70% se zyada ho jaye to ek aur instance add kar do" (scale-out), aur "agar load kam ho jaye to instance hata do" (scale-in). Isse manual intervention ke bina traffic spikes handle ho jate hain (jaise tax-filing deadline ke aas-paas heavy load).

**Deployment Slots**
Ye ek feature hai jisme tum production ke alawa ek "staging" slot bana sakte ho — naya code pehle staging pe deploy karo, test karo, phir ek click mein staging aur production ko **swap** kar do (zero-downtime deployment). Isse rollback bhi easy hota hai — agar naya deployment problematic ho to wapas swap kar do.

**Availability Zones**
Azure ke andar ek Region (jaise "Central India") ke andar multiple physically-separate datacenters hote hain — inhe Availability Zones kehte hain. Agar tumhara App Service availability-zone-redundant hai, to agar ek zone (datacenter) down ho jaye (power failure, hardware issue), doosri zone automatically traffic handle kar leti hai — isse high availability milti hai.

**Azure AD (Active Directory)**
Microsoft ka identity/authentication service. Enterprise users (company employees) isse login karte hain, aur ye JWT tokens issue karta hai jinhe backend services verify karte hain. Iska integration "OAuth2 / OpenID Connect" standard follow karta hai.

**Cosmos DB**
Azure ka globally-distributed NoSQL database. Schema-flexible (JSON documents), automatically scale ho sakta hai (throughput measured in RU/s — Request Units per second), aur multiple regions mein replicate ho sakta hai low-latency reads ke liye. Consistency levels configurable hote hain (Strong, Bounded Staleness, Session, Eventual) — trade-off between consistency aur latency/availability.

## 4. Interview Drill-Down Question Bank (Exhaustive)

### A. Scalability
1. **Q: Tax filing deadline ke time traffic spike aata hoga — kaise handle karoge?**
   A: App Service auto-scale rules (CPU/memory based, ya schedule-based scale-out before known deadlines). Ingestion aur Template Engine independently scale ho sakte hain based on jisme zyada load ho.
2. **Q: Agar Data Ingestion service ka load Template Engine se bahut zyada ho, to kya hoga?**
   A: Chunki dono alag App Service instances hain, Ingestion ko independently zyada instances mil sakte hain — that's the whole point of splitting into microservices (independent scaling).
3. **Q: Large datasets (lakhs of tax records) ko filter karna — bottleneck kaha ban sakta hai?**
   A: MSSQL query performance — indexing strategy, avoiding full table scans, using pagination/batching instead of loading everything in memory at once, and possibly read-replicas for heavy read queries.
4. **Q: Cosmos DB scaling kaise kaam karta hai?**
   A: RU/s (Request Units) based — tum provision karte ho kitna throughput chahiye, aur autoscale bhi enable kar sakte ho jo automatically RU/s adjust karta hai based on load.
5. **Q: BFF single point of scaling bottleneck ban sakta hai — kaise mitigate karoge?**
   A: BFF ko bhi auto-scale App Service pe rakho, aur agar query aggregation heavy ho to caching layer add karo (e.g., Redis) for frequently-requested combined data.

### B. Availability
6. **Q: Agar Template Engine service down ho jaye, to Excel generate karne wala flow kya karega?**
   A: Saga step B fail hoga → compensating action trigger hoga (dataset release) → user ko clear error message milega ki "Template service unavailable, try again". Circuit breaker pattern lagana chahiye taaki BFF baar-baar down service ko hit na kare.
7. **Q: High availability kaise ensure ki App Service pe?**
   A: Standard/Premium tier ke availability zones, health checks + auto-restart on failure, deployment slots for zero-downtime deploys.
8. **Q: Azure region hi down ho jaye to?**
   A: Multi-region deployment with Traffic Manager/Front Door for failover (agar setup tha — confirm karna, agar nahi tha to ye ek improvement point ban sakta hai jo tum interview mein propose kar sakte ho).
9. **Q: Cosmos DB availability kaise handle hoti hai?**
   A: Cosmos automatically data ko multiple replicas mein rakhta hai within a region, aur agar multi-region writes enabled hon to cross-region failover bhi mil sakta hai.

### C. Consistency & Data Integrity
10. **Q: Saga pattern mein consistency kaise maintain karte ho jab ACID transaction possible nahi hai cross-service?**
    A: Eventual consistency accept karte hain — Saga ensures ki agar koi step fail ho to already-completed steps compensate ho jayein, so system ek "valid" state mein wapas aa jata hai, even though intermediate states temporarily inconsistent ho sakte hain.
11. **Q: Agar BFF crash ho jaye Saga ke beech mein (Step A success, Step B pending), to kya hoga?**
    A: Saga state ko persist karna padta hai (e.g., a "SagaLog" table/store with requestId + status) taaki restart ke baad BFF pending/incomplete sagas ko detect karke resume ya compensate kar sake. *(Agar ye implement nahi tha to ye ek honest gap hai jo tum bata sakte ho — "we didn't persist saga state, that was a known limitation".)*
12. **Q: Query side (CQRS) mein stale data ka risk hai kya, jab dono DBs se combine kar rahe ho?**
    A: Haan — agar ek DB update ho gaya but doosra abhi lag raha hai, query response temporarily inconsistent dikh sakta hai. Ye eventual consistency ka trade-off hai jo CQRS mein accept karte hain for better read performance.
13. **Q: Cosmos DB ka consistency level kya use karte the?**
    A: *(Confirm karna — agar pata nahi to bol sakte ho "Session consistency" default hota hai zyada apps mein, ye balance deta hai performance aur consistency ke beech.)*

### D. Security
14. **Q: JWT validate kaise hota hai har service pe?**
    A: Azure AD ka public signing key use karke JWT signature verify karte hain (middleware level, har service mein — ya sirf BFF pe agar downstream services BFF ko trust karte hain via internal network).
15. **Q: Downstream services (Ingestion, Template Engine) directly access ho sakte hain bina BFF ke?**
    A: Ideally nahi — VNet integration ya internal-only endpoints use karke unhe public internet se isolate karna chahiye, sirf BFF unko call kar sake.
16. **Q: Sensitive tax data encrypt kaise hota hai?**
    A: At-rest encryption (SQL Server TDE - Transparent Data Encryption, Cosmos DB automatic encryption at rest) aur in-transit (HTTPS/TLS everywhere).
17. **Q: Token expiry aur refresh kaise handle hota hai?**
    A: Azure AD short-lived JWT access tokens deta hai + refresh tokens for silent re-authentication, taaki user ko baar-baar login na karna pade.

### E. Performance
18. **Q: Stored procedures kyun use kiye complex calculations ke liye, application code mein kyun nahi?**
    A: Bade dataset ke saath calculation karna hai to data ko application layer tak la kar process karna network overhead aur memory pressure badhata hai. Stored procedures DB ke andar hi run hote hain — data movement minimize hota hai, aur SQL Server ka query optimizer bhi use ho jata hai.
19. **Q: Excel file generation slow ho to kaise debug/optimize karoge?**
    A: Profiling — kaha time zyada lag raha hai (data fetch, formula application, file write)? Batching/streaming large datasets instead of loading all in memory, async generation with polling/webhook notification instead of synchronous blocking call.

### F. Failure Handling & Resilience
20. **Q: Retry logic kaise implement ki thi service calls ke beech?**
    A: *(Confirm — agar Polly library ya similar retry-with-backoff use hua tha bolna, warna generic answer: "exponential backoff with limited retries, plus circuit breaker to avoid hammering a failing service".)*
21. **Q: Idempotency kaise ensure ki, taaki retry se duplicate Excel files na bane?**
    A: requestId/Saga correlation ID use karke — agar same requestId dobara aaye to check karo ki already processed hai ya nahi, taaki duplicate side-effects na hon.

### G. Monitoring & Observability
22. **Q: Production issues kaise detect/debug karte the?**
    A: *(Confirm tool — assumed Application Insights)* — distributed tracing (ek requestId ko BFF se leke dono services tak trace karna), centralized logging, alerts on failure rate/latency spikes.
23. **Q: Saga failures ko track kaise karte the?**
    A: Correlation ID (requestId) based logging across services, dashboard/alert jab compensation trigger ho (indicates a failure pattern worth investigating).

### H. Cost & Trade-offs
24. **Q: CQRS ka cost kya tha — kya simpler design se better tha?**
    A: Extra complexity (do paths maintain karna, aggregation logic) — lekin fayda ye mila ki reads fast aur flexible ho gaye without tightly coupling downstream services ko each other se. Trade-off worth it tha kyunki reads frequent the (dashboard views) aur writes kam.
25. **Q: Microservices split karne ka cost kya tha (vs monolith)?**
    A: Operational overhead badha (2 services deploy/monitor karna, network calls, distributed transaction complexity via Saga) — lekin fayda mila independent scaling aur independent deployment ka (Template Engine ko change karne ke liye Ingestion redeploy nahi karna padta).

### I. Migration-Specific (Monolith → Microservices)
26. **Q: Monolith se microservices migrate karte time sabse bada challenge kya tha?**
    A: Data ko split karna (kaunsa data kis service ko belongs karta hai), aur transactions jo pehle single DB transaction the, unko Saga mein convert karna.
27. **Q: Migration strategy kya thi — big bang ya incremental?**
    A: *(Confirm — agar strangler fig pattern use hua tha, ya phased rollout, bolna. Generic answer: "incremental — ek service pehle extract ki, monolith ke saath parallel chalaya, phir traffic gradually shift kiya".)*

### J. CQRS-Specific
28. **Q: CQRS kyun BFF pe implement kiya, downstream services mein kyun nahi?**
    A: Kyunki query ke liye data dono services (MSSQL + Cosmos) se combine karna tha — ye responsibility kisi ek downstream service ki nahi honi chahiye (tight coupling create karega), BFF neutral aggregation layer hai.
29. **Q: Command aur query model ke beech sync kaise hota hai?**
    A: *(Important gap — since there's no separate read-store, ye "CQRS-lite" hai jaha command aur query dono live data pe hi kaam karte hain, sirf path/logic alag hai. Agar interviewer drill kare "to real CQRS event-sourcing wala hai?", honestly bolna: "nahi, humne full event-sourcing nahi kiya — humne sirf command/query responsibility ko code-level pe separate kiya, both hitting live data".)*

### K. Database-Specific (MSSQL vs Cosmos)
30. **Q: MSSQL aur Cosmos DB choose karne ka criteria kya tha?**
    A: Ingestion service ka data relational/structured hai (tax records with fixed schema, complex joins/calculations needed) — MSSQL fits well. Template data flexible/variable schema hai (har template ka apna formula/validation set) — Cosmos (NoSQL/JSON) fits better.
31. **Q: Do alag database technologies manage karna operational complexity nahi badhata?**
    A: Haan, badhata hai (do alag backup/monitoring/scaling strategies seekhni padti hain) — lekin trade-off worth tha kyunki data shape fundamentally different tha, ek single DB dono use-cases ke liye compromise hota.

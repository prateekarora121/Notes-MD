### 1.2 Components — Detailed Explanation (Hinglish)

**Monolith Application (ECS pe hosted)**
Poora backend — Dashboard APIs, Import API, Export API — ek hi service/deployment unit hai. Koi microservices split nahi hai. Ye monolith Angular dashboard ko bhi serve karta hai (backend APIs), aur external/internal dealers ke import/export API calls bhi yahin handle hoti hain.

**Import Flow**
Third-party dealer system se deal data pull karte hain (ya dealer push karta hai), jo unke apne format mein hota hai. System us data ko apne **native DMS format** mein translate karta hai — is translation ka logic **script** mein likha hota hai (dealer-specific ya global script), jo runtime pe fetch aur execute hoti hai (bina application redeploy kiye — script engine doc mein explain kiya gaya pattern). Translation ke baad system customer aur vehicle records create/update karta hai, jo aage contract generation ke liye dusre internal systems ko support karte hain.

**Export Flow**
Reverse process — DMS ke native data ko external/target system ke format mein convert karna, phir se script rules ke through, based on jis type/dealer ke liye export ho raha hai.

**Script Engine**
C# script source (text form) S3 mein store hoti hai (`dealerId/scriptName` path pattern se). Runtime pe ye script Roslyn se in-memory compile hoti hai aur reflection se execute hoti hai (detailed flow "Script Engine" reference doc mein hai). Isse har dealer ke liye custom translation logic ho sakta hai bina code redeploy ke.

**AWS API Gateway**
External/internal API consumers ka entry point — requests yahan se WAF aur phir ALB tak route hoti hain.

**AWS WAF (Web Application Firewall)**
Common web attacks (SQL injection, XSS, bad bots) se protect karta hai — requests ko application tak pahunchne se pehle filter karta hai.

**ALB (Application Load Balancer)**
Incoming traffic ko multiple ECS tasks (containers) ke beech distribute karta hai — health checks bhi karta hai taaki unhealthy instances ko traffic na bheje.

**NACLs (Network ACLs)**
VPC subnet level pe stateless firewall rules — kaunsa traffic kaunsi subnet mein aana/jaana allowed hai, ye control karta hai (security group se ek layer aur neeche/upar ka network-level control).

**ECS with EC2 launch type + Auto Scaling Group (ASG)**
ECS (Elastic Container Service) containers ko orchestrate karta hai. "EC2 launch type" matlab tumhare khud ke EC2 instances hain jinpe containers run hote hain (Fargate ke bajaye, jaha AWS underlying servers manage karta). ASG in EC2 instances ko automatically scale karta hai (load ke hisaab se instance count badhana/ghatana).

**RDS (MSSQL) Multi-AZ**
RDS = **Relational Database Service** — AWS ka managed database offering, jisme AWS backup/patching/failover khud handle karta hai. **Multi-AZ** matlab primary database ka ek synchronous standby replica alag Availability Zone mein rehta hai — agar primary fail ho jaye, automatic failover ho jata hai standby pe, minimal downtime ke saath.

**S3 (Simple Storage Service)**
Object storage — yahan 2 cheezein store hoti hain: (1) Scripts (C# class files, text/blob ki tarah), (2) Request/Response logs (har third-party call ka log, compliance/debugging ke liye). S3 **lifecycle rules** automatically purane versions/objects delete karti hain (90 din ke baad non-current versions, logs 3 mahine retain).

**Secrets Manager**
Sensitive credentials (DB passwords, Okta client secrets, API keys) securely store karta hai — application runtime pe securely fetch karta hai, hardcode nahi karna padta config mein.

**KMS (Key Management Service)**
Encryption keys manage karta hai — data encrypt/decrypt karne ke liye (e.g., Secrets Manager ke secrets khud KMS se encrypted hote hain, ya specific sensitive fields database mein encrypt karne ke liye bhi use ho sakta hai).

**New Relic (APM) + PagerDuty**
New Relic **Application Performance Monitoring** hai — requests ki latency, error rate, traces track karta hai. Jab koi threshold cross hoti hai (e.g., error rate spike, high latency), alert trigger hota hai jo **PagerDuty** ko jata hai — jo on-call engineer ko notify karta hai (SMS/call/push).

**Okta**
Identity provider, do alag flows use hote hain yahan:
- **Dashboard (internal onboarding team)** → **SSO (Single Sign-On)**: user browser redirect hota hai Okta login page pe, login karta hai (company credentials se), Okta ek session/token deta hai, user wapas dashboard pe redirect ho jata hai already-authenticated. Ye human/interactive login ke liye best fit hai.
- **API consumers (internal + external subscribed dealers)** → **Client Credentials flow**: ye machine-to-machine (M2M) auth hai, koi human login involved nahi. Subscription ke time client ek `client_id` + `client_secret` milta hai. Har API session ke liye wo Okta ko directly (secret ke saath) call karke ek short-lived access token lete hain, phir har request mein wo token Bearer header mein bhejte hain. Isse credentials baar-baar expose nahi karne padte, aur token expire ho jata hai (security ke liye).

## 1.2.1 Multi-Region DR — Recommended Standard Pattern (Detailed)

> Ye woh **recommended/industry-standard pattern** hai jo tum confidently interview mein present kar sakte ho, chahe exact numbers (RTO/RPO) pata na ho. Confirmed: RDS read replica maintain hoti hai DR ke liye, aur Route 53 se traffic dusre region/AZ pe divert hota hai — yahi standard AWS DR approach hai, neeche step-by-step samjhaya gaya hai.

### Setup (kya components involved hain)

```
Primary Region (e.g., us-east-1)              DR Region (e.g., us-west-2)
┌─────────────────────────┐                   ┌─────────────────────────┐
│  ALB → ECS → App          │                   │  ALB → ECS → App          │
│  RDS MSSQL (Primary,       │   Async           │  RDS MSSQL (Read Replica, │
│  Multi-AZ)                 │ ──Replication──▶ │  cross-region)             │
│                             │                   │  (read-only until         │
│  S3 (scripts+logs)          │  Cross-Region     │   promoted)                │
│                             │ ──Replication──▶ │  S3 (replicated copy)      │
└─────────────────────────┘                   └─────────────────────────┘
              ▲                                              ▲
              └────────────────┬─────────────────────────────┘
                                │
                    ┌───────────────────────┐
                    │   Route 53 (DNS)        │
                    │   + Health Checks        │
                    │   (failover routing       │
                    │    policy)                 │
                    └───────────────────────┘
                                ▲
                                │
                          End Users / Dealers
```

### Step-by-step DR Flow (Hinglish)

**1. Normal operation (steady state)**
- Primary region mein full stack active hai (ALB, ECS, RDS Primary with Multi-AZ standby, S3).
- **RDS Read Replica** DR region mein continuously maintain hoti hai — primary se **asynchronous replication** ke through data continuously sync hota rehta hai. Ye replica **read-only** hoti hai jab tak formally promote na ki jaye.
- **S3 Cross-Region Replication (CRR)** enabled hoti hai — scripts aur logs automatically DR region ke bucket mein bhi copy ho jate hain.
- DR region mein bhi ek minimal/standby application stack (ECS + ALB) ready rakha jata hai — ya to already running (warm standby, thoda zyada cost) ya scaled-to-zero/minimal (pilot light, kam cost lekin thoda slow spin-up).

**2. Route 53 — Health Checks + Failover Routing Policy**
- Route 53 ko ek **failover routing policy** ke saath configure karte hain: primary region ka endpoint "Primary" record hai, DR region ka endpoint "Secondary" record hai.
- Route 53 **health checks** continuously primary region ke ALB/endpoint ko monitor karti hain (e.g., har 30 seconds ek HTTP health-check request bhejti hai).
- Jab tak primary healthy hai, saara DNS traffic primary region ke IP/endpoint pe resolve hota hai — users ko normally primary region serve hota hai.

**3. Disaster Detection & Failover Trigger**
- Agar health check consecutively fail ho jaye (primary region down/unreachable), Route 53 automatically DNS resolution ko **Secondary (DR) region ke endpoint pe switch** kar deta hai.
- Naye DNS lookups (jo TTL expire hone ke baad hote hain) ab DR region ko point karte hain — is tarah traffic automatically divert ho jata hai without manual DNS changes.

**4. RDS Promotion (Manual ya Automated step)**
- DR region ki RDS Read Replica jab tak sirf **read-only** hai — usse **promote** karna padta hai ek independent, writable Primary banane ke liye (ye ek explicit action hai — "Promote Read Replica" — AWS console/CLI se).
- Promotion ke baad, application (jo ab DR region mein serve ho rahi hai) is naye-promoted DB ko apna primary DB maan kar writes bhejna start karti hai.

**5. Application scale-up in DR region (agar pilot-light/cold standby tha)**
- Agar DR region minimal tha, ASG ko scale-out karna padega actual production load handle karne ke liye — ye configured scaling policies se automated ho sakta hai, ya manual trigger.

**6. Failback (jab primary region wapas healthy ho jaye)**
- Ek baar primary region recover ho jaye, data ko reverse-sync karke (DR se primary) wapas consistent karna padta hai, phir Route 53 traffic ko wapas primary pe switch kiya jata hai — ye typically ek **carefully planned, manual process** hota hai (auto-failback risky hota hai data-loss ke against).

### RTO / RPO — Kaise Explain Karo (agar exact numbers na pata ho)

- **RPO (Recovery Point Objective)** — kitna data loss acceptable hai. RDS async replication mein hamesha kuch **replication lag** hoti hai (seconds se minutes tak, load ke hisaab se) — is lag jitna data potentially lose ho sakta hai agar primary crash ho jaye replication complete hone se pehle.
- **RTO (Recovery Time Objective)** — kitna time lagta hai fully recover hone mein. Ismein shaamil hota hai: Route 53 health-check detection time + DNS TTL propagation time + RDS replica promotion time + (agar cold/pilot-light hai to) application scale-up time.
- **Interview mein honest answer:** "Exact RTO/RPO numbers is specific project ke liye maine measure/document nahi kiye the, lekin architecture-wise ye typical async-replication-based DR hai jaha RPO kuch minutes ka ho sakta hai (replication lag ke hisaab se) aur RTO detection+promotion+DNS-propagation time पर depend karta hai — typically minutes to low tens-of-minutes range mein."

### Trade-offs to mention

- **Async replication = potential data loss window** — agar primary crash ho replication complete hone se pehle, wo un-replicated writes lose ho sakte hain. Isse avoid karne ke liye synchronous cross-region replication chahiye hoga, jo latency cost pe aata hai (writes ko dusre region ke acknowledgment ka wait karna padega — bahut slow ho jata for cross-region distances).
- **Manual promotion step** — RDS replica ko automatically primary nahi bana deta AWS khud (safety ke liye, taaki accidental split-brain na ho) — ye ek deliberate/controlled action hai, jo RTO mein add hota hai but data-integrity safety deta hai.
- **DNS TTL** — Route 53 record ka TTL jitna kam hoga, utni fast failover propagate hogi clients tak, lekin bahut low TTL zyada DNS query load bhi create karta hai.



| Decision | Reasoning |
|---|---|
| Monolith (not microservices) | Low request volume (~4K/day) — microservices ka operational overhead justify nahi hota is scale pe. Ek hi team maintain kar rahi thi shayad — monolith simpler hai. |
| Script Engine (runtime C# compilation) | Dealer-specific/global translation logic frequently change hoti hai — release cycle wait karna business ke liye slow tha. Runtime scripts se business logic ko "data" ki tarah treat karte hain, redeploy ki zaroorat khatam. |
| S3 for scripts (not DB) | Scripts basically files hain (C# source text) — S3 natural fit hai, versioning built-in milti hai, aur cheap storage hai bade text blobs ke liye. |
| RDS Multi-AZ (not self-managed EC2 MSSQL) | Managed failover, automated backups, patching — operational burden kam karta hai, availability improve karta hai. |
| ECS EC2 launch type (not Fargate) | Shayad cost optimization (EC2 reserved/spot instances Fargate se sasta ho sakta hai predictable workload ke liye), ya existing EC2 expertise/tooling already tha. |
| Sync (not async) import/export | Dealer ko turant confirmation chahiye (deal create hua ya nahi) — business requirement immediate response ka tha, async complexity (queue+polling) avoid ki. |
| New Relic + PagerDuty | Proactive monitoring — issues turant detect ho, on-call engineer ko turant notify ho, SLA maintain ho. |
| Multi-region DR | Tax/vehicle/contract data critical hai business ke liye — single region failure se poora business down nahi hona chahiye. |

## 2. Low-Level Design (LLD)

### 2.1 Import Flow — Detailed Steps

```
1. Third-party dealer/subscribed system calls Import API (Bearer token via Okta)
2. API Gateway → WAF → ALB → ECS (monolith)
3. Request validated (auth token, payload schema)
4. System resolves dealerId → fetches applicable script from S3 (dealerId/scriptName)
5. Script Engine compiles (Roslyn, in-memory) + executes:
      - Parses/translates incoming deal data into native DMS format
6. Translated data used to:
      - Create/Update Customer record (MSSQL)
      - Create/Update Vehicle record (MSSQL)
      - Create/Update Deal record (linking Customer + Vehicle)
7. Request + Response logged to S3 (for audit/debugging, 3-month retention)
8. Synchronous response returned to caller (success/failure + details)
```

### 2.2 Export Flow — Template Method Pattern (Your Recent Work)

**Template Method Pattern** — ek base class mein fixed algorithm skeleton define karte hain, aur specific steps subclasses (ya script-driven logic) override/customize karte hain.

**Fixed Steps (Template — same for all exports):**
```
1. Resolve Dealer       — dealerId se dealer context load karna
2. Create/Update Customer — customer record base logic se handle karna
3. Create/Update Deal      — deal record base logic se handle karna
4. Apply Script Logic       — dealer/type-specific script run karke customer/deal ko
                                further transform/update karna (yahi variable step hai)
```

**Kya Fixed hai vs Kya Vary karta hai:**
- **Fixed (Template/base class mein):** Dealer resolve karna, basic Customer/Deal create-or-update ka core flow, orchestration sequence (order of steps).
- **Varying (Hook methods / script-driven):** Step 4 mein exact transformation logic — export target format ke hisaab se (dealer type, external system requirements) — ye script ke through inject hota hai, base algorithm ko touch kiye bina.

**Design Benefit:** Naya export "type" add karna ho to sirf naya script likhna padta hai (ya script logic modify karna), base Template class ka core flow (resolve → customer → deal → script-hook) reuse ho jata hai — code duplication nahi hoti, aur consistency guaranteed rehti hai across export types.

### 2.3 Transaction Boundary — No Atomicity Across Writes (Important!)

Confirmed: Customer → Vehicle → Deal writes **independent hain, ek single DB transaction mein wrap nahi hote**. Matlab agar Customer create ho gaya lekin Deal create karte time failure aa jaye, **Customer record already committed reh jayega** — poora operation atomically rollback nahi hota.

**Isse jo risk banta hai:**
- Partial/orphan data ban sakta hai (customer bina deal ke, ya vehicle bina deal ke)
- Retry karne pe duplicate customer/vehicle create hone ka risk (agar idempotency check na ho)

**Iske peeche possible reasoning (interview mein explain karne ke liye):**
- Har entity (Customer, Vehicle, Deal) apne aap mein ek valid/independent record hai business ke liye — ek customer exist karna without a deal bhi meaningful ho sakta hai (future deal ke liye reusable).
- Script-driven logic ke saath ek single long-running DB transaction rakhna (jabki beech mein script execution bhi ho raha hai) risky hota — transaction locks lambe time tak hold honge, DB contention badhega.
- Trade-off: Consistency thoda weaken kiya gaya (no atomicity) taaki system responsive/less-locking rahe — is decision ko **explicitly acknowledge karna** interview mein accha lagega, "hume pata hai ye a trade-off hai" bolna better hai defend karne se.

**Agar interviewer puche "isko kaise fix karoge":**
- Idempotency keys (dealId/requestId based) taaki retry duplicate na banaye
- Reconciliation/cleanup job jo orphan records detect kare aur flag/cleanup kare
- Ya explicitly wrap Customer+Vehicle+Deal creation ek transaction mein (agar business requirement allow kare longer locks)

### 2.4 Script Fallback — No Fallback, Fail Fast

Confirmed: **Koi fallback logic nahi hai.** Agar dealer-specific script na mile (missing), ya script execution fail ho (dealer-specific ya global, dono cases), system **directly validation/internal error throw karta hai** — kabhi silently global/default script pe fallback nahi karta.

**Design reasoning (defend karne ke liye):**
- Silent fallback dangerous ho sakta hai tax/vehicle data jaisa critical domain mein — agar galat (wrong dealer ka ya generic) script use ho gayi bina explicit awareness ke, data corruption ka risk hai jo detect karna mushkil hoga baad mein.
- **Fail-fast** approach better hai yahan — explicit error turant dealer/onboarding team ko pata chal jayega ki script missing/broken hai, aur wo fix kar sakte hain, instead of silently wrong data process hona.

### 2.4 Script Storage & Lookup

- **S3 Key pattern:** `dealerId/scriptName` — is se lookup simple hai: dealer ke liye applicable script directly path se fetch ho jati hai (no separate search index chahiye for this simple case).
- **Global Scripts:** Shayad ek reserved/common prefix (e.g., `global/scriptName`) ya separate bucket/folder mein rehti hain — jab dealer-specific script na mile to fallback global script use hoti hai. *(Confirm karna exact fallback logic.)*
- **Versioning:** S3 native versioning enabled — purani script version bhi retrievable hai (rollback ke liye), lifecycle rule 90 din ke baad **non-current versions** delete kar deti hai (cost control).
- **Caching:** Global settings/global scripts frequently read hote hain but rarely change — isliye cache kiya jata hai (in-memory ya ElastiCache — confirm) taaki har request pe S3 hit na ho (latency + cost dono kam hota hai).

## 3. AWS Services — Detailed Explanation (Hinglish)

**API Gateway**
Managed service jo APIs ko expose/manage karne ke liye hota hai — request routing, authentication integration, throttling/rate-limiting, request/response transformation sab yahan configure ho sakta hai. External dealers ke liye ek consistent, secure entry point deta hai.

**AWS API Gateway — Likely Role Here (since WAF + ALB already exist)**
Chunki architecture mein WAF aur ALB already hain (jo generic traffic filtering aur load-balancing karte hain), API Gateway ka hona matlab kuch **API-specific management** add ho raha hai jo ALB akela nahi deta. Ye "likely roles" hain jo is tarah ke external-dealer-facing API setup mein commonly use hote hain — inmein se koi ek ya combination ho sakta hai:

1. **Per-dealer API Keys / Usage Plans** — har subscribed dealer ko API Gateway mein ek alag API key/usage plan assign ki ja sakti hai, jisse **per-dealer rate limiting aur quota** (e.g., "Dealer X max 100 req/min") enforce hoti hai — ye ALB akela nahi kar sakta, ye API Gateway ka specific feature hai.
2. **Request Throttling/Rate Limiting** — global ya per-client throttling rules jo abuse/spike traffic se downstream (ECS/RDS) ko protect karte hain.
3. **Authorizer Integration (Okta token validation)** — API Gateway mein ek **Custom Lambda Authorizer** ya JWT Authorizer configure ho sakta hai jo Okta-issued Bearer token ko validate karta hai **before** request backend tak pahunche — isse invalid/expired tokens wali requests ECS tak pahunchti hi nahi, load bachti hai.
4. **Request Validation** — incoming JSON payload ka basic schema-validation (required fields, types) API Gateway level pe hi ho sakta hai, backend ko malformed requests se bachata hai.
5. **API Versioning / Stage Management** — different API versions (v1, v2) ya environments (dev/staging/prod) ko manage karne ke liye stages use ho sakte hain.
6. **Centralized Logging/Metrics for API usage** — kis dealer ne kitni calls ki, kaunsi endpoints zyada use hui — CloudWatch ke through track ho sakta hai, business/usage analytics ke liye useful.
7. **Single External Entry Point** — external dealers ko ek clean, documented (Swagger/OpenAPI-integrated) API surface dena, jabki internal ALB/ECS setup unse abstract rahe.

*(In-mein se konsa exactly configured tha, wo tumhe apne project mein verify karna hoga — but ye sab valid/common reasons hain jo interview mein bolne layak hain agar drill ho.)*

**WAF (Web Application Firewall)**
Layer 7 pe malicious traffic filter karta hai — common attack patterns (SQLi, XSS) ke against rules define kar sakte ho, aur rate-based rules bhi (jaise "ek IP se X requests/min se zyada aaye to block").

**ALB (Application Load Balancer)**
Layer 7 load balancer — HTTP/HTTPS traffic ko multiple backend targets (ECS tasks) mein distribute karta hai, path-based/host-based routing bhi support karta hai, aur health checks karke unhealthy targets ko automatically traffic dena band kar deta hai.

**NACLs (Network Access Control Lists)**
VPC ke subnet level pe operate karte hain — **stateless** rules (matlab inbound aur outbound dono explicitly allow karne padte hain, unlike Security Groups jo stateful hote hain). Extra defense layer network level pe.

**ECS (Elastic Container Service)**
Container orchestration service — Docker containers ko manage/schedule karta hai. **EC2 launch type** ka matlab hai ki tum khud EC2 instances provision karte ho jisme containers chalte hain (Fargate ke against, jaha AWS underlying compute manage karta hai — tumhe sirf container specify karna padta).

**Auto Scaling Group (ASG)**
EC2 instances ka pool jo automatically scale hota hai defined policies ke hisaab se (CPU utilization, request count, ya scheduled scaling — jaise business hours 9am-6pm mein zyada instances rakhna).

**RDS (Relational Database Service) — Multi-AZ**
Managed relational database. Multi-AZ deployment mein ek **synchronous standby replica** dusri Availability Zone mein maintain hoti hai — primary fail hone pe automatic failover hota hai (usually seconds mein), application ko manual intervention nahi karna padta.

**S3 (Simple Storage Service) + Lifecycle Rules**
Object/blob storage, highly durable (99.999999999% durability). **Lifecycle rules** automated policies hain jo objects ko time ke hisaab se manage karti hain — e.g., "90 din se purani non-current versions delete karo" ya "30 din baad Glacier (cheaper cold storage) mein move karo".

**Secrets Manager**
Credentials/secrets securely store aur rotate karne ke liye — application ko hardcoded passwords/keys rakhne ki zaroorat nahi, runtime pe securely fetch karta hai (aur automatic rotation bhi configure ho sakti hai).

**KMS (Key Management Service)**
Encryption keys create/manage karta hai. Is project mein specifically **S3 mein stored sab data** (scripts + request/response logs, dono) KMS keys se encrypt hote hain (server-side encryption, SSE-KMS). Isse data-at-rest security milti hai — agar koi unauthorized tareeke se S3 bucket access bhi kar le, encrypted data bina KMS key permission ke unreadable rehta hai. KMS centralized key management aur audit trail bhi deta hai (kisne kab kaunsi key use ki — CloudTrail ke through track hota hai).

**Multi-Region DR (Disaster Recovery)**
Agar poora AWS region hi down ho jaye (rare but possible), to business continuity ke liye ek doosre region mein backup setup hota hai — typically RDS cross-region read replica (jo failover ke time primary ban sakti hai) + S3 cross-region replication + DNS-level failover (Route 53) taaki traffic automatically healthy region pe redirect ho jaye.

## 4. Recommendations — Scaling & Making It More Robust (If Traffic Increases)

> Ye section directly kaam aayega agar interviewer puche: **"Agar traffic 10x/50x badh jaye to kya badloge?"** — classic system design follow-up. Neeche **low-hanging fruit** (quick, low-effort wins) se start karke **major infra changes** (agar scale genuinely bahut badh jaye) tak arrange kiya gaya hai.

### 5.1 Low-Hanging Fruit (Quick Wins — Days, Not Months)

1. **Compiled script caching** — sabse impactful, sabse easy fix. Roslyn compilation expensive hai; script text/hash ke basis pe compiled `Assembly` ko in-memory dictionary mein cache karo. Script change hone pe hi recompile karo (cache invalidate karke). Isse per-request latency aur CPU dono drastically kam ho jayenge.
2. **Dealer-specific scripts ko bhi cache karo** (abhi sirf global settings/scripts cache ho rahe hain) — TTL ya explicit invalidation (script update hote hi cache clear) ke saath.
3. **ASG scaling policies tune karo** — target-tracking scaling (CPU/request-count based) ke saath-saath **scheduled scaling** add karo for known peak hours (9am-6pm) — proactively instances warm rakho instead of reactive scale-out lag jhelna.
4. **RDS Read Replica (same-region) add karo** read-heavy queries (dashboard reads, reporting) offload karne ke liye, primary ko write-heavy import/export ke liye free rakho.
5. **DB connection pooling tune karo** — agar traffic badhega, connection exhaustion ek common bottleneck banta hai; pool size aur timeout settings ko load ke hisaab se tune karna.
6. **Idempotency keys add karo** import/export requests pe (dealId/requestId based) — retries (jo traffic badhne pe zyada hone lagenge) duplicate Customer/Vehicle/Deal na banayein.
7. **API Gateway throttling/usage plans properly configure karo** per-dealer — ek dealer ka traffic spike doosre dealers ko affect na kare (noisy-neighbor problem se bachne ke liye).
8. **Response compression (gzip)** enable karo — payload size kam, network transfer time kam, especially bade deal-data responses ke liye.
9. **New Relic dashboards/alerts fine-tune karo** — proactively bottlenecks spot karne ke liye (jaise "compile time badh raha hai" ya "DB connection wait time badh raha hai") before they become outages.

### 5.2 Medium-Term Improvements (Weeks — Some Rearchitecture, No Full Rewrite)

1. **Fix the atomicity gap** — Customer/Vehicle/Deal writes ko DB transaction mein wrap karo (ya proper compensating-action/saga-lite logic add karo) — traffic badhne pe partial-failure/orphan-record risk bhi badhega, ye ab priority ban jata hai.
2. **Move to async processing for import/export** — sync flow high-load pe thread/connection resources ko lambe samay tak hold karti hai. Request accept karo, queue karo (SQS), turant `requestId` return karo, processing background mein ho, result webhook/callback ya polling endpoint se milay. Isse system spikes ko gracefully absorb karta hai instead of timing out.
3. **In-memory cache ko distributed cache (Redis/ElastiCache) mein migrate karo** — abhi in-memory cache hai jo **per-ECS-instance** hai (har instance apna alag cache rakhta hai, restart pe lost ho jata hai, aur multiple instances ke beech inconsistent ho sakta hai). Jaise-jaise instances badhenge (scale-out), ye inconsistency zyada visible hogi. Redis se shared, consistent cache milega across all instances.
4. **Circuit breaker pattern add karo** third-party dealer system calls ke liye (Polly library jaisa kuch) — agar external system slow/down ho, fail-fast karo instead of threads ko block karke rakhna, jo traffic-heavy time pe cascade failure bana sakta hai.
5. **Collectible AssemblyLoadContext use karo** script engine mein — abhi compiled assemblies kabhi unload nahi hoti (memory leak risk, reference doc mein bhi flagged hai). Traffic badhne se ye leak fast ho jayega — is fix ko priority dena chahiye scale se pehle.
6. **Monolith ko partially split karo** — poori microservices migration na sahi, lekin **Dashboard** (low-volume, internal) aur **Import/Export API** (high-volume, external) ko alag services mein separate karo. Inke traffic patterns bahut alag hain — Import/Export ko independently scale karne ki flexibility milegi bina Dashboard ko unnecessarily scale kiye.

### 5.3 Major Infra Changes (If Traffic Genuinely Grows 10x+ or Business Scale Demands It)

1. **Full microservices split** — Dashboard, Import, Export, Script Management ko alag-alag independently deployable/scalable services banao. Isse team bhi independently kaam kar sakti hai, aur ek component ka issue poore system ko down nahi karega.
2. **Dedicated Script Execution Service** — Roslyn compilation CPU-intensive hai; isse ek alag scalable service (ya serverless — AWS Lambda, jo per-invocation scale karta hai) mein extract karo, taaki iska scaling API-handling layer se decoupled ho.
3. **Event-driven architecture** — Import/Export orchestration ko message broker (SQS+SNS, ya Kafka agar volume bahut high ho) se decouple karo. Isse downstream internal systems (jaise contract generation) events **subscribe** kar sakte hain instead of tightly-coupled synchronous calls — resilience aur scalability dono improve hoti hai.
4. **Database sharding/partitioning** — agar single RDS instance (even scaled-up) write-throughput ke liye insufficient ho jaye, dealer-based ya region-based sharding consider karo. *(Ye kaafi complex hai — sirf tab justify hoga jab genuinely bahut zyada scale ho, and should be last resort after vertical scaling/read-replicas exhausted ho.)*
5. **Fargate/EKS mein migrate karo** (from ECS EC2 launch type) — agar EC2 instance management operational overhead badhne lage, ya finer-grained auto-scaling chahiye ho container-level pe.
6. **Multi-region ACTIVE-ACTIVE (not just DR)** — agar business truly global/24x7-critical ho jaye, sirf passive DR se aage badhke active-active consider karo: dealers ko nearest region pe route karo (latency improve), data bidirectionally replicate karo (with conflict resolution strategy) — ye significant complexity add karta hai (consistency trade-offs), isliye sirf tab consider karo jab business requirement genuinely justify kare.

### How to Present This in Interview

Agar puchha jaye "scale kaise karoge", ye **teen-tier approach** mein answer dena best lagta hai:
> *"Pehle main low-effort, high-impact cheezein karunga — jaise compiled-script caching aur ASG scaling policies tune karna, kyunki ye bina architecture change kiye bahut fayda dete hain. Phir agar aur scale chahiye, main async processing aur distributed caching jaisi medium-term improvements introduce karunga. Aur sirf tab jab traffic genuinely 10x+ ho jaye ya business requirement demand kare, main full microservices split ya multi-region active-active jaisa major re-architecture propose karunga — kyunki wo complexity/cost bahut zyada hai, aur premature optimization avoid karna chahiye."*

Ye approach interviewer ko dikhata hai ki tum **pragmatic** ho — har problem ka solution "rewrite everything" nahi hota.

## 4. Interview Drill-Down Question Bank (Exhaustive)


### A. Scalability
1. **Q: 4K requests/day toh kaafi low hai — scaling ki zaroorat kab padegi?**
   A: Peak hours (9am-6pm) mein traffic concentrated hota hai — ASG CPU/request-based auto-scale policies configured hain taaki peak ke time extra EC2 instances spin ho jayein. Absolute volume kam hai but burst handling zaroori hai.
2. **Q: Script compilation (Roslyn) har request pe hoti hai — performance bottleneck nahi banta kya scale pe?**
   A: Haan, ye ek known risk hai (reference doc ke Cons section mein bhi hai) — per-call compilation expensive hai. Agar volume badhta hai, compiled-assembly caching add karni padegi (already-compiled script ko cache karke reuse karna, sirf script text change hone pe recompile).
3. **Q: Monolith scale kaise karte ho — agar sirf Import API pe load ho aur Dashboard pe nahi, to?**
   A: Chunki monolith hai, poori application hi scale hoti hai (extra EC2 instance = poora app replicate hota hai) — granular/independent scaling possible nahi hai. Ye microservices split ka ek valid argument ban sakta hai future improvement ke liye.
4. **Q: RDS scale kaise karoge agar write load badh jaye?**
   A: Vertical scaling (bigger instance class) ya read-replicas add karke read-heavy queries offload karna. Write scaling RDS mein fundamentally vertical hi hota hai (until sharding consider karo, jo complex hai).

### B. Availability
5. **Q: Agar ek EC2 instance (ECS host) crash ho jaye, to kya hota hai?**
   A: ALB health check fail detect karega, us instance ko traffic milna band ho jayega, ASG automatically naya instance launch karega replace karne ke liye.
6. **Q: RDS Multi-AZ failover ke dauraan application ko kya dikhta hai?**
   A: Thoda downtime (typically 60-120 seconds) hota hai failover ke dauraan jab tak connection re-establish na ho — application ko retry logic honi chahiye transient connection failures ke liye.
7. **Q: Poora region down ho jaye to?**
   A: Multi-region DR setup activate hota hai — assumed RDS replica ko promote karna, Route 53 failover se traffic naye region pe redirect karna. *(Exact RTO/RPO confirm karna interview se pehle.)*
8. **Q: Script Engine fail ho jaye (bad script deployed) to poora import/export flow down ho jata hai kya?**
   A: Validator component (reference doc mein mentioned) deploy se pehle script ko compile-check karta hai — isse bad scripts production tak pahunchne se pehle hi catch ho jati hain, reducing risk of runtime failures.

### C. Consistency & Data Integrity
9. **Q: Customer/Vehicle/Deal create karte time agar beech mein failure ho (partial write), to kya hota hai?**
   A: **Confirmed — ye atomic nahi hai.** Customer, Vehicle, Deal writes independent hain, single transaction mein wrap nahi hote. Agar Deal creation fail ho jaye Customer commit hone ke baad, Customer record reh jata hai without a deal. Ye ek conscious trade-off tha — long-running single transaction (jab script execution bhi beech mein chal rahi ho) DB locks/contention ka risk badhata, isliye consistency ko thoda weaken kiya gaya for better responsiveness. Mitigation: idempotency keys (duplicate-prevent karne ke liye retries pe) aur reconciliation jobs orphan records ke liye. *(Section 2.3 dekho poora reasoning ke liye.)*
10. **Q: Script logic galat translate kare to data corruption ka risk hai — kaise mitigate karte ho?**
    A: Validation layer before/after script execution — translated data ko schema/business-rule validate karna before DB write. Plus script validator (compile-check) deploy-time pe.

### D. Security
11. **Q: Script engine arbitrary C# code execute kar sakti hai — ye bada security risk nahi hai kya?**
    A: Haan, ye known risk hai (reference doc mein "Cons" section) — script *authoring* aur *storage* (S3) tak access tightly controlled hona chahiye (IAM permissions, sirf trusted onboarding team likh sake), taaki koi malicious script inject na kar sake.
12. **Q: External dealers ka access kaise isolate karte ho — ek dealer doosre dealer ka data na dekh sake?**
    A: Token (Okta) mein dealer/client identity embed hoti hai, application layer pe every query dealerId se scoped/filtered hoti hai. Script bhi dealerId-specific S3 path se hi fetch hoti hai — cross-dealer access by-design prevent hota hai.
13. **Q: Secrets (DB password, Okta client secret) kaise protect karte ho?**
    A: AWS Secrets Manager mein store, KMS se encrypted, application runtime pe securely fetch karta hai — kabhi code/config mein hardcode nahi.
14. **Q: WAF kya specific rules block karta hai yahan?**
    A: *(Generic answer if exact rules unknown)* — common OWASP Top 10 patterns (SQLi, XSS), rate-based rules against abuse/DDoS-like patterns from a single source.
15. **Q: WAF aur ALB dono already traffic filter/route karte hain — phir API Gateway ki zaroorat kyun padi?**
    A: WAF aur ALB generic network/HTTP-level protection aur load-balancing dete hain, lekin **API-specific management** nahi dete — jaise per-dealer API keys aur usage quotas, request-level throttling per client, ya token (Okta) validation before request backend tak pahunche. API Gateway ye extra layer add karta hai jo specifically **external API consumers ko manage karne** (kaun kitna use kar raha hai, kisko kitna allow hai) ke liye designed hai — ALB sirf traffic route karta hai, wo per-client business logic nahi samajhta.

### E. Performance
15. **Q: Sync flow hone se agar script execution slow ho (heavy translation logic), to caller ko lamba wait karna padta hai — acceptable hai?**
    A: Business requirement thi immediate confirmation ki — trade-off accept kiya gaya. Lekin agar script complexity/latency badhti jaye, future mein async (submit + webhook/poll) consider karna padega.
16. **Q: S3 se script fetch karna har request pe — latency add nahi karta?**
    A: Global scripts cache hoti hain (as mentioned) — dealer-specific scripts bhi cache ki ja sakti hain agar frequently used hon, reducing repeated S3 calls.

### F. Failure Handling & Resilience
17. **Q: Third-party dealer API down ho (import ke time unse data pull karna hai), to kya hota hai?**
    A: *(Confirm — timeout + retry logic honi chahiye, aur agar persistent failure ho to clear error response caller ko, logged for investigation.)*
18. **Q: Assembly memory leak (script engine doc mein mentioned) — is production issue ko kaise monitor/handle karte ho?**
    A: New Relic APM se memory usage trends track karna, aur periodic ECS task restarts (rolling restarts) ek mitigation ho sakta hai jab tak collectible AssemblyLoadContext jaisa proper fix implement na ho.

### G. Monitoring & Observability
19. **Q: New Relic + PagerDuty setup kaise kaam karta hai end-to-end?**
    A: New Relic APM agent application mein integrated hai — requests, errors, latency, custom transactions track karta hai. Threshold-based alerts (e.g., error rate > X%, response time > Y ms) configure hain jo PagerDuty ko trigger karte hain, jo on-call engineer ko notify karta hai.
20. **Q: Debugging ke liye request/response logs kaise use karte ho?**
    A: Har third-party call ka request/response S3 mein logged hota hai — issue investigate karte time specific dealer/timeframe ke logs pull karke actual payload dekh sakte hain (kya translate hua, kya error aaya).

### H. Cost & Trade-offs
21. **Q: Logs sirf 3 mahine retain karte ho — kyun, aur risk kya hai?**
    A: Cost control (S3 storage cost, GBs of daily logs) — trade-off ye hai ki agar 3 mahine se purana koi compliance/audit issue investigate karna ho to log unavailable hoga. Business requirement ke hisaab se ye acceptable window decide kiya gaya hoga.
22. **Q: EC2 launch type ECS mein kyun, Fargate kyun nahi?**
    A: *(Reasoning: cost — predictable/steady workload ke liye reserved/spot EC2 instances Fargate se cheaper pad sakte hain. Fargate ka fayda hai no server management, but EC2 zyada control aur potentially lower cost deta hai stable workloads ke liye.)*

### I. Monolith-Specific
23. **Q: Monolith se microservices split karne ka case banao — kab justify hoga?**
    A: Agar traffic significantly badhe, ya Dashboard aur Import/Export APIs ke scaling needs alag ho jayein, ya team size badhe (independent deployment cycles chahiye ho) — tab split justify hoga. Abhi 4K req/day scale pe monolith operational simplicity ka fayda deta hai.
24. **Q: Monolith mein ek buggy deploy poore system (Dashboard + APIs dono) ko down kar sakta hai — risk kaise manage karte ho?**
    A: Deployment slots/blue-green deployment strategy (agar hai — confirm), thorough testing/staged rollout, aur script-based logic changes ko application deploy se decouple karke (jo already kiya hua hai) is risk ko significantly reduce kiya gaya hai — business logic changes redeploy ki zaroorat hi nahi rakhte.

### J. Script Engine — Specific (Deep Dive)
25. **Q: DLL plugin pattern kyun use kiya — direct reference kyun nahi?**
    A: Loose coupling — engine DLL ko hot-swap/upgrade kar sakte hain bina orchestrator ko redeploy kiye. Reflection-based loading (`Assembly.LoadFrom`) explicit binding context control deta hai.
26. **Q: Compiled script cache nahi karte to performance risk hai — kya karoge is ko fix karne ke liye?**
    A: Compiled `Assembly` ko in-memory dictionary mein cache karo keyed by script-hash/version — agar script text change na hua ho to recompile skip karo, seedha cached assembly use karo.
27. **Q: Script fail/exception throw kare to kya hota hai caller ko?**
    A: "Return-no-exception" pattern (reference doc mein hai) — agar flag set ho to exception ko result dictionary mein return karte hain instead of bubbling up, taaki APM tools mein "unhandled error" na dikhe aur caller gracefully handle kar sake.
28. **Q: Global vs dealer-specific script mein conflict/precedence kaise decide hoti hai?**
    A: **Confirmed — no fallback.** Har request ke liye specific script (dealer-specific ya global, jo bhi applicable ho) directly resolve hoti hai; agar wo script missing hai ya execution fail hoti hai, system **fail-fast** approach leta hai — validation/internal error throw kar deta hai, kabhi silently doosri script pe switch nahi karta. Reasoning: tax/vehicle jaisa critical data domain mein silent fallback se wrong-script-processing ka risk hai jo detect karna mushkil hota — explicit failure better hai taaki issue turant pata chale aur fix ho sake.

### K. Multi-Region DR — Specific
29. **Q: DR kaise kaam karta hai yahan — walk me through it.**
    A: RDS ek **cross-region read replica** maintain karta hai DR region mein (async replication se continuously sync). Route 53 **health checks + failover routing policy** primary region ko monitor karti hai — agar primary unreachable ho, Route 53 automatically DNS ko DR region ke endpoint pe switch kar deta hai. RDS replica ko explicitly **promote** karna padta hai writable primary banane ke liye (auto nahi hota, safety ke liye). *(Poora detailed flow Section 1.2.1 mein hai.)*
30. **Q: RTO/RPO kya target tha DR ke liye?**
    A: Exact numbers documented/measured nahi the mere paas is project mein, lekin architecture ke hisaab se reasoning explain kar sakta hoon: RPO async replication lag pe depend karta hai (kuch seconds-minutes), RTO mein health-check detection + DNS propagation + manual replica promotion time shaamil hota hai.
31. **Q: RDS replica ko auto-promote kyun nahi karte, manual step kyun rakha?**
    A: Auto-promotion risky hai — agar temporary network blip ho (primary actually theek hai, bas thodi der ke liye unreachable dikha), auto-promote karne se **split-brain** situation ban sakti hai (do writable primaries, data conflict). Manual/controlled promotion safety deta hai, thoda RTO cost pe.
32. **Q: DR region mein scripts (S3) kaise available hote hain?**
    A: S3 Cross-Region Replication (CRR) configure hoti hai taaki scripts automatically doosre region ke bucket mein bhi replicate ho jayein.
33. **Q: Failback (wapas primary pe aana) kaise hota hai jab primary recover ho jaye?**
    A: Ye typically ek careful, manual process hai — data ko DR se wapas primary mein sync karna padta hai (reverse direction), phir Route 53 traffic wapas primary pe switch karte hain. Auto-failback avoid karte hain kyunki iske beech data-loss/conflict ka risk hota hai.

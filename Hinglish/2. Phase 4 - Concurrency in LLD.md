# PART A — Must-Know Primitives

> Inhe practical rakho. (Deep theory — memory model, happens-before — alag fundamentals file mein reh sakti hai.) Yahan focus hai ki **design mein kab kaunsa use karein** aur **thread-safety angle** kya hai.

<a id="a1-lock--monitor"></a>
## A1. `lock` / Monitor

**Hinglish mein:** `lock` statement ek *washroom ka lock* hai — ek time pe sirf ek banda andar (mutual exclusion). Baaki wait karte hain. Iska doosra fayda: jo changes tumne lock ke andar kiye, woh agle thread ko dikhengi (memory visibility). `lock (obj) { ... }` andar-andar `Monitor.Enter(obj)` / `Monitor.Exit(obj)` mein compile hota hai, aur woh `try/finally` mein wrap hota hai — isliye exception aaye tab bhi lock hamesha release ho jaata hai. Jab bhi tumhe "pehle padho, phir badlo, phir likho" wala compound operation atomic chahiye (jaise `count++`), tab `lock` lagao. Sabse simple aur reliable — pehle isse solve karo, baad mein optimize.

```csharp
class Counter
{
    private int _count = 0;

    // Private lock object — jis object pe lock lagao usse kabhi expose mat karo
    private readonly object _lock = new object();

    public void Increment()
    {
        lock (_lock)
        {
            _count++; // read-modify-write: lock ke bina NOT atomic
        }
    }

    // Critical section chhoti rakho: non-critical kaam lock ke bahar karo
    public void IncrementBlock()
    {
        // ... yahan non-critical kaam (koi lock nahi) ...
        lock (_lock)
        {
            _count++;
        }
    }

    public int Get()
    {
        lock (_lock) { return _count; }
    }
}
```

Ek simple atomic counter ke liye lock ki zaroorat bhi nahi — `Interlocked.Increment(ref _count)` ek lock-free, atomic read-modify-write hai.

**Interview points / pitfalls:**
- `this`, ek `Type`, ya kisi bhi publicly reachable object pe lock lagana tumhara lock leak kar deta hai — bahar ka code usi monitor pe lock lekar surprises de sakta hai. **`private readonly object _lock` use karo.**
- Kabhi value type pe `lock` mat karo (woh box hota hai — har `lock` alag box dekhega) ya `string` pe (interned strings poore process mein shared hoti hain).
- `lock`/Monitor **reentrant** hai: same thread jo monitor already hold kar raha hai use dobara le sakta hai.
- Slow I/O ke dauraan lock hold karna throughput maar deta hai — critical sections **chhoti** rakho. `lock` ke andar `await` kabhi mat karo (kar bhi nahi sakte, aur woh thread switch ke across monitor hold karega).
- Do locks alag order mein alag threads ne liye → **deadlock**. Hamesha ek consistent global order mein lo.
- Reads ko bhi **visibility** ke liye synchronization chahiye, sirf writes ko nahi.

<a id="a2-volatile--volatile"></a>
## A2. `volatile` & `Volatile`

**Hinglish mein:** `volatile` keyword ka kaam hai "hamesha fresh value dikhao" (visibility) aur field ke aaspaas kuch instruction reordering rokna — lekin yeh *atomicity nahi deta* compound operations ke liye. Socho ek notice board hai (volatile): jaise hi koi update likhta hai, sab turant dekh lete hain. Par agar do log ek saath board pe "+1" karne aayein, to bhi galti ho sakti hai. Isliye `volatile` sirf **flag** ke liye (jaise `bool _running` jo ek thread set kare aur baaki padhein), counter ke liye nahi. `Volatile.Read(ref x)` / `Volatile.Write(ref x)` method-based equivalents hain jab tum ek normal field pe per-access volatile semantics chahte ho.

```csharp
class Worker
{
    private volatile bool _running = true; // visibility across threads

    public void Stop() => _running = false; // ek writer

    public void Run()
    {
        while (_running)   // many-reader flag: yahan volatile ENOUGH hai
        {
            DoWork();
        }
    }

    private void DoWork() { /* ... */ }
}

// volatile yahan ENOUGH NAHI hai:
class BadCounter
{
    private volatile int _count = 0;
    public void Inc() => _count++; // BUG: read-modify-write, atomic nahi
    // Fix: Interlocked.Increment(ref _count) ya lock use karo
}
```

Atomic counters ke liye `Interlocked.Increment(ref _count)` use karo (thread-safe `++` ka sahi tareeka).

**Interview points / pitfalls:**
- **Iske liye kaafi:** single-writer / multi-reader flags, ek immutable object reference publish karna.
- **Iske liye NAHI kaafi:** counters, check-then-act, koi bhi compound action → `Interlocked` ya lock use karo.
- Reference pe `volatile` sirf *reference* ko visible banata hai, object ke andar ke fields deeply nahi.
- `volatile` `long`/`double`/`ulong` fields pe nahi lag sakta (woh 64-bit hain; unke liye `Interlocked` ya `Volatile.Read/Write`).
- Yeh lock se sasta hai (koi blocking nahi) par sirf visibility/ordering solve karta hai, mutual exclusion nahi.

<a id="a3-explicit-locks"></a>
## A3. Explicit locks: `Monitor.TryEnter` & `ReaderWriterLockSlim`

**Hinglish mein:** `lock` statement simple case cover karta hai, par kabhi-kabhi zyada chahiye. `Monitor.TryEnter(obj, timeout)` tumhe **non-blocking ya timed** acquire deta hai taaki tum hamesha ke liye wait na karo ("agar lock time pe mile to le lo, warna chhod do" — deadlock se bachaav). `ReaderWriterLockSlim` mein **bahut saare readers ek saath** access share karte hain jabki **writer akela (exclusive)** hota hai — read-heavy shared state ke liye perfect. Coordinated wait/signal ke liye `Monitor.Wait` / `Monitor.Pulse` / `Monitor.PulseAll` low-level primitives hain, aur `SemaphoreSlim` (uska `WaitAsync` bhi) modern async-friendly choice hai.

```csharp
using System;
using System.Threading;

class Account
{
    private readonly object _lock = new object();
    private double _balance;

    public void Deposit(double amt)
    {
        lock (_lock)
        {
            _balance += amt;   // critical section
        }
    }

    // Monitor.TryEnter: hamesha ke liye block mat karo — bail out ya retry
    public bool TransferIfFree(Account to, double amt)
    {
        bool taken = false;
        try
        {
            Monitor.TryEnter(_lock, TimeSpan.FromMilliseconds(500), ref taken);
            if (!taken) return false; // time pe lock nahi mila

            if (_balance >= amt)
            {
                _balance -= amt;
                to.Deposit(amt);
                return true;
            }
            return false;
        }
        finally
        {
            if (taken) Monitor.Exit(_lock); // release HAMESHA finally mein
        }
    }
}
```

**Reader/writer separation** read-heavy data ke liye:

```csharp
using System.Threading;

class SettingsStore
{
    private readonly ReaderWriterLockSlim _rw =
        new ReaderWriterLockSlim(LockRecursionPolicy.NoRecursion);
    private string _value = "";

    public string Read()
    {
        _rw.EnterReadLock();               // bahut saare readers ek saath
        try { return _value; }
        finally { _rw.ExitReadLock(); }
    }

    public void Write(string v)
    {
        _rw.EnterWriteLock();              // writer exclusive
        try { _value = v; }
        finally { _rw.ExitWriteLock(); }
    }
}
```

**Plain `lock` se aage kab jaayein:**
| Need | `lock` (Monitor) | Explicit API |
|------|------------------|--------------|
| Simple mutual exclusion | Best (auto-release) | — |
| Timed / non-blocking acquire | Nahi | `Monitor.TryEnter(obj, timeout, ref taken)` |
| Read/write separation | Nahi | `ReaderWriterLockSlim` |
| Async-friendly gate | Nahi (`lock` mein `await` nahi) | `SemaphoreSlim.WaitAsync()` |
| Condition wait/signal | — | `Monitor.Wait/Pulse/PulseAll` |

**Interview points / pitfalls:**
- **Release bhoolna** (`Monitor.Exit` / `ExitReadLock` / `ExitWriteLock`) `finally` ke bahar → permanent lock leak. `lock` keyword yeh avoid karta hai; raw APIs nahi karte.
- `ReaderWriterLockSlim` ka real cost hai — bahut chhoti critical sections ke liye plain `lock` aksar fast hota hai. RW locks tabhi use karo jab reads sach mein dominate karein aur non-trivial hon.
- Bahut readers ke saath **writer starvation** ka dhyaan rakho; `LockRecursionPolicy` aur upgradeable read locks careful use karo.
- Simple cases ke liye `lock` keyword prefer karo (kam error-prone); explicit APIs tabhi jab unke features chahiye.

<a id="a4-threadpool--tpl"></a>
## A4. ThreadPool & Task Parallel Library (TPL)

**Hinglish mein:** Har task ke liye naya raw `Thread` banana galti hai — thread mehenga hai, aur unlimited threads banaoge to process crash. Iske badle kaam ko shared **`ThreadPool`** pe bhejo **Task Parallel Library** ke through: `Task` / `Task.Run` pooled worker threads reuse karte hain, result ka handle dete hain (`Task<T>`), aur cancel/await allow karte hain. Ek fixed team of workers jo tasks baari-baari uthate hain (jaise restaurant mein 5 waiters, unlimited orders — waiters reuse hote hain). **Size** workload pe depend karta hai: CPU-heavy kaam ko `Environment.ProcessorCount` ke aas-paas cap karo; I/O-bound kaam ko threads pe baithao hi mat — usse `await` karo. Jab throughput overwhelm kar sake to **back-pressure** chahiye (throttle ya bound karo) taaki overload OOM na ban jaaye.

**`Task` / `Task.Run` / `Task.WhenAll`** — pool pe kaam chalane ka default tareeka:
```csharp
using System.Linq;
using System.Threading.Tasks;

// Task.Run delegate ko shared .NET ThreadPool pe schedule karta hai
Task<int> t = Task.Run(() => ExpensiveComputation()); // Task<T> = result handle

int result = await t;                                  // non-blocking await (koi thread hold nahi)

// Fan out and join — bahut tasks chalao, sabko await karo
Task<int>[] tasks = keys.Select(k => Task.Run(() => Compute(k))).ToArray();
int[] all = await Task.WhenAll(tasks);
```

**`Parallel.ForEach`** — ek collection pe data parallelism (items ko pool threads mein partition karta hai):
```csharp
Parallel.ForEach(items,
    new ParallelOptions { MaxDegreeOfParallelism = Environment.ProcessorCount },
    item => Process(item));   // MaxDegreeOfParallelism effective pool width cap karta hai
```

**`async/await` aur thread pool:** Genuinely I/O-bound kaam (`HttpClient`, DB, file) pe `await` wait karte waqt thread hold **nahi** karta — thread wapas pool mein chala jaata hai aur I/O complete hone pe continuation schedule hoti hai. Isliye I/O concurrency ke liye tum pool size karte hi nahi; bas bahut saare tasks `await` karte ho. `Task.Run` sirf **CPU-bound** kaam ko current (jaise UI) thread se hataane ke liye use karo — already-async I/O ko `Task.Run` mein wrap mat karo.

**Sizing / back-pressure .NET mein:** `ThreadPool` apni worker count khud auto-tune karta hai, isliye tum use direct set shayad hi karte ho. CPU-bound fan-out ko `MaxDegreeOfParallelism` se cap karo; concurrent async kaam ko ek `SemaphoreSlim(n)` gate se throttle karo; producer/consumer pipelines ke liye `System.Threading.Channels` (bounded) use karo jo automatically back-pressure deta hai.

```csharp
// I/O fan-out throttle karo taaki hazaaron concurrent calls na chalein
var gate = new SemaphoreSlim(initialCount: 10); // max 10 in flight

async Task<Result> CallThrottled(Key k)
{
    await gate.WaitAsync();
    try { return await CallServiceAsync(k); }
    finally { gate.Release(); }
}

var results = await Task.WhenAll(keys.Select(CallThrottled));
```

**Interview points / pitfalls:**
- Async pe block mat karo: `Task` pe `.Result` / `.Wait()` avoid karo (deadlock risk + pool thread waste) — `await` karo.
- `Task.Run` CPU-bound offloading ke liye hai, I/O ko "async" banane ke liye nahi — I/O `await` se already async hai.
- CPU-bound parallelism `~ Environment.ProcessorCount` tak cap karo; I/O fan-out ko `SemaphoreSlim` se throttle karo taaki hazaaron concurrent calls launch na hon.
- Exceptions tab surface hoti hain jab tum task ko `await` karte ho (ya `task.Exception` se); ek unobserved faulted task chup-chaap swallow ho sakta hai.
- Scheduled/recurring kaam ke liye `System.Threading.Timer` ya `PeriodicTimer`; long-running dedicated kaam ke liye `Task.Factory.StartNew(..., TaskCreationOptions.LongRunning)` pool thread ke bajaye ek dedicated thread deta hai.

<a id="a5-thread-safe-singleton"></a>
## A5. Thread-safe Singleton

**Hinglish mein:** Singleton ka matlab: poore app mein object ki *sirf ek* copy (jaise ek office ka ek hi CEO). Challenge yeh hai ki multi-threaded environment mein galti se do CEO na ban jaayein, aur har baar access pe lock lagakar slow bhi na ho. Achhi baat: .NET mein runtime yeh sab khud handle kar leta hai, tumhe manually lock likhne ki zaroorat hi nahi. Do recommended tareeke: `Lazy<T>` aur static field / static constructor pattern.

**1) `Lazy<T>` (idiomatic, by default thread-safe)**
```csharp
public sealed class Config
{
    // ExecutionAndPublication DEFAULT hai: factory ek baar chalti hai, result safely publish
    private static readonly Lazy<Config> _instance =
        new Lazy<Config>(() => new Config());

    private Config() { }

    public static Config Instance => _instance.Value; // lazy: pehle access pe banta hai
}
```
- Lazy + thread-safe with **zero manual locking**. Default mode `LazyThreadSafetyMode.ExecutionAndPublication` guarantee deta hai ki factory race mein bhi exactly ek baar chale; baaki threads block hote hain jab tak woh complete na ho, phir sab same instance dekhte hain.
- "Lazy + fast + safe" paane ka sabse saaf tareeka — code na ke barabar.

**2) Static field / static constructor (`static readonly`)**
```csharp
public sealed class Config
{
    // CLR guarantee: static-field init ek baar, thread-safely, first use se pehle
    private static readonly Config _instance = new Config();

    private Config() { }

    public static Config Instance => _instance;
}
```
- CLR ki type-initialization guarantee se thread-safe. Tumhare code mein koi lock nahi.
- Laziness ka note: `beforefieldinit` (default jab koi explicit static constructor nahi) ke saath runtime first field use se pehle kabhi bhi eagerly-ish init kar *sakta* hai. Strict "type ko pehli baar touch karne pe hi init" laziness chahiye to ek explicit `static Config() { }` constructor daalo.

**Kyun preferred hai C# mein:** Runtime khud ek one-time, thread-safe initialization deta hai — `Lazy<T>` se ya static field/static-ctor semantics se — isliye manual double-checked locking likhna unnecessary + error-prone hai. Factory ya thread-safety mode pe control chahiye → `Lazy<T>`; object sasta hai aur hamesha chahiye → `static readonly`.

**Trade-off summary:**
| Approach | Lazy? | Locking cost | Notes |
|----------|-------|--------------|-------|
| **`Lazy<T>`** | Haan | Koi nahi (runtime-managed) | **Recommended**; factory ek baar chalti hai |
| **`static readonly`** | Effectively (note dekho) | Koi nahi | Best jab object sasta + hamesha chahiye |
| Getter mein manual `lock` | Haan | Har call (ya double-check chahiye) | Kaam karta hai par error-prone — avoid; `Lazy<T>` use karo |

**Interview points / pitfalls:**
- `Lazy<T>` (ya `static readonly`) se lead karo — bolo ki runtime one-time thread-safe init guarantee karta hai isliye manual locking nahi likhni padti.
- Double-checked locking poochein to: yeh woh manual pattern hai (`if (null) { lock { if (null) ... } }`) jo doosre ecosystems ko chahiye; ek subtle reordering bug reference ko constructor complete hone se pehle publish kar sakta hai. `Lazy<T>` yeh gap band kar deta hai, isliye C# mein tum yeh kabhi haath se nahi likhte.
- `Lazy<T>` gotcha: `LazyThreadSafetyMode.None` aur `PublicationOnly` run-once guarantee **nahi** dete — default `ExecutionAndPublication` deta hai.
- Tests mein singletons se savdhaan (global state) — modern alternative ke roop mein dependency injection mention karo (type ko DI container mein **singleton lifetime** ke saath register karo, jaise `services.AddSingleton<Config>()`).

<a id="a6-producerconsumer-pattern"></a>
## A6. Producer–Consumer pattern

**Hinglish mein:** Producer kaam banata hai, consumer kaam karta hai, aur beech mein ek **bounded blocking collection** dono ki speeds ko decouple karti hai (jaise restaurant ka kitchen order-rack). `BlockingCollection<T>` saara synchronization sambhaal leta hai: `Add()` full hone pe block karta hai (**back-pressure** — tez producer ko rok deta hai), `Take()` empty hone pe block karta hai (consumers sasti idle-wait). Modern .NET isi pattern ke liye `System.Threading.Channels` (`Channel<T>`) prefer karta hai — clean `async` API ke saath. Pipelines/task ingestion/log processing ke liye first-choice pattern.

**`BlockingCollection<T>`** (default mein `ConcurrentQueue<T>` wrap karta hai):
```csharp
using System.Collections.Concurrent;

class PC
{
    // bounded => back-pressure; full hone pe producers block
    private readonly BlockingCollection<int> _queue =
        new BlockingCollection<int>(boundedCapacity: 100);

    public void Producer()
    {
        for (int i = 0; ; i++)
            _queue.Add(i);                 // full ho to blocks
        // "aur items nahi" signal karne ke liye _queue.CompleteAdding() call karo
    }

    public void Consumer()
    {
        foreach (int item in _queue.GetConsumingEnumerable()) // empty ho to blocks
        {
            Process(item);                 // CompleteAdding() call hone pe cleanly exit
        }
    }

    private void Process(int x) { /* ... */ }
}
```

**`System.Threading.Channels`** — modern, async-first choice:
```csharp
using System.Threading.Channels;

var channel = Channel.CreateBounded<int>(new BoundedChannelOptions(100)
{
    FullMode = BoundedChannelFullMode.Wait   // back-pressure: full hone pe writer await karta hai
});

// Producer
async Task ProduceAsync()
{
    for (int i = 0; i < 1000; i++)
        await channel.Writer.WriteAsync(i); // full hone pe await (koi thread hold nahi)
    channel.Writer.Complete();              // completion signal
}

// Consumer
async Task ConsumeAsync()
{
    await foreach (int item in channel.Reader.ReadAllAsync())
        Process(item);
}
```

**Interview points / pitfalls:**
- **Production mein collection/channel hamesha bound karo** — unbounded ek slow consumer ko OOM crash bana deta hai.
- Consumers ko cleanly band karne ke liye poison-pill sentinel ke bajaye `CompleteAdding()` / `Writer.Complete()` (ek graceful "aur items nahi" signal) use karo.
- Agar collection/channel fit ho to low-level wait/signal khud mat likho — woh tricky parts already sahi karta hai. (Low-level primitive `Monitor.Wait`/`Monitor.Pulse` hai, par modern C# `SemaphoreSlim`, `BlockingCollection<T>`, ya `Channels` prefer karta hai.)
- Multiple producers/consumers naturally scale karte hain; collection/channel single synchronization point hai.
- `BlockingCollection<T>` timeouts aur `CancellationToken` ke saath `TryAdd`/`TryTake` bhi support karta hai — responsive shutdown ke liye inhe use karo.

## B1. Thread-safe Cache

### Requirements
**Hinglish mein:** Ek in-memory key→value store jismein `Get(k)` aur `Put(k,v)` ho, ek max size ho **LRU eviction** ke saath (bhar jaaye to sabse purana kam-use hua item nikaalo), optional **TTL** (items time ke baad expire), heavy concurrent reads/writes mein safe rahe, aur **cache stampede** se bache (ek hi key ke liye 100 threads ek saath DB hit na karein).

### Class design
| Component | Role |
|-----------|------|
| `ConcurrentDictionary<K, CacheEntry<V>>` | Store — lock-striped, high concurrency |
| `CacheEntry<V>` | Value + `ExpiryAt` rakhta hai (TTL ke liye) |
| Eviction policy | LRU ordering (access order) |
| `GetOrAdd` (with `Lazy<T>`) | Atomic "get-or-load", per-key stampede solve karta hai |

### Thread-safety strategy
**Hinglish mein:** `ConcurrentDictionary` isliye kyunki yeh reads ko parallel chalne deta hai aur writes ke liye **fine-grained (bucket-level) locking** karta hai — poore `Dictionary` ko ek `lock` mein wrap karne se bahut fast. Simple get-or-compute ke liye `GetOrAdd(k, factory)` existing value return karta hai ya nayi add karta hai; par ek **.NET gotcha** yaad rakho: race mein `factory` **ek se zyada baar** chal sakti hai (sirf ek winner ka result store hota hai). Sach mein "loader per key exactly ek baar chale" (jo stampede rokta hai) chahiye to value ke roop mein ek `Lazy<V>` store karo — tab `GetOrAdd` bhale kai `Lazy` wrappers banaye, par sirf winner ka `.Value` evaluate hota hai, to expensive loader ek hi baar chalta hai. Jab operation **multiple keys/structures ko ek saath atomically** touch kare (jaise size ≤ capacity rakhne ke liye evict-and-insert, ya external LRU list ke saath coordinate), tab **explicit lock** chahiye, kyunki `ConcurrentDictionary` sirf single-key operations ko atomic banata hai.

### C# skeleton
```csharp
using System;
using System.Collections.Concurrent;
using System.Collections.Generic;

class ThreadSafeCache<K, V> where K : notnull
{
    private sealed class Entry
    {
        public readonly V Value;
        public readonly long ExpiryAt;   // epoch millis; long.MaxValue = never
        public Entry(V value, long expiryAt) { Value = value; ExpiryAt = expiryAt; }
        public bool IsExpired() =>
            DateTimeOffset.UtcNow.ToUnixTimeMilliseconds() > ExpiryAt;
    }

    private readonly ConcurrentDictionary<K, Lazy<Entry>> _map = new();
    private readonly int _capacity;
    private readonly long _ttlMillis;

    // Access-ordered LRU tracking — thread-safe NAHI, isliye lock se guard karo
    private readonly LinkedList<K> _lruOrder = new();      // front = most recent
    private readonly Dictionary<K, LinkedListNode<K>> _lruNodes = new();
    private readonly object _evictionLock = new object();

    public ThreadSafeCache(int capacity, long ttlMillis)
    {
        _capacity = capacity;
        _ttlMillis = ttlMillis;
    }

    public bool TryGet(K key, out V value)
    {
        value = default!;
        if (!_map.TryGetValue(key, out var lazy)) return false; // lock-free read
        var e = lazy.Value;
        if (e.IsExpired())
        {
            _map.TryRemove(key, out _);                         // lazy TTL expiry
            return false;
        }
        Touch(key);                                             // recently used mark
        value = e.Value;
        return true;
    }

    // get-or-load: Lazy<T> se cache stampede rokta hai (loader per key exactly ek baar)
    public V GetOrLoad(K key, Func<K, V> loader)
    {
        var lazy = _map.GetOrAdd(key,
            k => new Lazy<Entry>(() => new Entry(loader(k), Expiry())));
        var e = lazy.Value;                                     // sirf EK loader chalta hai
        if (e.IsExpired())
        {
            _map.TryRemove(key, out _);
            return GetOrLoad(key, loader);                      // expiry pe reload
        }
        Touch(key);
        return e.Value;
    }

    public void Put(K key, V value)
    {
        _map[key] = new Lazy<Entry>(new Entry(value, Expiry()));
        Touch(key);
        EvictIfNeeded();                                        // multi-key op → lock chahiye
    }

    private void Touch(K key)
    {
        lock (_evictionLock)
        {
            if (_lruNodes.TryGetValue(key, out var node))
                _lruOrder.Remove(node);
            _lruNodes[key] = _lruOrder.AddFirst(key);           // most recent front pe
        }
    }

    private void EvictIfNeeded()
    {
        lock (_evictionLock)
        {
            while (_map.Count > _capacity && _lruOrder.Last != null)
            {
                K eldest = _lruOrder.Last.Value;                // least recently used
                _lruOrder.RemoveLast();
                _lruNodes.Remove(eldest);
                _map.TryRemove(eldest, out _);
            }
        }
    }

    private long Expiry() =>
        _ttlMillis <= 0
            ? long.MaxValue
            : DateTimeOffset.UtcNow.ToUnixTimeMilliseconds() + _ttlMillis;
}
```
> Note: real applications ke liye built-in `Microsoft.Extensions.Caching.Memory.MemoryCache` / `IMemoryCache` prefer karo — yeh TTL (absolute/sliding expiration), size limits, aur eviction callbacks out of the box deta hai, hand-rolled cache se kahin efficiently. Interview mein yeh dikhana ki tumhe pata hai **lock kahan chahiye** (multi-key eviction) aur **kahan nahi** (single-key `GetOrAdd`) — yahi key insight hai.

**Interview talking points / pitfalls:**
- **`ConcurrentDictionary` kyun, `lock`ed `Dictionary` kyun nahi?** Doosra poore map ko per operation lock karta hai; `ConcurrentDictionary` bucket-level locking karta hai → bahut zyada read/write concurrency, aur reads lock-free hain.
- **Stampede ke liye `GetOrAdd`:** **main .NET gotcha** yeh hai ki race mein factory kai baar chal sakti hai. Value ko `Lazy<V>` mein wrap karo taaki expensive loader per key exactly ek baar chale; baaki usi `Lazy` pe block karte hain.
- **TTL strategies:** lazy (read pe check, upar dikhaya) vs. active (ek background `Timer`/`PeriodicTimer` sweeper). Lazy simple hai par kabhi-na-read hone wali keys ke liye memory leak karta hai — dono mention karo. `MemoryCache` yeh tumhare liye handle karta hai.
- **LRU + concurrency sach mein mushkil hai** — plain `LinkedList`/`Dictionary` thread-safe nahi, isliye lock-guard karna padega; woh lock bottleneck ban sakta hai. Real libs use shard karti hain.
- **Stampede alternatives:** request coalescing (`Lazy<T>` + `GetOrAdd`), stale-while-revalidate, jittered TTLs taaki expiry synchronize na ho.

<a id="b2-rate-limiter"></a>
## B2. Rate Limiter

### Requirements
**Hinglish mein:** Har client (key) ko allowed: max **N requests per time-window**. Thread-safe ho (bahut requests concurrently hit karti hain), low-overhead ho, aur ideally smooth ho (window edges pe bade bursts na hon). Do classic algorithms banao: **Token Bucket** aur **Sliding Window**.

### Algorithm 1 — Token Bucket
**Hinglish mein:** Ek balti (bucket) mein max `capacity` tokens, aur fixed rate se tokens bharte rehte hain (jaise 10 tokens/sec, nal se paani). Har request ek token uthaati hai; token nahi to reject (ya wait). Fayda: chhoti **burst** allowed (balti bhari ho to), par lambe time ka average rate control mein. Thread-safe: refill + consume ek hi atomic critical section mein hona chahiye.

```csharp
using System.Diagnostics;

class TokenBucket
{
    private readonly long _capacity;       // max tokens
    private readonly double _refillPerMs;  // per millisecond add hone wale tokens
    private double _tokens;                // current tokens (fractional refill ke liye double)
    private long _lastRefillMs;            // last refill timestamp (monotonic)
    private readonly object _lock = new object();

    public TokenBucket(long capacity, double tokensPerSecond)
    {
        _capacity = capacity;
        _refillPerMs = tokensPerSecond / 1000.0;
        _tokens = capacity;
        _lastRefillMs = Stopwatch.GetTimestamp() * 1000 / Stopwatch.Frequency;
    }

    // Ek lock refill+consume compound operation ko guard karta hai
    public bool TryAcquire()
    {
        lock (_lock)
        {
            Refill();
            if (_tokens >= 1) { _tokens -= 1; return true; }
            return false; // rate exceeded
        }
    }

    private void Refill()
    {
        long now = Stopwatch.GetTimestamp() * 1000 / Stopwatch.Frequency; // monotonic ms
        double add = (now - _lastRefillMs) * _refillPerMs;
        if (add > 0)
        {
            _tokens = System.Math.Min(_capacity, _tokens + add); // capacity se zyada kabhi nahi
            _lastRefillMs = now;
        }
    }
}

// Per-client: ConcurrentDictionary<string, TokenBucket>, ek bucket per key
```

### Algorithm 2 — Sliding Window (log / counter)
**Hinglish mein:** Pichhle window (jaise 1 min) ke saare request timestamps rakho. Nayi request aaye to pehle purane (`now - window` se bahar) timestamps hatao, phir agar bache hue count `< limit` hai to allow. Fixed-window se zyada accurate (boundary pe double-burst nahi hoti), par har request ka timestamp store karna padta hai (memory cost). Sasta approximation: **sliding-window-counter** — do adjacent fixed buckets ka weighted average.

```csharp
using System.Collections.Generic;
using System.Diagnostics;

class SlidingWindowLimiter
{
    private readonly int _limit;
    private readonly long _windowMs;
    private readonly Queue<long> _timestamps = new();
    private readonly object _lock = new object();

    public SlidingWindowLimiter(int limit, long windowMs)
    {
        _limit = limit;
        _windowMs = windowMs;
    }

    public bool Allow()
    {
        long now = Stopwatch.GetTimestamp() * 1000 / Stopwatch.Frequency; // monotonic ms
        lock (_lock)
        {
            // window ke bahar wale timestamps evict karo
            while (_timestamps.Count > 0 && _timestamps.Peek() <= now - _windowMs)
                _timestamps.Dequeue();

            if (_timestamps.Count < _limit)
            {
                _timestamps.Enqueue(now);
                return true;
            }
            return false;
        }
    }
}
```

### Trade-offs
| Algorithm | Accuracy | Memory | Bursts | Notes |
|-----------|----------|--------|--------|-------|
| Fixed window counter | Low (boundary spikes) | Tiny | Edges pe 2×limit allow | Simplest |
| **Token bucket** | Good | Tiny (kuch numbers) | Controlled bursts allow | Great default; smooth avg |
| **Sliding window log** | Highest | High (per-request) | Strict | Accurate par memory-heavy |
| Sliding window counter | Good | Tiny | Edges smooth karta hai | Best memory/accuracy balance |

**Built-in option:** .NET 7+ ke saath `System.Threading.RateLimiting` aata hai — `TokenBucketRateLimiter`, `SlidingWindowRateLimiter`, `FixedWindowRateLimiter`, aur `ConcurrencyLimiter` built-in — aam taur pe tum inhe use karoge (async `AcquireAsync`, queueing, permit counts support karte hain) bajaye hand-roll karne ke. Distributed limiting ke liye state Redis mein rakho (jaise `INCR`+`EXPIRE` ya Lua token-bucket script).

**Interview talking points / pitfalls:**
- **Per-client isolation:** ek `ConcurrentDictionary<string, Limiter>` rakho; unbounded growth se savdhaan (idle clients evict karo — upar wale cache design se tie karo).
- **Single-node vs distributed:** in-memory limiters N app servers ke across nahi tikte. Bolo "distributed ke liye state Redis mein atomic Lua script ke saath, ya Redis mein token bucket."
- **Token bucket vs leaky bucket:** leaky bucket output ko constant rate pe smooth karta hai (queue), token bucket bursts allow karta hai. Difference jaano.
- **Clock issues:** wall-clock (`DateTime.UtcNow`) ke bajaye monotonic time (`Stopwatch.GetTimestamp()`) use karo — wall-clock jumps (NTP, DST) misbehave kar sakte hain.
- Critical section tiny rakho (bas refill+consume / evict+check).

## B3. Parking Lot with concurrent access

### Requirements
**Hinglish mein:** Multi-level parking lot. Vehicles (bike/car/truck) andar aate hain, unhe **nearest available compatible spot** milta hai, ek **ticket** milti hai, aur exit pe spot free hota hai + fee calculate. Kai entry/exit gates ek saath kaam karte hain (**concurrent**) — do gaadiyon ko same spot na mile, lot full ho to saaf message mile, aur free-spot count race conditions mein bhi sahi rahe.

### Entities
| Entity | Responsibility |
|--------|----------------|
| `ParkingLot` (singleton) | Levels rakhta hai; entry/exit route karta hai |
| `Level` | Spots rakhta hai; apne andar allocate/free (lock scope) |
| `ParkingSpot` | Ek spot; `SpotType`, occupied flag, `AssignedTo` |
| `Ticket` | SpotId, vehicle, entry time, (exit time, fee) |
| `Vehicle` / subtypes | `Motorcycle`, `Car`, `Truck` (+ size compatibility) |
| `SpotType` enum | `Small`, `Medium`, `Large` |

### Thread-safety strategy
**Hinglish mein:** Contested shared state hai "kaunse spots free hain." Do safe designs:
1. **Level ke hisaab se lock (coarse-ish, simple):** har `Level` ka apna `lock` object; spot dhundhna + occupy karna usi lock ke andar. Alag levels parallel chalte hain, sirf same-level operations line mein aate hain. Simple aur correct.
2. **Lock-free per spot (`Interlocked.CompareExchange`):** har spot ka occupied flag ek `int` (0/1); claim karne ke liye `Interlocked.CompareExchange(ref _occupied, 1, 0) == 0` — jo CAS jeeta usse spot mila, haarne wale agla spot try karte hain. Saath mein ek `Interlocked`-updated free-count taaki "lot full hai?" O(1) mein pata chale.

Interview mein clarity ke liye **per-level lock** best hai; CAS ko "high-concurrency optimization" ke roop mein mention kar do. Har level ka ek counter (`Interlocked` se update) rakho taaki "nearest available" scans aur "full lot" checks ke liye sirf count karne ke liye full lock na lagana pade.

### C# skeleton
```csharp
using System;
using System.Collections.Concurrent;
using System.Collections.Generic;
using System.Threading;

enum VehicleType { Motorcycle, Car, Truck }
enum SpotType { Small, Medium, Large }

class Vehicle
{
    public string Plate { get; }
    public VehicleType Type { get; }
    public Vehicle(string plate, VehicleType type) { Plate = plate; Type = type; }
}

class ParkingSpot
{
    public string Id { get; }
    public SpotType Type { get; }

    // Lock-free claim: CAS 0 -> 1 spot jeet leta hai (C# mein AtomicBoolean nahi; int use karo)
    private int _occupied = 0;
    private volatile Vehicle? _vehicle;

    public ParkingSpot(string id, SpotType type) { Id = id; Type = type; }

    public bool TryOccupy(Vehicle v)
    {
        if (Interlocked.CompareExchange(ref _occupied, 1, 0) == 0) // atomic winner-takes-spot
        {
            _vehicle = v;
            return true;
        }
        return false; // kisi aur ne pakad liya
    }

    public void Free()
    {
        _vehicle = null;
        Interlocked.Exchange(ref _occupied, 0);
    }

    public bool IsFree() => Volatile.Read(ref _occupied) == 0;

    public bool Fits(VehicleType vt) => vt switch
    {
        VehicleType.Motorcycle => true,                 // kahin bhi fit
        VehicleType.Car        => Type != SpotType.Small,
        VehicleType.Truck      => Type == SpotType.Large,
        _                      => false
    };
}

class Level
{
    public int Floor { get; }
    private readonly List<ParkingSpot> _spots;          // ordered => "nearest" = first free
    private int _available;                              // O(1) full-check, koi full lock nahi

    public Level(int floor, List<ParkingSpot> spots)
    {
        Floor = floor;
        _spots = spots;
        _available = spots.Count;
    }

    // Lock-free allocation: har spot ka CAS + ek Interlocked counter
    public ParkingSpot? Allocate(Vehicle v)
    {
        if (Volatile.Read(ref _available) == 0) return null;   // full ho to fast fail
        foreach (var s in _spots)                              // order mein scan = nearest pehle
        {
            if (s.Fits(v.Type) && s.IsFree() && s.TryOccupy(v))
            {
                Interlocked.Decrement(ref _available);
                return s;
            }
        }
        return null; // full ya koi compatible spot nahi
    }

    public void Release(ParkingSpot s)
    {
        s.Free();
        Interlocked.Increment(ref _available);
    }

    public int AvailableCount() => Volatile.Read(ref _available);
}

class Ticket
{
    public string Id { get; }
    public string SpotId { get; }
    public Vehicle Vehicle { get; }
    public long EntryTime { get; }
    public long ExitTime { get; set; }
    public double Fee { get; set; }

    public Ticket(string id, string spotId, Vehicle v, long entryTime)
    {
        Id = id; SpotId = spotId; Vehicle = v; EntryTime = entryTime;
    }
}

// Singleton via Lazy<T> — thread-safe, lazy, koi manual locking nahi
sealed class ParkingLot
{
    private static readonly Lazy<ParkingLot> _instance = new(() => new ParkingLot());
    public static ParkingLot Instance => _instance.Value;
    private ParkingLot() { }

    private readonly List<Level> _levels = new();
    private readonly ConcurrentDictionary<string, (ParkingSpot Spot, Level Level)> _ticketToSpot = new();

    public void AddLevel(Level l) => _levels.Add(l);

    // Concurrent-safe: har spot claim atomic; levels lowest-first scan (nearest)
    public Ticket Park(Vehicle v)
    {
        foreach (var level in _levels)
        {
            var spot = level.Allocate(v);      // andar thread-safe
            if (spot != null)
            {
                var t = new Ticket(Guid.NewGuid().ToString(),
                                   spot.Id, v, NowMs());
                _ticketToSpot[t.Id] = (spot, level);
                return t;
            }
        }
        throw new InvalidOperationException($"Parking full for {v.Type}"); // saaf "full" signal
    }

    public double Unpark(Ticket t)
    {
        // TryRemove double-exit safe banata hai: doosri call ko false milega
        if (!_ticketToSpot.TryRemove(t.Id, out var entry))
            throw new ArgumentException("Invalid/used ticket");

        entry.Level.Release(entry.Spot);       // spot free + level counter update (O(1))
        t.ExitTime = NowMs();
        t.Fee = ComputeFee(t);
        return t.Fee;
    }

    private double ComputeFee(Ticket t)
    {
        long hours = System.Math.Max(1, (t.ExitTime - t.EntryTime) / 3_600_000);
        return hours * 10.0; // $10/hr, min 1 hr
    }

    private static long NowMs() => DateTimeOffset.UtcNow.ToUnixTimeMilliseconds();
}
```
> **Alternative (lock-based `Level.Allocate`):** scan+occupy ko ek `lock` mein wrap karo:
> ```csharp
> private readonly object _lock = new object();
>
> public ParkingSpot? Allocate(Vehicle v)
> {
>     lock (_lock)
>     {
>         foreach (var s in _spots)
>             if (s.Fits(v.Type) && s.IsFree()) { s.TryOccupy(v); _available--; return s; }
>         return null;
>     }
> }
> ```
> Reason karna aasan; CAS version se thoda kam concurrent. Dono valid interview answer hain — trade-off bata do.

**Interview talking points / pitfalls:**
- **Race kahan hai?** Do gates ek hi free spot pick karte hain. Fix: atomic claim — ya to spot pe `Interlocked.CompareExchange`, ya level lock ke andar occupy. `IsFree()` check karke phir do steps mein occupy karna (bina atomicity) classic bug hai.
- **Nearest spot:** spots ko ordered rakho (ya per-level free-spots ki priority structure) taaki pehla free compatible spot *hi* nearest ho.
- **Full-lot check sasta hona chahiye:** per level ek `Interlocked`-maintained counter "hum full hain?" ke liye scanning/locking se bachata hai.
- **Poore lot ko lock mat karo** — per level lock (ya per spot lock-free) taaki alag floors parallel chalein.
- **`Unpark` ko spot→level mapping chahiye** O(1) release + counter update ke liye — yahan ticket map mein tuple ke roop mein store kiya.
- **Idempotency:** ticket ko `ConcurrentDictionary` se `TryRemove` se hataana double-exit pakad leta hai (doosri call `false` return karti hai).
- Agar gates back up karein to **fairness/entry queue**, aur **overflow handling** (waiting queue vs. reject) ko extensions ke roop mein mention karo.

# Interview Cheat-Sheet

| Design | Key concurrency tools | Main gotcha |
|--------|-----------------------|-------------|
| Singleton | `Lazy<T>` / `static readonly` (runtime-managed) | Manual double-checked locking mat likho; `Lazy<T>` mode `ExecutionAndPublication` hona chahiye |
| Producer–Consumer | **bounded** `BlockingCollection<T>` ya `Channel<T>` | Unbounded → OOM; koi back-pressure nahi |
| Thread-safe Cache | `ConcurrentDictionary` + `GetOrAdd` mein `Lazy<T>`, eviction ke liye lock | `GetOrAdd` factory do baar chal sakti hai → `Lazy<T>` mein wrap; multi-key eviction ko lock chahiye |
| Rate Limiter | `Interlocked` / chhoti `lock` critical section, per client `ConcurrentDictionary`, `System.Threading.RateLimiting` | Single-node only; window-edge bursts; unbounded client map |
| Parking Lot | Per-level `lock` **ya** `Interlocked.CompareExchange` CAS + `Interlocked` counter | Do gates ek spot; check-then-act race |
| Counters | `Interlocked.Increment` | Akela `volatile` `++` ke liye atomic NAHI |
| Read-heavy state | `ReaderWriterLockSlim` | Writer starvation; writes pe abhi bhi lock |
| Timed / non-blocking acquire | `Monitor.TryEnter(obj, timeout, ref taken)` | `Monitor.Exit` `finally` mein bhoolna |

**Quick decision rules:**
- Compound action pe atomicity chahiye → **`lock`** (Monitor) — sabse chhota correct tool pehle.
- Sirf ek flag ki visibility chahiye → **`volatile`** (ya `Volatile.Read/Write`).
- Ek atomic counter chahiye → **`Interlocked.Increment`** (`volatile` nahi).
- Ek concurrent map chahiye → **`ConcurrentDictionary`** (+ get-or-load ke liye `GetOrAdd` mein `Lazy<T>`).
- Tasks chalane hain → **`Task.Run`/`Task.WhenAll`** (I/O: bas `await`; CPU-bound ko `SemaphoreSlim`/`MaxDegreeOfParallelism` se cap karo).
- Threads ke beech kaam hand off karna hai → **`BlockingCollection<T>`** ya **`Channel<T>`** (bounded).

# How to talk about thread-safety in an interview

**Hinglish mein:** Interview mein thread-safety samjhane ka ek clean formula:
1. **Shared mutable state clearly batao** — "yeh data multiple threads share kar rahe hain" (jaise free-spot map, token count, LRU list).
2. **Us pe hone wale operations batao** — read hai, write hai, ya **compound** ("pehle check phir act", "pehle padho phir badlo")? Races hamesha compound operations mein chhupi hoti hain.
3. **Sabse chhota correct tool chuno:** immutable > `Interlocked` > concurrent collection > fine-grained lock > coarse lock. Aur kyun chuna, woh batao.
4. **Critical section chhoti rakho** — lock ke andar network/DB call mat karo; `lock` ke andar `await` kabhi mat karo.
5. **Failure modes khud se bolo:** race condition, deadlock (lock hamesha same order mein lo), starvation (fairness), memory blow-up (collections bounded rakho), visibility (`volatile`).
6. **Scale ki baat karo:** "yeh single server pe correct hai; multiple servers ke liye main state Redis/DB mein rakhta with atomic operations."
7. **Trade-offs hamesha batao:** simple vs fast. Sabse fancy solution har baar zaroori nahi — correct aur maintainable pehle.

**Yaad rakhne wali one-liner:**
> "Pehle isse **correct** banao (shared state protect karo), phir **fast** banao (lock chhota karo, lock-free sirf wahan jaao jahan faayda ho)."
